## 2. 产品定位

**一句话定义**：LinkForge 是一个把「长链 → 短码 → 302 跳转」这条读多写少链路做到可量化高性能的短链平台。

**它的核心不是功能数量，而是跳转读路径的性能可解释性。** 因此：

- 写路径（创建短链）是低频、可以慢；读路径（跳转）是高频、必须快且稳定。
- 每一个性能优化都必须有**优化前后对比数字**，没有对比数据的优化视为未完成。
- 全链路必须能在别人机器上**一键复现**（评审者视角，见 §8）。

**与 bit.ly / 微博短链这类产品的取舍差异**：本项目不追功能广度（不做用户体系、不做营销漏斗、不做二维码），换来的是对**缓存分层、防穿透、限流、异步统计**这几个点的深度和可讲清楚的权衡。

**为什么选这个题目**：短链天然是读多写少、缓存收益极高的场景，能在一个单体内同时承载「缓存穿透/击穿/雪崩」「限流」「异步化」「压测对比」四类面试高频考点，且不需要微服务就能讲透。

## 3. 目标用户与使用场景

### 3.1 主 persona：分享者

把长链贴到社交平台、聊天、文档里的人。诉求只有三个：短、能点开、能看到被点了多少次。
不关心：短码长什么样、背后是哪个数据库、有没有 API 文档。

### 3.2 副 persona：运营者

手里有一批自己创建的短链，需要看某条短链的 PV/UV/来源分布，并清理失效或误建的链接。
v1 里运营者与分享者是**同一个人**（无用户体系，见 §5），后台靠 Token 保护，不区分操作人。

### 3.3 第三 persona（本项目特有，会反向约束设计）：评审者

面试官或看简历的人。他会做三件事：

1. 按 README 起环境；
2. 跑仓库里给的压测脚本，看我们的数字是不是真的；
3. 读代码找「实现和描述不一致」的地方。

**这条 persona 直接产生硬性约束**：环境必须 `docker compose up` 一键起，压测脚本必须能直接跑并产出可复现结果（见 §8）。凡是「只有作者本机能跑通」的东西，v1 不通过。

## 4. 用户故事与验收标准

统一约定：`short_code` = 短码，`target_url` = 原始长链。

### US-1 创建短链

**As** 分享者，**I want** 把长链换成短链，**so that** 分享出去更短且可统计。

- Given 一个合法 `target_url`（仅 http/https），When 调用创建接口，Then 返回一个 **7 位**固定长度 `short_code`。
- 验收：返回的 `short_code` 立即可用于跳转，无需等待。
- 验收：非法协议（`javascript:`、`file:`、`data:`）被拒绝，返回参数错误，**不落库**。
- 验收：超长 `target_url`（超过约定上限）被拒绝并给出明确错误。

### US-2 自定义短码

**As** 分享者，**I want** 指定一个好记的短码，**so that** 分享出去更符合品牌或语义。

- Given 一个符合字符集/长度规则且未被占用的自定义短码，Then 创建成功且该短码指向给定长链。
- 验收：短码规则违例（含非法字符、超长、超短）返回参数错误。
- 验收：短码落在**保留字黑名单**内（`api`、`admin`、`actuator`、`health`、`favicon.ico`、`static`、`error` 等，黑名单**配置化**，新增无需改代码）返回参数错误。
- 验收：短码已被占用（含历史已过期但未清理的记录）返回**冲突**错误，**不做静默覆盖**。

### US-3 跳转

**As** 访问者，**I want** 点开短链就到目标页，**so that** 我不关心中间发生了什么。

- Given 一个存在且未过期的短码，Then 返回 **302** 并携带 `Location` 指向原始长链。
- 验收：P99 < 50ms（见 §6）。
- 验收：跳转响应**不产生同步数据库写**（统计走异步，见 §5）。
- 验收：短码格式非法时按「不存在」处理，不泄露内部错误细节。

### US-4 失效与边界

- 短码已过期 → 返回 **410 Gone**（语义：曾经存在但已失效）。
- 短码不存在（含从未创建、已被删除、被布隆过滤器判定不存在）→ 返回 **404 Not Found**。
- 请求被限流 → 返回 **429 Too Many Requests**，并带 `Retry-After`。
- 验收：以上四种错误响应体格式统一，便于调用方判断。

### US-5 访问统计

**As** 运营者，**I want** 看到短链的 PV/UV/IP/来源，**so that** 我知道推广效果。

- Given 短链已被访问若干次，Then 能在 10 秒内查到该短链当天的 PV。
- 验收：统计口径按**自然日**聚合；UV 为当日去重访客数。
- 验收：跳转接口的响应时间**不随统计功能开启而变差**（统计异步化）。
- 验收：统计落库失败不导致跳转失败。

### US-6 删除短链

**As** 运营者，**I want** 删除一条短链，**so that** 误建或失效的链接立刻停止生效。

- Given 一个存在的短码，When 调用删除，Then 该短码**立即**不可跳转（返回 404）。
- 验收：删除时**同步删除缓存**，采用 **Cache Aside**（先落库状态变更，再删缓存），**不采用改缓存**。
- 验收：删除是幂等的——重复删除同一短码不报错。

### US-7 幂等性（v1 明确不做）

- **v1 同一 `target_url` 重复创建，每次都新建一个短码，不做幂等返回**。
- 即：连续两次提交相同长链 → 得到两个不同短码，各自独立统计、独立过期、独立删除。
- 理由见 §5「不做」清单。验收：不存在「相同长链返回相同短码」的行为，也不会因重复提交报错。

## 5. 功能范围

### 5.1 做（v1）

| 编号 | 功能 | 关键语义（PRD 只锁语义，不锁实现） |
|---|---|---|
| F-1 | 短码生成 | 全局唯一、只读不可改；**固定 7 位**（Base62）；由**发号器**保证无碰撞，唯一索引仅作兜底 |
| F-2 | 自定义短码 | 受字符集、长度、保留字黑名单约束；不可被覆盖 |
| F-3 | 过期时间 | 可指定；不指定则永久有效；过期判定以秒级时间为准，测试需可注入时间 |
| F-4 | 302 跳转 | 根路径 `/{code}`；低延迟；不写库 |
| F-5 | 访问统计 | 按天聚合 PV；UV 去重；记录 IP 与来源（Referer）；异步批量落库 |
| F-6 | 防穿透 | 布隆过滤器前置判断 + 空值缓存 |
| F-7 | 防击穿 / 防雪崩 | 热点短码保护；缓存 TTL 加随机抖动 |
| F-8 | 限流 | 跳转按 IP 限流；后台接口独立限流 |
| F-9 | 后台-查统计 | `/admin/**` 独立路径，环境变量 Token 鉴权 |
| F-10 | 后台-删除短链 | `/admin/**`，删除同时按 Cache Aside 删缓存 |
| F-11 | 可观测 | 健康检查 + 关键指标暴露（跳转 QPS、缓存命中率、限流拒绝数） |

**接口路径形态（v1 定稿）**：

- 跳转走根路径 `/{code}`——最短、最贴近真实使用、压测最真实。
- 代价与对策：根路径必须维护**保留字黑名单**，避免 `/{code}` 吃掉 `/api/**`、`/admin/**`、`/actuator/**` 等系统路径；黑名单来自配置，创建时校验、启动时断言。
- 后台统一挂 `/admin/**`，与跳转链路**物理隔离**：跳转链路不得依赖 admin 模块（详见 §7）。

### 5.2 不做（v1，逐条给理由）

| 不做项 | 为什么暂不做 |
|---|---|
| 多租户 / 用户体系（注册、登录、找回密码、权限角色） | 与性能主线无关，是典型范围黑洞；v1 用环境变量 Token 保护后台即可 |
| 301 永久跳转 | 浏览器会永久缓存，统计会失真，且无法回收误建短链（详见 §7 决策 D-3） |
| 短链编辑 / 短码改绑 | 与「短码只读不可改」冲突；改绑会让已分享出去的链接语义漂移 |
| 幂等创建（同长链复用短码） | 需要额外索引与并发去重逻辑，且「两个短码各自统计」在短链场景更符合直觉；v1 明确每次新建 |
| 点击热力图、转化漏斗、地域分布 | 属于分析产品范畴，需要明细日志长期留存，成本高收益低 |
| 原始访问明细日志长期留存 | 存储与隐私成本高；v1 只保留按天聚合结果（见 §6 容量假设） |
| QR 码生成 | 纯附加功能，不产生任何性能或架构考点 |
| A/B 分流、权重跳转 | 会把跳转路径从「查一次就能答」变成「带业务规则」，直接损害核心指标 |
| 短信/邮件验证、防滥用注册 | 无用户体系则不需要 |
| 微服务拆分 | 与「先单体跑通，再优化」原则冲突；单体足以承载 §6 的量级 |
| 分库分表 | v1 数据量不需要（见 §6 容量假设与估算依据）；提前做只会增加复杂度且无法验证收益 |
| 消息队列（RocketMQ/Kafka） | v1 用「Redis 计数 + 定时批量落库」已满足异步统计；MQ 作为 v2 备选，在统计链路成为瓶颈后再引入 |

## 6. 非功能需求

### 6.1 性能指标（全部可测）

| 指标 | 基线 | v1 目标 | 测量方式 |
|---|---|---|---|
| 跳转单机 QPS | ~2k（无缓存直查库） | 5k~1w | 压测脚本，固定并发与时长 |
| 跳转 P99 延迟 | ~200ms | < 50ms | 同上，取 P99 |
| 缓存命中率 | 0%（无缓存） | > 95% | 应用指标 |
| 数据库写入压力 | 100%（每次跳转写库） | 降低 80% | 优化前后 DB 写入次数对比 |

**基线与目标的关系**：先按「无优化」跑一次基线并留存数据，再逐项优化，每项优化后重跑同一脚本。**没有优化前后对比数据 = 本阶段不通过。**

### 6.2 容量假设（具体数字）

| 项 | v1 假设值 |
|---|---|
| 短链总量 | **1000 万条** |
| **活跃短链比例** | **1%**（即约 **10 万条活跃**） |
| 日跳转量 | **500 万次** |
| 统计保留时长 | **90 天** |
| 峰值因子 | 日均值的 **5 倍**（约 290 QPS 均值 → 峰值约 1450 QPS 量级） |

**估算依据**：

1. **短链总量 1000 万**——按「一个中小型内容/营销团队一年积累的自有短链」量级取整。该量级下单表存储与单列唯一索引完全可控（千万级 row 对 MySQL 8 属于舒适区），**不足以成为分库分表的理由**，这也是 v1 明确不做分表的量化依据。
2. **活跃短链比例 1%（约 10 万条活跃）**——⭐ **这条是「不需要分表」结论成立的关键假设**：绝大多数历史短链不再被访问，且不产生按天统计行。没有这条假设，`1000 万 × 90 天 = 9 亿行`会直接推翻单表结论，两者不自洽。
   - 由此推出的统计行数上界：**10 万活跃 × 90 天 = 约 900 万行**，单表可控。
   - 该假设必须**在第 1 周基线阶段用真实数据校验**；若实测活跃比例远高于 1%，则统计表的保留策略或分表策略必须重新评估（见 `docs/DATABASE.md` 容量估算）。
3. **日跳转 500 万次**——按短链总量的 50% 当天被访问一次估算。折算均值约 58 QPS（500 万 / 86400），远低于单机目标；**真正的压力来自峰值与热点**，所以容量规划的重点是缓存与限流，而不是数据库吞吐。
4. **统计保留 90 天**——按「一个季度」的运营复盘窗口取值，覆盖绝大多数「看推广效果」的需求。按天聚合后行数上界 = **活跃**短链数 × 天数，**因此原始明细不做长期留存**（对应 §5.2 的不做项）。
5. **峰值因子 5 倍**——经验取值，用于压测时设置并发量，避免只测均值导致线上峰值崩。

> 这些数字是**设计输入**，不是承诺。它们的作用是让 DATABASE 的索引/分片决策、ARCHITECTURE 的缓存容量决策有据可依。

### 6.3 可用性与一致性

- **可用性优先级**：跳转路径 > 统计路径 > 后台管理路径。跳转路径故障即产品不可用；统计短暂延迟可接受。
- **一致性**：短链的创建/删除要求**强一致**（创建后立即可跳、删除后立即可失效）；统计数据允许**分钟级最终一致**。
- **降级要求**：缓存层整体不可用时，跳转必须能回退到查库并继续服务（性能下降可接受，不可用不可接受）。限流组件异常时**放行**而非拒绝。

### 6.4 安全与合规

- **协议白名单**：`target_url` 仅允许 http/https，杜绝 `javascript:`、`data:` 等开放重定向与注入风险。
- **后台鉴权**：`/admin/**` 全部要求环境变量提供的固定 Token；Token 通过环境变量注入，**禁止提交进仓库**（`.gitignore` 已覆盖 `.env` 与本地配置文件）。
- **限流**：跳转按 IP 限流；后台接口独立限流，避免后台被刷影响跳转。
- **隐私**：IP 仅用于当天的去重统计与限流，**不做长期明细留存**；聚合后不保留可直接定位个人的记录。

### 6.5 可观测与可部署

- 可观测：健康检查端点；跳转 QPS、缓存命中率、限流拒绝数、统计落库延迟可观测。
- 可部署：`docker compose up` 起全套依赖；应用配置全部走环境变量，无「本机硬编码路径」。
- 可回滚：每个可运行阶段对应一次提交，回滚粒度到阶段。

## 7. 关键实现约定与决策记录

PRD 只锁定**语义与对外行为**，实现方式留给 ARCHITECTURE。

### 7.1 短码

- 全局唯一、**只读不可改**。短码一旦生成，永不改变其语义（删除即整个链接失效，而不是换一个码）。
- **长度固定 7 位**，字母表为 Base62（`[0-9A-Za-z]`）。7 位 Base62 空间约 **3.5 万亿**（62⁷ ≈ 3.52 × 10¹²），对 §6.2 的 1000 万总量有约 5 个数量级余量。
- **生成方式：发号器分配**——Redis `INCR` 发号（或数据库号段），将序号编码为 Base62 并**左补零到固定 7 位**。发号器保证每个号唯一，因此**短码天然无碰撞**；唯一索引只作为兜底防线，不是防碰撞的主要手段。
- **Redis 不可用时的降级**：切换到**数据库号段**发号，保证创建功能不因 Redis 故障而不可用（呼应 §6.3 的可用性优先级）。
- ⚠️ **明确不做**：不用「随机生成 + 冲突重试」作为主要生成方式——在 1000 万量级下随机取 7 位虽然空间充足，但把正确性押在重试上不如押在发号器的单调唯一性上。
- **自定义短码**走独立校验路径（字符集、长度、保留字黑名单），其唯一性由数据库唯一索引判定，冲突返回冲突错误，**不做静默覆盖**。
- 生成过程**不得**依赖「先查库再写入」这种有竞态的判重。

### 7.2 跳转语义

- 使用 **302**，不使用 301（决策 D-3）。
- 跳转路径**不写数据库**：统计只做内存/缓存层计数，落库由异步任务完成。
- 跳转路径与 admin 模块**物理隔离**：跳转链路的代码、依赖、限流配置、线程池均不得依赖 `/admin` 相关组件（决策 D-4）。

### 7.3 过期语义

- 过期时间精确到秒，默认不设置（永久有效）。
- 过期判定必须以**服务端当前时间**为准，不接受客户端传入时间。
- 测试可控性要求：时间获取必须可注入/可替换，不允许在业务逻辑里直接散落调用系统时间（否则过期场景无法写单测）。

### 7.4 统计语义（决策 D-5、D-6）

- **只保留按天聚合结果**，不长期留存原始访问明细（对应 §5.2）。
- **UV 使用 Redis HyperLogLog**：
  - 标准误差率约 **0.81%**（Redis 官方给出的 HLL 精度，p=14）；
  - 内存成本约 **12KB / key**（每个 key 对应「一个短码一天」的 UV 基数估计）。
  - 取舍：UV 是估算值而非精确值。**推荐理由**——若用精确去重（Set 存每个独立访客），内存随访客数线性增长，500 万次/日的量级下成本不可控；HLL 用固定 12KB 换取 0.81% 误差，在「看推广效果」的使用场景下完全够用。**代价必须写进文档与简历**，面试被问到 UV 精度时要能答出误差率与内存数字。
- **PV 用计数累加**，与 UV 分开存储。
- **IP 与来源（Referer）**：IP 用于当日 UV 去重与限流；来源用于渠道分布统计。
- **异步落库**：跳转只做计数，定时任务批量写入；落库失败必须可重试且不阻塞跳转。

### 7.5 缓存一致性（决策 D-7）

- 删除/更新短链时采用 **Cache Aside：先改数据库状态，再删缓存**，**不使用改缓存（先写库再写缓存）**。
- 推荐理由：删缓存的实现更简单，且天然规避「并发写缓存导致脏数据长期驻留」的问题；改缓存在并发下需要额外版本号/cas 才能正确。
- 已知代价：删缓存后的第一个请求会回源查库（一次缓存未命中），需要靠 §7.6 的手段兜住。
- **删除缓存失败时必须报警/记录**，否则会出现「库里已删、缓存仍可跳转」的脏读窗口；v1 的处理策略是删除操作自带重试，仍失败则记录并暴露指标（不静默吞掉）。

### 7.6 防穿透 / 击穿 / 雪崩

| 问题 | v1 策略 |
|---|---|
| 缓存穿透（查不存在的短码） | 布隆过滤器前置拦截 + **空值缓存 30 秒**（空值缓存必须有较短 TTL，避免长期占用） |
| 缓存击穿（热点 key 失效瞬间） | 热点短码延长/逻辑过期保护；回源加互斥，避免同一热点被并发打穿到数据库 |
| 缓存雪崩（大批 key 同时失效） | 基础 TTL 上叠加随机抖动，避免同时失效 |

### 7.7 限流

- 跳转按 IP 限流，阈值配置化（默认量级：每秒 20 次/IP）。
- 限流作用域：跳转与后台**分开计数**，后台限流更严。
- 失败策略：限流组件不可用时**放行**（可用性优先于防刷）。

### 7.8 决策记录汇总

| 编号 | 决策 | 选项 | 选择 | 推荐理由 | 代价 |
|---|---|---|---|---|---|
| D-1 | 短码路径形态 | 根路径 `/{code}` vs 前缀 `/r/{code}` | **根路径** | 最短、最贴近真实、压测最真实 | 必须维护保留字黑名单 |
| D-2 | 自定义短码 | 支持 vs 不支持 | **支持** | 简报要求；且是校验与并发冲突的好素材 | 需处理保留字与占用冲突 |
| D-3 | 跳转状态码 | 301 vs 302 vs 307 | **302** | 不被浏览器永久缓存，统计不失真，误建链接可回收 | 每次访问都到服务端（这正是我们要统计的） |
| D-4 | 后台管理是否进 v1 | 进 / 只做删除 / 都不做 | **进 v1，第 4 周实现** | 简报第 3 节核心功能；「删除短链」是缓存一致性最佳素材 | 必须做物理隔离，否则拖累跳转链路 |
| D-5 | 统计明细 | 明细长期留存 vs 只存按天聚合 | **只存按天聚合** | 存储与隐私成本低 | 无法回答单次访问级问题 |
| D-6 | UV 去重 | 精确 Set vs HyperLogLog | **HyperLogLog** | 固定约 12KB/key，内存可控 | 约 0.81% 误差，是估算值 |
| D-7 | 缓存一致性 | Cache Aside 删缓存 vs 改缓存 vs 双写 | **Cache Aside 删缓存** | 实现简单，并发下不易留脏数据 | 删除后首个请求回源一次 |
| D-8 | 幂等创建 | 幂等复用 vs 每次新建 | **每次新建** | 语义直观，避免额外去重成本 | 同一长链会产生多个短码 |
| D-9 | 用户体系 | 做 vs 不做 | **不做** | 聚焦性能主线 | 无法区分是谁创建的链接、无法多租户 |

## 8. 成功指标与验收方式

v1 通过验收，必须**同时**满足以下硬性标准：

| 编号 | 硬性验收标准 | 验证方式 |
|---|---|---|
| A-1 | `docker compose up` 一键起全套环境（应用 + MySQL + Redis），无需手工建库建表以外的人工步骤 | 在**干净机器/干净目录**按 README 逐字执行 |
| A-2 | 仓库自带压测脚本，**可直接运行**并输出 QPS / P99 / 命中率 | 评审者不修改脚本、不填私有参数即可跑出结果 |
| A-3 | 有**优化前后对比数据**（基线 vs 优化后），且对比在同一脚本、同一并发下取得 | 压测报告 |
| A-4 | §6.1 四项性能指标全部达标 | 压测报告 |
| A-5 | 跳转链路 P99 < 50ms，且不产生同步数据库写 | 指标 + 数据库写入计数 |
| A-6 | 缓存命中率 > 95% | 应用指标 |
| A-7 | 后台 `/admin/**` 全部需要 Token，缺 Token 一律拒绝 | 手工验证（无 Token 请求被拒） |
| A-8 | 非 http/https 的目标地址一律被拒绝 | 用例验证 |
| A-9 | 核心逻辑（短码生成唯一性、过期判定、缓存一致性、限流）有自动化测试 | 测试报告 |

**「不合格」的定义（明确写出来，避免自我欺骗）**：

- 只有功能、没有压测数据 → 不通过。
- 压测数据来自与本仓库脚本不一致的跑法 → 不通过。
- 只能在本机跑通、README 步骤在别处失败 → 不通过。
- 性能数字只有「优化后」、拿不出基线 → 不通过。

## 9. 风险与依赖

### 9.1 技术风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 缓存与数据库不一致 | 删除后仍可跳转 | Cache Aside + 删除缓存重试 + 暴露失败指标（§7.5） |
| 布隆过滤器误判 | 真实短码被判不存在，返回 404 | 接受极低误判率；创建短链时同步写入布隆过滤器；保留「误判后可回源复核」的开关 |
| 热点短码打穿 | 单个 key 失效瞬间压垮数据库 | 回源互斥 + 逻辑过期保护（§7.6） |
| 短码发号器不可用（Redis 故障） | 无法生成新短码 | 降级到数据库号段发号（§7.1）；跳转不受影响 |
| 短码空间耗尽 | 无法生成新短码 | 7 位空间约 3.5 万亿，远超 §6.2 假设；需监控已分配序号水位 |
| 统计落库延迟/丢失 | 数据不准 | 保留 90 天聚合；失败可重试；跳转不因此失败 |

### 9.2 环境与工程风险（本机已实测）

| 风险 | 实测状态 | 应对 |
|---|---|---|
| JDK 版本错位 | 已装 JDK 17，但 PATH 生效 JDK 11、`JAVA_HOME` 指向 JDK 23 | 第 0 周统一到 **JDK 17 LTS**，写入 README 与构建配置 |
| 构建工具不在 PATH | Maven / Gradle 均未在 PATH 找到 | 第 0 周确认并固定一个（建议用 `mvnw` 包装脚本，避免依赖机器环境） |
| Docker 守护进程未运行 | CLI 29.6.2 / Compose v5.3.1 已装，daemon 未启动 | 第 0 周先解决；A-1 验收依赖它 |
| 本机无 wrk | wrk 不在 PATH，Windows 无原生支持 | 第 5 周定压测方案：容器内 wrk 或 JMeter；A-2 要求脚本可复现，必须把这个选择固化下来 |
| 沙箱对工作区外路径的写入限制 | 本机 DSH 沙箱以低完整性运行，工作区外路径（如 `~/.m2`、`~/.docker`）可能被拒绝写入 | 第 0/5 周若命中，改为把依赖目录放进工作区或调整配置；不在 v1 功能范围内 |
