## DR-001 构建工具：Maven + mvnw

- **决策**：构建工具采用 **Maven**，并通过 **Maven Wrapper（`mvnw` / `mvnw.cmd`）** 调用，不依赖机器上全局安装的 Maven。
- **选项**：Maven（全局安装） / Maven + Wrapper / Gradle + Wrapper / Gradle（全局安装）
- **结论**：**Maven + `mvnw`**。
- **理由**：
  1. Spring Boot 生态与 Java 后端面试最通用，减少沟通成本。
  2. 本机实测 Maven 不在 PATH，Wrapper 可自带固定版本，直接规避环境依赖。
  3. 满足 PRD A-1/A-2「在干净环境可复现」的硬性要求——评审者不需要预装 Maven。
- **代价与影响**：
  - `mvnw` 首次运行会下载 Maven 发行包并写入 `~/.m2/wrapper`。
  - ⚠️ **已知风险（必须验证）**：本机 DSH 沙箱以低完整性运行，**工作区之外的路径可能拒绝写入**。`~/.m2/wrapper` 与 `~/.m2/repository` 都在工作区外，第 0 周收口时**必须实测 `mvnw -v` 与一次完整构建**。
  - 若被拒绝，备选方案（按优先级）：① 把 Maven 本地仓库通过配置指向工作区内目录；② 把仓库路径配置为可由用户手动写入的位置并在 README 说明。**该验证是第 0 周的退出条件之一，不允许「先跳过、以后再说」。**

## DR-002 限流实现：Redis + Lua 自研令牌桶

- **决策**：跳转与后台的限流由 **Redis + Lua 脚本**实现（自研令牌桶 / 滑动窗口），**Redisson 仅作兜底对照，不进主路径**。
- **选项**：Guava/RateLimiter 本地限流 / Redisson `RRateLimiter` / Redis + Lua 自研 / 网关层限流
- **结论**：**Redis + Lua 自研**，主路径唯一实现。
- **理由**：
  1. 限流的**原子性**与「为什么必须用 Lua」是面试高频追问点，自研才能讲清楚。
  2. 本地限流在多实例下失效，Redis 方案天然可横向扩展，与「分布式短链平台」定位一致。
  3. 直接用 Redisson 会丢失这个考点，项目深度不足。
- **代价与影响**：
  - 需自行处理脚本加载、超时、异常降级；**限流组件异常时必须放行**（PRD §7.7 已定）。
  - Redisson 仅作为对照实现保留在代码中用于说明取舍，**不得出现在跳转主路径上**。

## DR-003 压测工具：容器内 wrk

- **决策**：压测采用 **容器内 wrk**；**JMeter 作为高复杂度场景备选**，不作为默认。
- **选项**：Windows 原生 wrk / 容器内 wrk / JMeter / k6
- **结论**：**容器内 wrk**。
- **理由**：
  1. 本机实测无 wrk，Windows 无原生支持；容器内运行可跨机器复现（PRD A-2）。
  2. wrk 脚本简单、结果稳定，适合「同一脚本前后对比」这一唯一判据。
- **代价与影响**：
  - ⚠️ **测量口径问题（必须写进压测报告）**：wrk 跑在容器网络、压宿主机上的服务时，流量跨了容器网络边界，**绝对延迟仅供参考**；**优化前后的比例才是关键结论**。
  - 缓解手段：优先把被测服务放进**同一 compose 网络**内加压；若做不到，报告中必须显式标注口径，禁止用跨网络测量的绝对延迟去对比单机目标值。

## DR-004 第 1 周基线必须记录环境快照

- **决策**：第 1 周的基线压测**必须同时记录环境快照**；第 2、3 周的所有对比数据**必须基于同一环境**。
- **理由**：性能数字脱离环境毫无意义；若基线在配置 A 上取、优化后在配置 B 上取，整个「优化前后对比」就是不可信证据，直接违反 PRD A-3。
- **记录项（缺一不可）**：CPU 型号与核数/线程数、内存容量、JDK 版本与发行方、Docker 资源限制（CPU/内存配额）、MySQL 与 Redis 版本、操作系统版本。
- **影响**：对比数据未标注环境快照的，视为无效数据，不允许进入压测报告与简历。环境快照模板见 `docs/ROADMAP.md` §5。

## DR-005 第 4 周排期调整（admin 拆分）

- **决策**：把原「第 4 周 = 异步统计 + 过期 + admin 后台」**拆开**：
  - **「删除短链」提前到第 3 周末**；
  - **「查统计」留在第 4 周末**；
  - **第 4 周只做「异步统计 + 过期」**；
  - **第 5 周不再承接 admin**。
- **变更原因**：
  1. 第 4 周同时塞三块内容是本路线最重的一周，且有**真实依赖阻塞**：「查统计」依赖统计落库完成，放在统计之前做只能返回假数据或空壳接口。
  2. 「删除短链」的实质考点是**缓存一致性**，而缓存体系恰好在第 3 周成型；第 3 周末落地它，能与 Cache Aside 的验证在同一阶段闭环，不必等到第 4 周。
  3. 拆分后第 4 周只剩一条主线（统计异步化），与「每阶段只推进一个最小可运行阶段」的执行规则一致。
- **代价与影响**：
  - 第 3 周负载上升，成为全程第二重的一周，需要在 §11 时间预算里显式标注。
  - `docs/PRD.md` D-4 中「admin 排到第 4 周」的表述需理解为：**admin 主体（删除）在第 3 周末、查询在第 4 周末**，PRD 的功能范围本身（F-9、F-10 进 v1）**不变**。

## DR-006 第 4 周溢出时的裁剪顺位

- **决策**：**不做整体顺延**。保留应急预案：若第 4 周实际溢出，**Grafana 面板深度是第 5 周第一顺位裁剪项**。
- **选项**：整体顺延一周 / 裁剪可观测性深度 / 压缩统计功能 / 压缩跳转主线
- **结论**：**裁剪 Grafana 面板深度**，不动主线。
- **理由**：
  1. 可观测性存在的最低要求是「有指标暴露 + 能用」，面板美观度与仪表盘数量不影响任何 PRD 验收标准。
  2. 压缩统计功能或跳转主线会直接违反 PRD（A-3、A-4、A-5），而裁剪面板深度不违反任何一条。
- **绝不能砍的清单（优先级最高）**：第 1 周基线数据、优化前后对比、`docker compose up` 一键起、跳转链路性能。
- **影响**：第 5 周开始时先确认第 4 周是否达标；若未达标，立即执行本顺位，而不是拖延整个计划。

## DR-007 布隆过滤器：Redis 唯一权威 + 规格定死 + 定时重建

- **决策**：
  1. **Redis 布隆过滤器为唯一权威**，本地**不做**第二份布隆；本地缓存只缓存「确定存在」的正结果。
  2. **布隆检查与缓存查询合并为一次 Redis 往返**（Lua 脚本或 pipelining），避免跳转路径上两次独立网络往返。
  3. **规格写死**：`n = 1000 万`（容量上界）、`p = 0.01`（误判率）、`m ≈ 12MB`（位数组）、`k = 7`（哈希函数个数）。
  4. **重建策略**：**创建时写穿**（新增短码立即写入）+ **每小时从 DB 定时全量重建**；写穿失败**只记日志**，不阻塞创建。
- **选项**：本地布隆 / Redis 布隆 / 两者都有 / 无布隆只靠空值缓存
- **结论**：**Redis 唯一权威 + 写穿 + 每小时重建**。
- **理由**：
  1. 多实例下本地布隆状态发散、重启要预热、重建要同步，运维与一致性成本远超收益。
  2. 正结果已被本地缓存覆盖，本地布隆带来的额外收益很小，却引入两份真相。
  3. 规格定死是为了让内存占用**可预测、可写进文档**，而不是运行时算出来一个说不清的数字。
  4. 写穿失败只记日志：布隆过滤器是**性能优化**而非正确性来源，误判（false positive）只会导致多一次回源查库，**不会返回错误结果**；小时级重建会自愈。
- **代价与影响**：
  - ⚠️ **重建期间必须避免假阴性**：全量重建时不能先删旧 key 再建，否则窗口期内真实短码会被判「不存在」而返回 404。方案见 `docs/ARCHITECTURE.md` §7。
  - 每次跳转增加一次 Redis 访问（已通过「合并为一次往返」缓解）。
  - 删除短链**不从布隆过滤器移除**（布隆不支持删除），删除后该短码会多一次回源查库，属可接受代价。

## DR-008 Caffeine：第 2 周引入，只做正结果缓存

- **决策**：**第 2 周引入 Caffeine**，作为独立一层缓存，**只缓存正结果**；`maximumSize` 与 `expireAfterWrite` **在第 2 周就定下来**，第 3 周只补单飞（回源互斥）与调参。
- **选项**：第 3 周再引入 / 第 2 周引入 / 不做本地缓存
- **结论**：**第 2 周引入，只做正结果缓存**。
- **理由**：
  1. 第 2 周与第 3 周分别产出一次对比数据，能清楚拆出「Redis 的收益」与「本地缓存的收益」，让压测报告的因果干净；若一次性在第 3 周堆上，只会得到一个说不清来源的合数（违反 PRD A-3 的可解释要求）。
  2. 只缓存正结果：负结果（不存在）交给空值缓存 + 布隆过滤器，避免本地缓存被大量随机不存在的短码挤爆。
- **代价与影响**：
  - 第 2 周多写一层缓存逻辑，第 2 周工作量上升。
  - 多实例下本地缓存**必然不一致**（同一短码在不同实例上可能一个命中缓存、一个回源），这是可接受的：短链的读路径是「最终一致即可」，删除是靠 Cache Aside 删 Redis + 本地缓存按 TTL 自然过期。
  - ⚠️ 已知边界：删除短链后，**已缓存该短码正结果的实例会在本地 TTL 到期前继续 302**。该窗口上限等于本地 `expireAfterWrite`，必须取值足够小并写进文档，同时作为「删除后立即失效」验收的**例外说明**（PRD US-6 的验收在单实例或本地缓存 TTL 过期后成立）。

## DR-010 限流降级：v1 只做放行，不做开关

- **决策**：限流组件（Redis 或 Lua 脚本）不可用时，跳转**一律放行**；**v1 不做**「本地内存兜底限流」开关。
- **选项**：放行（可用性优先） / 本地内存兜底限流 / 可配置开关
- **结论**：**v1 只做放行，不做开关**。
- **变更原因**：
  1. 开关本身是一个**需要被测试、被文档化、被压测验证**的功能分支，在 v1 范围内属于纯增量成本，而不做开关不违反任何 PRD 验收标准。
  2. 本地兜底限流在多实例下**阈值形同虚设**（每个实例各自计数），会给出一层虚假的安全感，比「明确放行」更容易误导。
  3. PRD §7.7 已定「可用性优先于防刷」，只做放行是与该原则一致的**最简实现**。
- **代价与影响**：
  - 已知风险：Redis 不可用期间平台**没有防刷能力**。该窗口必须有**可观测信号**（指标 + 告警），否则会静默失去防护。
  - **v2 可加本地兜底**：届时须同时说明其多实例阈值失真问题，并明确它只用于「降低而不是阻断」流量。
  - 本节与 `docs/ARCHITECTURE.md` §9 的降级矩阵、§12 的降级矩阵必须一致。

## DR-011 短码生成方式：改为发号器（Redis INCR / 数据库号段），固定 7 位

- **决策**：短码生成由「雪花 ID → Base62 → 6~8 位」改为 **发号器分配**：
  1. **Redis `INCR` 发号**（主路径），将序号编码为 **Base62** 并左补零到**固定 7 位**；
  2. **Redis 不可用时降级到数据库号段发号**，保证创建功能不因 Redis 故障而不可用；
  3. 数据库 `short_code` **唯一索引仅作兜底**，不再是防碰撞的主要手段；
  4. `short_code` **固定 7 位**（不再写「6~8 位」）。
- **选项**：
  - **A（选中）** 发号器 INCR/号段 → Base62 → 7 位；
  - B 保留雪花 ID，**接受 11 位短码**并诚实写明长度代价；
  - C 雪花 ID 截断 / 随机生成 + 冲突重试（**已否决**）。
- **变更原因**（原表述存在技术缺陷，必须更正）：
  1. **长度不兼容**：雪花 ID 是 64 位整数，其 Base62 表示约 **11 位**，**压不到 7 位**。原 PRD 的「雪花 ID → Base62 → 6~8 位」在数学上不成立。
  2. **截断必然碰撞**：若强行截断到 7 位，在 1000 万量级下按生日悖论，碰撞概率**接近 100%**。这是把正确性押在运气上，不可接受。
  3. **时钟回拨风险**：雪花 ID 依赖机器时钟，回拨会导致重复发号或需阻塞等待，在单机 Docker 环境中收益为零、风险非零。
  4. **发号器方案可辩护**：序号单调唯一 ⇒ 短码**天然无碰撞**，正确性由发号器的单调性保证，而不是由重试概率保证；这也是面试中更好讲清楚的方案。
- **空间核算**：Base62 的 7 位空间 = 62⁷ ≈ **3.52 万亿**（3.5 × 10¹²），对 PRD §6.2 的 1000 万总量有约 **5 个数量级**余量。
- **代价与影响**：
  - **新增一个运行时依赖**：创建路径依赖 Redis（或数据库）发号。已用「降级到数据库号段」兜住——创建是低频写路径，降级带来的性能损失可接受。
  - **短码可枚举**：序号连续 ⇒ 短码连续可猜（`0000001`, `0000002`…）。v1 **接受**该代价（短链本身是公开跳转，不承载隐私）；若未来需要不可枚举，可在编码时叠加一层可逆混淆（思路：Feistel/乘法置换），**属 v2**。
  - **需要监控发号水位**，避免序号逼近 7 位空间上界。
  - 受影响的文档已同步：`docs/PRD.md` §5.1 F-1、§4 US-1、§7.1、§9.1；`docs/DATABASE.md`（唯一索引定位、号段表）；`docs/ARCHITECTURE.md` 跳转/创建流程说明。

## DR-012 容量假设补充：活跃短链比例 1%

- **决策**：在容量假设中**显式引入「活跃短链比例 = 1%」**这一关键假设（即 1000 万总量中约 **10 万条活跃**）。
- **变更原因（原假设与结论不自洽）**：
  - 原估算把「统计保留 90 天」与「短链总量 1000 万」并列，隐含推导出 `1000 万 × 90 天 = 9 亿行`统计行数；
  - 而 PRD 同时宣称「**不需要分库分表**」。9 亿行的按天聚合表与「单表可控」的结论**直接矛盾**，是我上一轮的估算漏洞。
  - 引入 1% 活跃比例后，统计行数上界 = **10 万活跃 × 90 天 = 约 900 万行**，单表可控，与「不做分表」的结论**自洽**。
- **代价与影响**：
  - ⚠️ 该假设**必须用真实数据校验**：第 1 周基线阶段统计「当日被访问过的短码数 / 短码总量」，得出实际活跃比例并回填文档。
  - **若实测活跃比例显著高于 1%**，则必须重新评估统计表的保留策略（缩短保留期）或分表策略，并追加新的决策记录——**不允许默默沿用失真假设**。
  - 该假设同时是 `docs/DATABASE.md` 容量估算与「不做分区表」结论的前提。

## DR-013 接口契约层决策（时间格式、查询鉴权、删除语义、429 例外、CORS）

- **决策**（一组相互关联的契约决策，统一记入本条，依据见 `docs/API.md`）：
  1. **时间格式**：传输统一 ISO-8601 带时区，格式 `yyyy-MM-dd'T'HH:mm:ssXXX`；**数据库存 UTC**；不带时区的请求时间视为非法参数。
  2. **查询接口 `GET /api/v1/links/{code}` 不鉴权**，但**限流比跳转严格**（60 次/分钟 vs 跳转 20 次/秒）；只返回非敏感元信息，**不返回统计**。
  3. **删除语义**：删除**不存在**的短码 → **404**；删除**已删除**的短码 → **200 + `alreadyDeleted: true`**。
  4. **429 的 body 极简**：只含 `code`、`message`、`retryAfter`，**不带 `details`、不带嵌套结构**；**必须带 `Retry-After` 响应头（单位秒）**，且头与 body 的数值必须一致。
  5. **v1 不开启 CORS**，v2 再做。
  6. 创建接口也**按 IP 限流**（10 次/分钟，比跳转严格）；统计查询日期范围**默认 7 天、最大 90 天，超出 400 而非静默截断**。

- **理由**：
  1. **ISO-8601 带时区**：人类可读、无时区歧义；epoch 秒虽紧凑，但排查日志时不可读。
  2. **查询不鉴权**：短链本身是公开跳转的，目标 URL 通过一次 302 即可获得，给查询加鉴权属于**安全剧场**；但查询无跳转的业务价值，故**用更严的限流替代鉴权**控制成本。
  3. **删除区分 404 与 200**：「已删过了」是重复执行同一意图（幂等成功），「从未存在」通常是调用方**拼错短码**。都返回 200 会让拼写错误无法被发现；都返回 404 会让幂等重试看起来像失败。
  4. **429 极简**：429 发生在大流量滥用场景，此时不应再消耗序列化与带宽成本；其处置动作只有一个——等一会儿再来。
  5. **v1 不开启 CORS**：v1 无浏览器前端（后台只提供接口），跨域来源无从约束；开启 CORS 等于放宽一个不存在需求的边界。
  6. **日期范围超限返回 400**：静默截断会让调用方误以为自己拿到了完整数据。

- **代价与影响**：
  - `alreadyDeleted` 把**信息性差异**放在 body 而非状态码，使 200 保持「意图已达成」的单一含义；调用方若忽略该字段，重复删除会被当作首次删除（不影响正确性）。
  - 不鉴权的查询接口**可被枚举**短码并读取目标 URL。v1 接受：短码可枚举本已是 DR-011 的已知代价，且目标 URL 通过跳转同样可探测。
  - 区间 UV 的**跨天去重**能力缺失已记入 `docs/API.md` §7.2 与 P-2（v2）。
  - CORS 在 v2 开启时**禁止使用 `*` 配合凭证**。

## DR-014 跳转失败体完整，但 429 例外；Location 必须绝对 URL

- **决策**：
  1. **跳转失败返回完整统一 JSON 错误体**（带 `LINKFORGE-4xxx`），保持全接口契约一致；**唯一例外是 429**（DR-013 第 4 条）。
  2. **`Location` 头必须是绝对 URL**，由环境变量 **`SHORTLINK_BASE_URL`** 拼接生成；**该变量必填，缺失时应用启动失败**，不提供默认值。
  3. 开发环境取值 `http://localhost:8080`；`SHORTLINK_BASE_URL` **不得依赖请求的 `Host` 头**。
  4. 跳转响应加 **`Cache-Control: no-store`**。
- **理由**：
  1. 契约一致性优先，且失败请求占比低、不构成性能负担，压测报告也好统计失败路径。
  2. **依赖 `Host` 头会引入 Host 头投毒风险**；反向代理场景下 `Host` 与实际对外域名可能不一致，会产生错误的跳转地址。
  3. **必填而非给默认值**：默认值看似方便，但生产忘记设置时会返回 `http://localhost:8080/...` 这种**对外不可用的短链**——错误发生在用户点击时，排查成本极高。**启动即失败是更安全的选择。**
  4. `no-store` 与 PRD D-3「用 302 避免浏览器缓存、保证统计不失真」的初衷保持一致；不显式禁止，中间层仍可能缓存跳转结果。
- **代价与影响**：
  - 部署时必须正确设置 `SHORTLINK_BASE_URL`，否则应用**无法启动**（这是有意设计的失败方式）。
  - 多域名场景（不同短链走不同域名）v1 **不支持**——需要给短链记录增加域名维度，属 v2。

## DR-015 短码路径字符校验与尾斜杠处理

- **决策**：
  1. `GET /{code}` 中，**Base62 之外的字符直接返回 400**（不进入查找逻辑），不返回 404。
  2. **尾斜杠返回 400**（如 `/abc1234/`），**不做重定向、不做自动纠正**。
  3. 短码**长度不符**（如非 7 位）返回 **404**，不返回 400。
  4. 自定义短码规则：正则 **`^[a-zA-Z0-9]{4,8}$`**，**大小写敏感**，保留字黑名单在**应用层校验**，占用冲突返回 **409**。
- **理由**：
  1. **非 Base62 字符是请求格式错误，不是「查不到」**：区分 400 与 404 能让调用方立刻发现自己的拼接 bug（例如把短码错误地 URL 编码后传入）。
  2. **尾斜杠不自动重定向**：自动纠正会让「一个短码对应多个可访问 URL」，破坏短码与链接的一一对应，并使缓存与统计出现双份记录。明确拒绝比静默纠正更容易排查。
  3. **长度不符返回 404 而非 400**：长度不符虽然一定查不到，但它**格式合法**（仍是 Base62 字符串），语义上属于「不存在」而非「非法请求」。
  4. 自定义短码 4~8 位比自动生成的固定 7 位更宽松，便于用户取有意义的名字；大小写敏感避免「大小写不同却指向同一链接」的隐性混淆。
- **代价与影响**：
  - 调用方必须保证短码**不被 URL 编码**且**不附加尾斜杠**；该约束已写入 `docs/API.md` §4.1 与验收脚本。
  - 长度校验与 7 位固定长度的耦合关系：若将来缩短码长度（DR-011 的编码空间调整），`docs/API.md` §4.1 的「长度不符→404」判定需同步更新。

## DR-016 Maven 发行包与依赖来源改用阿里云仓库（Maven Central 本机不可达）

- **决策**：

## DR-017 MySQL 宿主机端口映射到 3307（容器内保持 3306）

- **决策**：MySQL 容器**内部端口保持 3306**，**宿主机映射端口改为 3307**（由 `.env` 的 `MYSQL_PORT` 控制）；Redis 保持 6379 不变。
- **变更原因（第 0 周实测）**：

- **为什么不选其它方案**：
  - ❌ 停止/卸载宿主机 MySQL80：会破坏用户本机其它用途的环境，代价远大于改一个端口。
  - ❌ 不暴露 MySQL 端口（只走 compose 网络）：第 1 周起需要用本机客户端（Workbench/CLI）排查数据，不暴露会显著拖慢调试。

  - **容器内与 compose 网络内仍用 `mysql:3306`**：第 1 周起应用的 JDBC 连接串在 compose 网络内必须是 `mysql:3306`；只有从宿主机直连时才用 `localhost:3307`。这两个值不一致是**有意的**，不要"统一"。
  - `.env.example` 中 `MYSQL_PORT` 默认值需为 `3307`，并保留中文注释说明避让原因；`.env`（本地）同样为 3307。
  - 已验证：`docker compose ps` 显示 `0.0.0.0:3307->3306/tcp`，容器 `healthy`；MySQL 版本 `8.4.11`；错误密码被拒。

## DR-018 模块划分由 4 模块改为 5 模块（补 `linkforge-core`）

- **决策**：Maven 模块由 4 个改为 **5 个**，新增 **`linkforge-core`**：

  | 模块 | 职责 |
  |---|---|
  | `linkforge-core` | **`Link` 实体、`LinkRepository`、`ShortCodeGenerator`、`RedirectCacheService` 接口** |
  | `linkforge-redirect` | `RedirectController`、缓存实现、布隆过滤器、限流 |
  | `linkforge-stats` | `StatsService`、定时落库 |
  | `linkforge-admin` | `AdminController`、鉴权、统计查询 |
  | `linkforge-app` | 启动 + 装配 |

- **依赖规则（编译期强制）**：

  ```
  app      → core + redirect + stats + admin
  redirect → core + stats
  stats    → core
  admin    → core + stats
  redirect → admin   ❌ 禁止
  admin    → redirect ❌ 禁止（新增约束）
  ```

- **变更原因（原 4 模块划分有一个走不通的设计洞）**：
  「admin 删除短链」需要访问 `Link` 实体与 `LinkRepository`，但在 4 模块（`app`/`redirect`/`stats`/`admin`）下**两条路都堵死**：
  1. `Link` 放 `redirect` ⇒ `admin` 必须依赖 `redirect` ⇒ **admin 被拖进跳转链路的全部依赖**（缓存、布隆、限流），与 DR-009「物理隔离」的初衷相反；
  2. `Link` 放 `admin` ⇒ `redirect` 必须依赖 `admin` ⇒ **直接违反 DR-009**。
  ⇒ 领域模型与数据访问**必须有一个既不属跳转也不属后台的归属**，这正是 `core` 存在的理由。
- **新增 `admin → redirect ❌ 禁止` 的理由**：隔离必须是**双向**的。只禁 `redirect → admin`，admin 仍可通过依赖 redirect 把跳转链路的重量级实现（缓存、限流）拉进后台进程；双向禁止才能保证两个模块都只依赖 `core` 的抽象。
- **回退规则（修改，替代 DR-009 中的 3 模块方案）**：D1 骨架若卡住超过一天，回退到 **4 模块：`app` / `core` / `redirect`（含 stats）/ `admin`**，**不是 3 模块**。
  - 修改原因：3 模块（`app`/`core`/`admin`）会让 `core` 过重——它会被迫同时承载跳转实现与统计实现，`core` 从"共享抽象层"退化成"什么都能装的杂物间"，ArchUnit 也就无从守起。
  - 触发回退时**必须**在本文件追加新的决策记录，并同步 `docs/ARCHITECTURE.md`。
- **代价与影响**：
  - 模块数 +1，父 POM 的 `<modules>` 与依赖声明各多一处；
  - **`core` 必须保持"薄"**：只放领域模型、仓储接口与跨模块共享的服务抽象，**不得**放缓存/限流/布隆的具体实现，否则它会变成第二个"什么都能装"的模块；
  - `docs/ARCHITECTURE.md` §3 的模块表与依赖图需同步为 5 模块（下次修订时更新）。

## DR-021 数据访问实现（MyBatis Mapper）放 `linkforge-core`，并修正 DR-018 的「core 必须保持薄」

- **决策**：
  1. **数据访问框架选 MyBatis**（`mybatis-spring-boot-starter` 3.x），**不用 Spring Data JDBC**。理由：国内面试默认预期、SQL 完全可控、便于讲索引与执行计划。
  2. **MyBatis Mapper 接口与 XML 放在 `linkforge-core`**，不在 `redirect`：

     | 内容 | 位置 |
     |---|---|
     | `Link` 实体 | `linkforge-core/src/main/java/com/linkforge/core/domain/` |
     | `LinkRepository` 接口 | `linkforge-core/src/main/java/com/linkforge/core/repository/` |
     | MyBatis Mapper 接口 | `linkforge-core/src/main/java/com/linkforge/core/infrastructure/persistence/` |
     | `LinkMapper.xml` | `linkforge-core/src/main/resources/mapper/` |

  3. **`core` 新增依赖**：`mybatis-spring-boot-starter`、`mysql-connector-j`。`core` **不再**是「只依赖 `spring-boot-starter`」。
  4. **⚠️ 修正 DR-018 中「`core` 必须保持薄」的表述**：该条**作废**，改为：**`core` 是共享抽象 + 共享持久化访问层**，允许装载被多模块共用的实体、仓储接口与数据访问实现；**仍然禁止**在 `core` 放缓存/限流/布隆/Web 等**只属于某一模块**的实现。

- **变更原因（原「Mapper 放 redirect」的方案走不通）**：
  「admin 删除短链」要改 `status`、查统计要查主表，**admin 必须能访问 `LinkRepository`**。原方案下两条路都堵死：
  1. Mapper 实现在 `redirect` ⇒ `admin` 要看到实现就必须依赖 `redirect` ⇒ **违反 DR-018**；
  2. `admin` 不依赖 `redirect` ⇒ **看不到 Mapper 实现** ⇒ Spring 装配时找不到 `LinkRepository` 的 Bean ⇒ **启动失败**。
  ⇒ 数据访问实现必须落在**双方都能依赖、又不互相依赖**的模块，即 `core`。
- **为什么让 `core` 变重而不要各写一份 Mapper**：`admin` 与 `redirect` 各写一份针对同一张表的 Mapper 是**重复代码**，而且两份 SQL 会随时间漂移（一处改了索引/字段，另一处不动），比 `core` 变重更糟。**DR-018 的核心是 `redirect` 与 `admin` 互不依赖，不是 `core` 必须薄**——隔离的目标是防止跳转链路与后台互相拖累，而不是限制共享层的体积。
- **代价与影响**：
  - `core` 及其下游（`redirect`、`stats`、`admin`）都会传递性获得 MyBatis。三者本都需要数据访问，**属预期**。
  - ⚠️ **新的边界必须守住**：`core` 现在可以装持久化，但**不得**装 Web、缓存、限流、布隆的具体实现——那些是 `redirect` 的职责，放进来会让 `admin` 被迫拖入跳转链路的全部重量，等于绕过 DR-018 的双向隔离。
  - `linkforge-core` 的 `package-info.java` 中「保持薄，不装具体实现」的描述**需要同步修正**（在数据访问层落地那一步一并改，避免留下过期 javadoc）。
  - ⚠️ **Mapper 放 core 的真实代价（启动时踩到，已修）**：**Spring 组件扫描与 MyBatis Mapper 扫描是两套独立机制**。
    `@SpringBootApplication(scanBasePackages = "com.linkforge")` 只影响 Spring 的组件扫描；
    MyBatis 自动扫描用的是 Spring Boot 的「自动配置包」，其值来自 **`@SpringBootApplication` 所在类的包**
    （即 `com.linkforge.app`），与 `scanBasePackages` **无关**。因此 core 下的 Mapper 不会被自动发现，启动报：
    ```
    No MyBatis mapper was found in '[com.linkforge.app]' package.
    ... required a bean of type 'com.linkforge.core.infrastructure.persistence.IdSegmentMapper' that could not be found.
    ```
    **修法**：在 `LinkForgeApplication` 上显式声明
    `@MapperScan("com.linkforge.core.infrastructure.persistence")`，并保留 `scanBasePackages`。
    两个 Mapper 上的 `@Mapper` 注解保留作为双保险。
    **这条是「Mapper 与启动类不同模块」这一布局的必然代价**：包路径不同源，就必须显式指定扫描范围。

## DR-022 短码发号：号空间区间划分、单向降级与已知回退风险

- **决策**：
  1. **号空间划分为两个互不重叠的区间**（不变量集中在 `core.domain.IdSpace`）：

     | 发号器 | 区间 | 容量 |
     |---|---|---|
     | Redis `INCR`（主路径） | `[100_000, 1_000_000_000)` | **9.999 亿**，按日创建 **10 万**条可用约 **27.4 年** |
     | 数据库号段（降级路径） | `[1_000_000_000, 62^7)` | 约 3.52 万亿（约为 Redis 区间的 3521 倍） |

     ⚠️ **口径更正**：本文档与进度台账此前写「可用约 **74 年**」，是**算术错误**。
     正确推导：`(1_000_000_000 − 100_000) / 100_000 / 365 = 999_900_000 / 100_000 / 365 = 27.39 年`。
     74 年对应的日创建量是 **37,020 条**，与已记录的「日创建 10 万条」假设不符——
     两个数字不能同时成立，以 **27.4 年 / 日创建 10 万条** 为准。
     该口径已由 `Base62Test.capacityIsSufficient` 断言锁住，避免文档与测试各算各的。
     27 年对练习项目已远超需求，**不构成缩短码长度的理由**。

  2. **降级是单向的**：一旦 Redis 发号失败，该实例**永久**切到号段，**不做恢复探测、不切回**。
  3. **Redis 清空用方案 A 处理**：启动时若 key 不存在则初始化为区间起点（`SETNX`，**绝不无条件 `SET`**）。
  4. **新增指标 `shortlink_id_conflict_total`**：在插入短链的唯一索引冲突重试处累加。该指标突增说明 Redis 号段可能回退。
  5. **边界值对齐**：`id_segment.max_id` 初始值必须是 **999999999**，不是 100000——号段发出的是 `max_id + 1`，写成 100000 会让号段从 **100001** 起，落进 Redis 区间内。

- **变更原因**：
  1. **为什么用区间划分而不是「共用同一个号空间」**：共用空间需要跨存储同步（Redis 恢复后要把号段的进度同步回计数器），任何一次同步失败都会导致重复发号。区间划分把唯一性从「依赖同步正确」降为「依赖常量正确」，**重启、切换、并发都安全**，无需任何协调。
  2. **为什么降级不回切**：回切必须知道「号段已经用到了哪里」，否则 Redis 会从旧值继续，而那段区间已被号段用过，**必然重复发号**。代价明确：一次短暂的 Redis 抖动会让该实例之后所有发号永久走数据库号段（每次约每 1000 个号一次数据库往返，低频写路径可接受）；重启实例即可回到 Redis 路径。
  3. **为什么必须处理 1 的偏移**：这是重复发号的经典成因——区间边界漏一个号，两个发号器就会在同一位置发出同一个短码。原方案把「Redis 起点 100000」与「数据库号段 max_id = 100000」并列，实际会让号段从 100001 起，与 Redis 首个发出的 100001 **重合**。现由 `IdSpace` 常量推导 + 单元测试断言锁住。

- **⚠️ 已知风险（Redis 被清空导致号段回退）**：
  - **场景**：Redis 丢失数据（RDB 恢复到旧快照、`FLUSHDB`、换实例）后，`INCR` 会从很小的值重新开始，发出的短码可能与历史短码**重复**。
  - **v1 的三层处置**：
    1. 启动时 `SETNX` 初始化为区间起点（不无条件覆盖，避免重启即重置）；
    2. **真正的兜底是 `short_link.uk_short_code` 唯一索引**——重复短码会被数据库拒绝，**不会静默覆盖他人链接**；应用层做有限重试；
    3. `shortlink_id_conflict_total` 指标让运维能**立即发现**回退（该指标理论上应恒为 0，突增即为异常）。
  - **v2 根治方案**：在 `short_link` 增加 **`seq` 列**（记录该短码对应的发号序号），启动时取 **`MAX(seq)`** 作为 Redis 计数器的初始值，让号段跟随**数据库里的真相**，而不是依赖一个可能被清空的计数器。**这是 v2 待办，不是 v1 遗漏。**

- **实现约束（评审重点）**：
  1. **取号段的事务必须独立于业务事务**（`REQUIRES_NEW`）：否则创建短链失败回滚时号段推进也回滚，而进程内 `current` 已前进，多实例下会重复分配同一段号。
  2. **`@Transactional` 不能写在自调用的方法上**：Spring 的注解依赖代理，类内自调用（`this.fetchNextSegment()`）**注解完全失效且不报错**。因此取段逻辑抽到独立 Bean `IdSegmentAllocator`。
  3. **自增必须「先取后判」**：`long next = current.getAndIncrement(); if (next >= limit) {取下一段}`。写成 `if (current.get() < limit) { current.incrementAndGet() }` 会让两个线程同时通过判断，**同一个号被发出两次**。
  4. **Base62 编码表自己写**，不用 `Long.toString(n, 62)`：JDK 的 `radix` 只支持 **2~36**（`Character.MAX_RADIX == 36`），传 62 会被**降级为 10 进制**——实测 `Long.toString(10, 62) == "10"`，而 36 进制才是 `"a"`，本项目的表是 `0-9A-Za-z`（序号 10 → `"A"`）。**JDK 根本不支持 base62，无法作为对照实现**。
  5. **`seq >= 62^7` 抛异常 + 记 ERROR**：绝不回绕、绝不截断。回绕会让已发出的短码指向另一条链接。
  6. **号段取号的并发写法（血泪教训，实测得出）**：
     - ❌ **不能用 `getAndIncrement` 走快路径**：取段会把 `current` **重置**回新段段首，而「读到旧值、却在重置之后才写回」的线程会用陈旧值覆盖计数器，**跳过整个区间的号**。实测连发 8000 个号只得到 **7947** 个唯一值。
     - ❌ **不能用「先取后判 + `Math.max(segmentStart, wasted + 1)` 推进」**：并发下多个越界线程各自把计数器推得很远，同样丢号。
     - ❌ **不能用 `Long.MIN_VALUE` 之类的哨兵配合「加一后比较」**：`Long.MIN_VALUE + 1` 仍小于 limit 初值，哨兵漏进业务逻辑（实测报错「序号不能为负: -9223372036854775808」）。哨兵必须显式判断。
     - ✅ **正确写法：CAS 抢占** `current.compareAndSet(observed, observed + 1)`，仅在 `observed <= limit` 时尝试；CAS 在值已被他人改动时**失败**，因此绝不会用陈旧值覆盖 `current`。取段全程持锁 + 双检。修复后 8000/8000 唯一。
     - ✅ **取段必须惰性**（首次使用时才取）：构造时取段会让「只为装配而创建的实例」也消耗一段号，并让单元测试互相污染（实测某用例期望 999999999 却得到 1000000999）。

- **影响**：`docs/DATABASE.md` D-4（号段步长最终取值）仍待第 1 周 D7 压测确定；`short_link.seq` 列与 `MAX(seq)` 初始化列入 v2 待办。

## DR-023 MySQL 8.4 JDBC 连接开启 allowPublicKeyRetrieval

- **背景**：MySQL 8.4 默认认证插件是 `caching_sha2_password`。JDBC 驱动**首次**连接时需要用服务器的
  RSA 公钥加密密码，而驱动默认**不允许自动获取该公钥**，于是连接被拒：
  ```
  Public Key Retrieval is not allowed
  SQL State  : 08001
  Error Code : 0
  ```
- **决策**：**本地开发**的连接串加 `allowPublicKeyRetrieval=true`，紧跟 `useSSL=false` 之后：
  ```
  jdbc:mysql://localhost:3307/linkforge?useSSL=false&allowPublicKeyRetrieval=true&connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true&characterEncoding=utf8
  ```
  （时区参数部分见 **DR-032**；此处只关心 `allowPublicKeyRetrieval`，两者互不冲突。）
- **代价（必须显式承认）**：允许驱动**明文索取服务器公钥**，会削弱中间人（MITM）防护——
  攻击者若能在链路上冒充服务器，就能提供自己的公钥。因此该参数**仅限本地开发**。
- **生产要求**：改为 **`useSSL=true` 并配置证书**，**不要开 `allowPublicKeyRetrieval`**。
  生产环境要么用 TLS 加密链路（推荐），要么改用 `mysql_native_password`（不推荐，MySQL 8.4 已不鼓励）。
- **触发位置（改动一致性清单，共 4 处）**：
  1. `.env`（本地，未跟踪）
  2. `.env.example`
  3. **`docker-compose.yml` 的应用服务（第 5 周添加，容器内 URL 用 `mysql:3306`，同样要带该参数）**
  4. `docs/` 中所有含具体 URL 的示例（当前为 `docs/PROGRESS.md`）
  - ⚠️ `application.yml` 的注释里只有 `...?` 形式的占位示例，不含具体参数，无需改。
- **关联输入源**：`application.yml` 的 Redis 配置同理从环境变量读取
  （`REDIS_HOST` 默认 `localhost` / `REDIS_PORT` 默认 `6379`，`timeout: 50ms` 对齐
  `docs/ARCHITECTURE.md` §11.3）。**容器内 `REDIS_HOST` 必须设为 `redis`**——
  `localhost` 在容器内指向应用容器自身。

## DR-024 错误码格式改为 `LINKFORGE-<HTTP状态码>-<两位序号>`

- **决策**：错误码格式由连写形式改为**连字符分隔**：
  ```
  LINKFORGE-400-01
     │       │   └── 该状态码下的第 n 个错误（01~99，从 01 起）
     │       └────── HTTP 状态码（3 位）
     └────────────── 固定前缀
  ```
- **变更原因（初版格式有两个真实问题）**：
  1. **无法一眼看出 HTTP 状态**：`LINKFORGE-4410` 是 410 段、`LINKFORGE-4029` 是 429 段、
     `LINKFORGE-5003` 是 503 段——读者必须做心算或查表，而错误码的第一用途就是**快速定位问题**。
  2. **`4xxx` 段容纳不下 5xx**：初版把格式定义为 `LINKFORGE-4xxx`，却又列了 `LINKFORGE-5003`（503），
     **格式定义与实例自相矛盾**。新格式覆盖 `400`~`599`，4xx 用 `4xx` 段、5xx 用 `5xx` 段。
- **编号规则（写死）**：
  1. `LINKFORGE-` + HTTP 状态码（3 位） + `-` + 两位序号（`01`~`99`）。
  2. **状态码段与 HTTP 响应状态必然一致**；由 `ErrorCode` 枚举同时持有 `code` 与 `httpStatus` 保证。
  3. 序号按「同一状态码内的新增顺序」递增，**不复用、不回收**。
  4. **已发布不得复用或改义**；废弃只在表中标记 `已废弃`，**不删行**。
  5. 新增只允许**追加**，且必须同步 `docs/API.md` §8 与 §9。
- **兼容性说明**：本次修订发生在**任何接口发布之前**（D4 尚未写代码），
  因此是**兼容性无损**的格式变更，不构成契约破坏。
- **代价**：错误码字符串变长 2 个字符；`docs/API.md` §8/§9 与全部示例已同步。
- **权威记录位置**：规则以**本节 + `docs/API.md` §8** 为准，两处必须一致。
- **⚠️ 400 段拆分（同一次修订内完成）**：`400` 段由 3 个码扩为 5 个，理由是**「调用方需要采取的修复动作不同」就拆**：

  | 错误码 | 含义 | 为什么独立 |
  |---|---|---|
  | `400-01` | 通用参数错误（缺失/超长/时间格式/日期范围/短码路径字符） | 纯用法错误，兜底 |
  | **`400-02`** | **协议不允许**（scheme 不在 http/https 白名单） | **安全边界**：若与「字段超长」共码，运维无法从错误码分布区分「开放重定向探测」与「调用方传了超长 URL」——前者需立刻告警。**把安全事件与用法错误混在一个码里等于放弃该信号** |
  | `400-03` | 自定义短码格式非法 | 写错字符集，改字符串即可 |
  | `400-04` | 自定义短码命中保留字 | 调用方在**猜系统路径**（`/api`、`/admin`），与字符集错误是不同行为 |
  | `400-05` | `expireAt` 不是将来时间 | 需要**改时间点**（或对齐时钟），而非改格式 |

  **粒度判据（写死）**：**「调用方需要采取的修复动作不同」就拆，「同一动作」就合并。**
  拆得过细的代价是错误码表变长、调用方要处理的码变多；但上述五类的修复动作确实互不相同，因此拆分是可辩护的。
  契约层修订发生在**任何接口发布之前**，**兼容性无损**。

## DR-025 保留字黑名单大小写不敏感

- **决策**：自定义短码的**保留字黑名单比较大小写不敏感**——`api`、`Api`、`API`、`aPi` 一律拒绝。
- **⚠️ 与短码本身规则的关系（看似矛盾，实为有意）**：
  - 短码本身**大小写敏感**（`Abc123` ≠ `abc123`，DR-015）；
  - **保留字比较却大小写不敏感**。
  两者并存是刻意的：**保留字保护的是一条路径而不是一个短码值**。
- **理由**：保留字存在的目的是**防止短码路径吃掉系统路径**（如 `/api/...`、`/admin/...`）。
  而 HTTP 路径在不同实现/容器/代理下的**大小写归一化行为并不一致**
  （有的会把路径小写化，有的不会）。若只拦小写 `api`，则 `Api` 在某些部署下**仍会撞上 `/api`**，
  防线的有效性就依赖于「部署环境恰好不做归一化」——这是不可接受的假设。
  **比短码本身的大小写规则更保守，是因为它防的是路径冲突，而不是短码值冲突。**
- **面试口径**（可能被问「为什么 `API` 不能用作自定义短码」）：
  短码大小写敏感保证了 `Abc123` 与 `abc123` 是两个不同短码；但保留字黑名单是**路径级防线**，
  必须假定路径比较可能被归一化，因此采用大小写不敏感的最保守比较。
- **实现要求**：黑名单加载时统一转小写存入 `Set`，校验时把 `customCode` 转小写后比较。
- **影响**：`docs/API.md` §5.2 与 §8 错误码表（`LINKFORGE-400-03`）已标注「大小写不敏感」。

## DR-026 `SHORTLINK_BASE_URL` 的启动校验与归一化

- **决策**：`SHORTLINK_BASE_URL` 除「必填、缺失即启动失败」（DR-014）外，**再加启动期校验与归一化**：
  1. **非法值直接启动失败**（不允许带病启动）：
     - 空字符串 / 全空白；
     - **纯斜杠**（`/`、`//`）——无法推断出 scheme 与 host；
     - **无 scheme**（`localhost:8080`、`example.com`）——会产生非法 URL；
     - scheme 不是 `http`/`https`。
  2. **末尾斜杠归一化**：`http://localhost:8080/` 与 `http://localhost:8080` 必须产出**同一个**结果，
     拼接结果中**不得出现 `//`**（如 `http://localhost:8080//abc1234`）。
- **理由**：
  - **非法值必须启动即失败**，而不是等到第一次创建短链才 500 —— 与 DR-014 的取向一致：
    配置错误暴露得越早，排查成本越低；
  - **纯斜杠与无 scheme 是最容易犯的两个错**：前者看起来「有值」所以不会被必填校验拦住，
    后者在本地开发时很自然（人习惯了 `localhost:8080`），但拼出来的 `shortUrl` 对外不可用。
  - 末尾斜杠是**复制粘贴**最常见的结果，必须归一化而不是要求使用者手工去掉。
- **影响**：该归一化逻辑可**纯函数化**（输入配置字符串 → 输出规范化 base 或抛异常），
  因此必须有单测覆盖（见 D4 设计第 6 节：空串、纯斜杠、无 scheme、末尾单斜杠、末尾双斜杠）。
- **关联**：`docs/API.md` §11 已声明该变量「缺失时启动失败」，本决策把**非法值**也纳入同一处理。

## DR-027 时间的时区处理链（D4 定稿，D5 复用）

- **决策**：时间的表示与转换在全链路固定为一条链条，不允许各处自行选择类型：
  | 环节 | 类型 / 格式 |
  |---|---|
  | HTTP 传输 | ISO-8601 带偏移，`yyyy-MM-dd'T'HH:mm:ssXXX` |
  | Java 入/出边界 | **`OffsetDateTime`**（保留偏移，不做隐式换算） |
  | 持久层（MyBatis ↔ MySQL） | **`LocalDateTime`（UTC）**，对应 `TIMESTAMP` 列 |
  | 比较与判定（如过期） | 统一在 **`Instant`** 语义下比较 |
- **转换链**：
  ```
  OffsetDateTime --withOffsetSameInstant(UTC).toLocalDateTime()--> LocalDateTime(UTC) 写库
  LocalDateTime(UTC) --atOffset(UTC)--> OffsetDateTime --withOffsetSameInstant(服务端时区)--> 响应
  ```
- **理由**：
  1. **入/出用 `OffsetDateTime` 而不是 `Instant`**：请求带的是偏移（`+08:00`），用 `OffsetDateTime` 能保留调用方原始意图，也便于按服务端时区回渲染；`Instant` 会丢失偏移信息。
  2. **持久层用 `LocalDateTime`（UTC）而不是直接存 `Instant`/带偏移对象**：MySQL 列是 `TIMESTAMP`，若应用层存一个带偏移的对象，就会出现**偏移被应用一次、又被驱动解释一次**的双重换算，时间整体偏移数小时。存 **UTC 的 `LocalDateTime`** 是唯一不产生歧义的组合。
     > ⚠️ **本条的前提是「数据库会话时区为 UTC」**，由 **DR-032** 的连接串参数
     > （`connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true`）保证。
     > 若会话时区是本地（如 `+08:00`），数据库**自己生成**的 `created_at` / `updated_at`
     > 就是本地墙上时钟，被应用层当 UTC 解释时会**再多加 8 小时**——
     > 这个分支在 D4 启动验证时才实测暴露出来，是 DR-027 最初未覆盖到的盲区。
  3. **`expire_at` 为 NULL 表示永久有效**（DATABASE §4.1），因此持久层不能改用 `Instant`（它无 null 语义优势，反而多一层包装）。
- **代价与影响**：
  - 需要一处**集中的时间转换工具/TypeHandler**，不允许各处在 DTO / Service / Mapper 里各写一遍 `toLocalDateTime()` 与 `atOffset()`；
  - ⚠️ **D5 的过期判定必须统一到 `Instant` 比较**：**不要**用「UTC 的 `LocalDateTime`」直接与 `LocalDateTime.now()`（本地时间）比较——在非 UTC 部署环境下会得出错误结论（例如把未过期的判成已过期）。要么统一转 `Instant`，要么统一用注入的 UTC 时间源。
  - **响应时区可配置**（默认 `+08:00`），但**存储永远是 UTC**，两者不得混用。

## DR-028 创建接口不返回 `Location` 头

- **决策**：`POST /api/v1/links` 成功返回 **201 Created**，**不添加 `Location` 响应头**。
- **选项与排除理由**：
  1. ❌ **`Location: <shortUrl>`**（指向跳转地址）——**语义混乱**：`Location` 在 201 中的含义是「新创建资源的地址」，
     而 `shortUrl` 是**给最终用户点击的跳转入口**，不是本 API 的资源端点。两者混用会让客户端误以为可以对它做后续 API 操作。
  2. ❌ **`Location: /api/v1/links/{code}`**（指向资源端点）——**该接口 D5 才存在**。
     现在返回一个尚不存在的 URL 是**指向空处**，客户端跟随会 404，比不加更糟。
  3. ✅ **不加**（选中）——`docs/API.md` 已定稿且未包含 `Location`；响应体里已有 `shortUrl`，客户端所需信息完整。
- **后续动作**：D5 完成查询接口 `GET /api/v1/links/{code}` **之后**，可再评估补 `Location: /api/v1/links/{code}`。
  **届时需先改 `docs/API.md` 再改代码**（契约优先）。
- **代价**：不符合「201 应带 `Location`」的严格 REST 惯例。可辩护的理由是：
  **返回一个客户端无法解析的资源端点（D5 前）或一个语义不符的跳转地址，都比不返回更糟**；
  且本接口的资源标识（`shortCode`）已在响应体中明确给出。

## DR-029 MyBatis 的 `boolean` 别名解析到包装类，基本类型必须用 `_boolean`

- **决策**：`LinkMapper.xml` 的 `<constructor>` 映射中，`is_custom` 的 `javaType` **必须写 `_boolean`**，不能写 `boolean`。
- **选项**：
  1. 改 XML 别名为 `_boolean`（**选中**）；
  2. 把 `Link` 的字段、构造器、getter 全改成包装类 `Boolean`；
  3. 改用 setter 映射绕开构造器（放弃不可变对象）。
- **结论**：**选项 1。`Link` 完全不动**（字段 `boolean`、构造器 `boolean`、getter `boolean` 全部保持基本类型）。
- **理由**：
  - **别名解析差异**：MyBatis 的 `TypeAliasRegistry` 里 `boolean` 注册的目标是 **`Boolean.class`（包装类）**，而 `_boolean` 才注册到 **`boolean.class`（基本类型）**。`<constructor>` 映射按 `javaType` 反射查找构造器，两者签名不匹配就找不到。
  - **DB 侧不可能为 null**：`is_custom` 列是 `TINYINT NOT NULL DEFAULT 0`，用基本类型语义正确，不需要包装类表达 `null` 的能力。
  - **改动面最小**：改 `Link` 会连带引出字段、getter 返回类型、`null` 检查、Service 层 `isCustom()` 调用的一串改动与潜在 NPE；改 XML 别名是**单点局部修复**，不触及任何业务代码。

- **⚠️ 完整故障链路（D4 启动验证实测，224 个单元测试全绿也测不到）**：

  ```
  1. LinkMapper.xml  <arg column="is_custom" javaType="boolean"/>
  2. MyBatis 用 TypeAliasRegistry 解析别名 "boolean"  ->  Boolean.class   ← 包装类
  3. <constructor> 按该类型反射查找 Link 的构造器
       实际查找签名：Link(Long, String, String, LinkStatus, Boolean, LocalDateTime, LocalDateTime, LocalDateTime)
       实际存在的签名：Link(Long, String, String, LinkStatus, boolean,  LocalDateTime, LocalDateTime, LocalDateTime)
       （Byte/short/int/long 同理，都必须写成 _byte/_short/_int/_long）
  4. 签名不匹配 ->
       org.apache.ibatis.reflection.ReflectionException: Error instantiating class
       com.linkforge.core.domain.Link with invalid types (Long,String,String,LinkStatus,Boolean,...)
       Caused by: java.lang.NoSuchMethodException: com.linkforge.core.domain.Link.<init>(..., java.lang.Boolean, ...)
  5. 表现为：POST /api/v1/links 返回 500 LINKFORGE-500-01
  ```

  **报错信息里的参数列表是「MyBatis 按别名解析后要找的签名」，不是 `Link` 实际声明的签名** —— 这是本次定位耗时最长的一个误解点。排查时必须先确认「XML 写的别名解析到什么类型」，而不是默认 XML 里写什么就是什么类型。

- **为什么 224 个测试全部漏过**：
  - `LinkCreationServiceTest` / `LinkControllerTest` 全部用 **mock 仓储**，不经过真实 `LinkMapper`；
  - `LinkControllerTest` 是 **`@WebMvcTest` 切片**，只加载 Web 层，连 `MyBatis` 配置都不装配；
  - 该缺陷**只存在于「真实 MyBatis + 真实反射构造器 + 真实 TIMESTAMP 列读回」这条路径上**，纯 mock 的单元测试在结构上永远测不到。
  - ⇒ 由 **DR-030** 的集成测试补上这个覆盖缺口。

- **影响**：`LinkMapper.xml` 的所有 `<constructor>` 基本类型参数一律用下划线别名；新增 Mapper 时同样适用。本条已写入 `LinkMapper.xml` 的行内注释，防止后续误改回 `boolean`。

## DR-030 `server.port` 必须显式声明（修复「配了但不生效」的死变量）

- **决策**：`linkforge-app/src/main/resources/application.yml` 显式声明 `server.port: ${APP_PORT:8080}`。
- **结论**：**必须显式配置，不依赖 Spring Boot 的默认 8080。**
- **理由**：
  - `.env` / `.env.example` 中 `APP_PORT=8080` 此前**从未被任何配置消费**——配置层没有 `server.port`，这是一个「配了但不生效」的死变量（断链）。
  - D3 的启动验证恰好在默认端口上通过（因为默认值恰好也是 8080），**掩盖了这个断链**，一直没被发现。
  - 显式声明后，配置值与实际生效值之间不再有「巧合」，改 `APP_PORT` 就能真实生效。

- **⚠️ 附注：Spring Boot 配置源的优先级（`SERVER__PORT` 这类环境变量的陷阱）**：
  - Spring Boot 的**环境变量优先级高于 `application.yml`**。IDE / 容器编排工具常注入形如 `SERVER__PORT` 的环境变量（双下划线作层级分隔符，等价 `server.port`），本项目在 IDE 内运行时就被注入过 `SERVER__PORT=59900`，导致 Tomcat 去抢占 59900 而启动失败。
  - 这类变量**无法靠改 `application.yml` 覆盖**——即使写了 `server.port`，环境变量依然赢。正确做法是**在启动进程内显式覆盖该环境变量**（本项目验证时用 `$env:SERVER__PORT = '8080'`），或用命令行参数 `--server.port=8080`（命令行参数优先级最高）。
  - **这是开发环境的工具特性，不是应用缺陷**：在用户自己的终端 / CI / 容器里不会有该变量注入。因此**不为它改动生产配置**，仅记录此现象供后续排查同类问题时参考。

- **影响**：`APP_PORT` 从死变量变为真实生效的配置项，与其他环境变量（`MYSQL_PORT`、`REDIS_PORT`）口径一致。

## DR-031 仓储层集成测试：复用真实 MySQL + `@EnabledIfEnvironmentVariable` 跳过

- **决策**：新增真实 MyBatis 集成测试（`LinkRepositoryMyBatisTest`），复用**已运行的本地 MySQL 容器**的**独立库 `linkforge_test`**，并用 `@EnabledIfEnvironmentVariable` 使其在无 MySQL 环境自动跳过。
- **选项**：
  1. **Testcontainers**（`@Testcontainers` + `MySQLContainer`）：环境隔离最彻底，但需新增依赖 + 拉取镜像（数百 MB）；
  2. **复用本地 MySQL + 独立 schema**（选中）。

- **结论**：**选项 2 + `@EnabledIfEnvironmentVariable(named = "RUN_MYBATIS_IT", matches = "true")`。**
- **理由（为什么选方案 2）**：
  - **精准命中缺陷性质**：DR-029 的 bug 只在「真实 MyBatis + 真实反射构造器 + 真实 `TIMESTAMP` 列读回」这条路径上暴露，Testcontainers 提供的额外价值（环境隔离）对这个缺陷不是关键项，而**拉镜像的成本是实打实的阻塞**。
  - **时区断言必须真实**：连接串强制数据库会话时区为 UTC（DR-032），只有真实 MySQL 才能验证「存 UTC、读回不被驱动二次换算」这件事。

- **理由（为什么用 `@EnabledIfEnvironmentVariable` 而不是 `@Tag` + surefire 排除）**：
  - **不引额外插件**：用 `@Tag` + `<excludedGroups>` 需要在父 POM 里配置 `maven-surefire-plugin` 的 `excludedGroups`，等于为一个断言机制引入构建配置；而 `@EnabledIfEnvironmentVariable` 是 **JUnit 5 自带**的 `@Disabled` 家族注解，零构建改动。
  - **意图表达更准确**：`@Tag("integration")` 表达的是「这是什么类型」，跳过与否还要另配 POM；`@EnabledIfEnvironmentVariable` 表达的是「没有 MySQL 就别跑」，**条件与意图写在同一处**，读代码即知跳过规则。
  - **粒度更细**：将来若有测试需要「只在这个 profile 下跑」，`@EnabledIfEnvironmentVariable` 可按变量精细控制，而 tag 是全局分组开关。
  - **执行方式**：`.\mvnw.cmd clean install` 默认**跳过**；需要时 `RUN_MYBATIS_IT=true .\mvnw.cmd clean install`。

- **⚠️ 类名必须是 `*Test` 而不是 `*IT`**（写代码时才发现的坑）：
  - surefire 默认只拾取 `**/Test*.java` / `**/*Test.java` / `**/*Tests.java` / `**/*TestCase.java`；`**/*IT.java` 属于 **failsafe 插件**的职责范围。
  - 若命名为 `LinkRepositoryMyBatisIT` 又不引入 failsafe 插件，这个测试会**永远不被执行**——构建照样全绿，但 DR-031 要求的覆盖缺口仍然敞着，等于写了一句空承诺。
  - 因此命名收敛为 `LinkRepositoryMyBatisTest`，由 `@EnabledIfEnvironmentVariable` 单独控制跳过与否：**命名负责「被拾取」，注解负责「何时跳过」**，两件事分开做，缺一不可。

- **测试覆盖范围**（必须包含）：
  1. `insert` 后 `findByShortCode` 能正确回读 —— **DR-029 的直接回归测试**；
  2. `createdAt` 时区正确性：写入前后对比 `Instant`，证明存的是 UTC、未被数据库会话时区二次换算（DR-032）；
  3. `status` 往返：`LinkStatusTypeHandler` 真实读写 `TINYINT`；
  4. **同时插入两条不同 `short_code`，读回后字段不串**（防 `<constructor>` 映射错位）；
  5. **`is_custom` 为 `NULL` 时的行为**：`NOT NULL` 列不会真的存 null，但用 SQL 强制写入 `NULL` 的模拟场景会被列约束拒绝，因此该用例断言的是「DB 层拒绝 null」这一事实（`is_custom` 为 `NOT NULL DEFAULT 0`），而非 Java 侧的 null 处理——因为**该列在数据库层面就不存在 null 这一状态**，Java 侧用基本类型是安全的。

- **隔离要求**：测试库必须是**独立的 `linkforge_test`**，不得触碰开发库 `linkforge`（避免测试数据污染 D5/D6 的验证基线）。建库 SQL 已提供给用户手动执行（`linkforge` 用户可能无 `CREATE DATABASE` 权限）。

- **影响**：第 5 周 CI 需显式设置 `RUN_MYBATIS_IT=true` 并提供 MySQL 服务，否则这批测试会静默跳过——这是**有意设计**（干净环境不因缺依赖而构建失败），但需在 README 中写明。

## DR-032 数据库会话时区强制为 UTC（消除 8 小时双重换算）

- **决策**：连接串**移除 `serverTimezone=Asia/Shanghai`**，改用 **`connectionTimeZone=UTC` + `forceConnectionTimeZoneToSession=true`**。
  ```
  jdbc:mysql://localhost:3307/linkforge?useSSL=false&allowPublicKeyRetrieval=true&connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true&characterEncoding=utf8
  ```
- **结论**：数据库会话时区必须是 **UTC**，由 JDBC 参数在建连时强制生效。
- **理由**：
  1. **`serverTimeZone` 参数在 Connector/J 8.0.23+ 已废弃**，改用现代参数名 `connectionTimeZone`。
  2. **`forceConnectionTimeZoneToSession=true` 是本条的关键**：它让驱动在建连后执行
     `SET time_zone='+00:00'`，**覆盖掉服务器自身时区**。只写 `connectionTimeZone=UTC`
     而不加这个参数，行为取决于服务器与驱动的协商，**不够确定**。
  3. 会话时区为 UTC 后，`DEFAULT CURRENT_TIMESTAMP` 生成的就是 UTC，读回的 `LocalDateTime` 也是 UTC，
     `TimeConverter` 可无条件按 UTC 处理。

- **⚠️ 完整故障链路（D4 启动验证实测）**：

  ```
  1. 连接串：...&serverTimeZone=Asia/Shanghai&...
  2. MySQL 会话时区 = Asia/Shanghai（@@session.time_zone = SYSTEM，随服务器 TZ）
  3. INSERT 不写 created_at（DDL: DEFAULT CURRENT_TIMESTAMP）
     => MySQL 按会话时区生成墙上时钟，库里存的是 2026-10-13 13:15:33（北京时间）
  4. 读回：驱动按 serverTimezone=Asia/Shanghai 解释 TIMESTAMP
     => LocalDateTime 13:15:33（应用以为这是 UTC）
  5. TimeConverter.toOffset(x, +08:00) 当作 UTC 再加一次偏移
     => 2026-10-13T21:15:33+08:00   ← 比真实时刻【晚 8 小时】
  ```

  **关键分歧点**：`created_at`/`updated_at` 是**数据库生成**的，不是应用写入的。
  DR-027 假定的「持久层统一是 UTC」对**应用写入的 `expire_at`** 成立，
  但对**数据库生成的列**不成立——这正是原设计漏掉的分支。
  ⚠️ 由此得出一个反直觉但重要的结论：**驱动侧与数据库侧必须同为一个时区**，
  否则「谁生成的值」不同，换算次数也不同，双重换算只会在其中一条路径上出现。
  本项目的实测恰好印证：`expire_at`（应用写入）在旧配置下**碰巧通过**，
  只有 `created_at`（数据库生成）失败——「一个通过一个失败」是最容易误判为偶发的特征。

- **⚠️ 为什么不能用「在应用层把 `createdAt` 反推成 UTC」来修**：
  那会让时区知识泄漏进领域对象，与 DR-027「转换只在 Service 边界」的意图相反；
  且真正的根因（会话时区不一致）依然存在，D5 接入过期判定后还会再撞一次。
  修正**数据来源的时区**比修正**读取时的解释**更根本。

- **不需要数据迁移**：`TIMESTAMP` 内部存的是 UTC epoch，会话时区只影响显示与 `CURRENT_TIMESTAMP` 的生成，
  改会话时区**不改变已有行的内部值**。旧的 `created_at` 在新会话下读回即是正确的 UTC。

- **⚠️ 触发位置（改动一致性清单，共 4 处，与 DR-023 的 `allowPublicKeyRetrieval` 同级）**：
  1. `.env`（本地，未跟踪）
  2. `.env.example`（含「为什么不用 `serverTimezone`」的注释）
  3. **`linkforge-app/src/test/resources/application-test.yml`** —— ⚠️ 测试连接串**必须与生产逐字符一致**，
     否则「createdAt 时区断言」会因配置不同而失去意义（DR-031）
  4. **`docker-compose.yml` 的应用服务（第 5 周添加，容器内 URL 用 `mysql:3306`）** —— ⚠️ 已加占位注释。
     这类「漏改一个环境」的缺陷最难排查，本项目已踩过一次。

- **回归防护**：由 DR-031 的 `createdAt_shouldNotBeShiftedByServerTimezone` 与
  `expireAt_shouldRoundTripWithoutInstantShift` 两条用例锁住。改动连接串时区参数前，
  先跑 `RUN_MYBATIS_IT=true .\mvnw.cmd clean install`——它们是这条决策唯一的自动化守卫。

## DR-033 含特殊字符的配置文件改写**禁止用 sed**

- **决策**：改写 `.env` / `application*.yml` / `docker-compose.yml` 等**含特殊字符的配置文件**时，
  **禁止使用 `sed`**，改用 **Python** 或 **PowerShell** 精确重写。
- **选项**：
  1. 继续用 `sed`（最省事）；
  2. **改用 Python / PowerShell 逐行精确处理**（选中）；
  3. 手工编辑（不可靠，无法进 Git 历史）。

- **结论**：**选项 2。**

- **背景（D4 实测踩坑）**：修 DR-032 的连接串时用 `sed -i "s|$OLD|$NEW|"`，
  把 JDBC URL 里的 **`&`** 当成了「整个匹配」的通配符，导致该行被撑成
  `...useSSL=falsejdbc:mysql://...characterEncoding=utf8allowPublicKeyRetrieval=truejdbc:...`
  这样一长串重复内容。
  ⚠️ **最危险的地方是它不报错**：退出码 0、有输出、看起来成功，
  静默损坏了一个含数据库连接配置的文件。发现时已晚了一步。

- **原因**：在 `s` 替换语法里，`&` 是「整个匹配」的转义；反向引用是 `\1`~`\9`。
  换言之**任何含 `&` 的替换文本都会被重新展开**。

- **触发场景（凡是替换文本可能含以下字符时，一律不用 sed）**：

  | 字符 | 场景 | sed 的坑 |
  |---|---|---|
  | **`&`** | **JDBC URL 的参数分隔符**（`?a=1&b=2`） | 本次踩坑点，撑坏整行 |
  | **`\|`** | Windows 路径分隔符 | 作为分隔符时冲突，需转义 |
  | `\` | Windows 路径、正则转义 | 与替换转义语法混用 |
  | `?` | 正则量词 | 在 `s` 左值中会被当量词 |
  | 换行 | 多行文件 | `sed` 不支持跨行替换 |

- **正确做法（本次实际用的）**：
  ```python
  # 逐行处理，只对命中的前缀行整体重写，绝不把行内容当替换模板
  for path in [".env", ".env.example"]:
      lines = open(path, encoding="utf-8").readlines()
      fixed = ["SPRING_DATASOURCE_URL=" + NEW_URL + "\n"
               if ln.startswith("SPRING_DATASOURCE_URL=") else ln
               for ln in lines]
      open(path, "w", encoding="utf-8", newline="").writelines(fixed)
  ```
  关键点：**新值是「赋值」而不是「替换」**——完全绕开了替换语法，因此不可能被展开。
  `sed -i "s|$OLD|$NEW|"` 则相反，是「替换」。

- **代价与影响**：
  - 比 `sed` 啰嗦（要多写几行），换来的是**不会静默损坏**；
  - ⚠️ 这条规则不只关于「用哪个工具」，更关于**改配置后必须核验**：
    本次靠「立刻 `grep` 校验整行内容」才发现损坏。**任何配置改写后都要回读确认**，
    这是比工具选择更重要的纪律。

- **影响**：D5 及之后涉及 `.env` / `application*.yml` / `docker-compose.yml` 的改动一律适用。

## DR-034 数据库权限边界：本地可自建库，生产应用账户只给 DML

- **决策**：数据库账户按环境分权，**本地开发**与**生产/CI**用不同权限模型。

- **选项**：
  1. 所有环境统一：应用账户持 `ALL PRIVILEGES`；
  2. 所有环境统一：应用账户只给 DML，本地建库靠人工；
  3. **按环境分权**（选中）：本地给建库权限以便自动化，生产严格最小权限。

- **结论**：**选项 3。**

- **权限模型**：

  | 环境 | 应用账户权限 | DDL 执行者 |
  |---|---|---|
  | **本地开发** | `linkforge`：业务库 DML + **`CREATE`/`DROP` 全局** + `linkforge_test.*` 的 `ALL` | 应用同账户（Flyway 迁移 + 集成测试建库） |
  | **生产 / CI** | 应用账户**只有 DML**：`SELECT` / `INSERT` / `UPDATE` / `DELETE` | **Flyway 独立账户**（持有 DDL，应用账户无 DDL 权限） |

- **理由（为什么生产不给 DDL）**：
  1. **最小必要原则**：应用运行期不需要 `CREATE` / `ALTER` / `DROP`。给了就是**攻击面的扩大**——
     一旦应用被拿到 SQL 注入或 RCE，攻击者能用 DDL 直接破坏表结构，而不只是读写数据。
  2. **DML 与 DDL 分离才能审计**：迁移是低频、需要评审的操作；应用运行是高频操作。
     把两者放在同一账户下，会让「谁改了表结构」这个问题失去答案。
  3. **Flyway 独立账户不是过度设计**：它让「谁能改 schema」变成一个**可配置的部署参数**，
     而不是「跑应用的人手里恰好有什么权限」。

- **本地为什么允许建库**（D4 实操背景）：
  DR-031 的集成测试需要独立库 `linkforge_test`。实测发现 `linkforge` 用户**默认无 `CREATE` 权限**：

  ```
  mysql: [ERROR] 1044 (42000): Access denied for user 'linkforge'@'%' to database 'linkforge_test'
  ```

  若不给权限，每次新建环境都要人工切 root 建库，**违背 PRD A-1「干净环境一条命令起」**。
  本地因此放宽到可以让 `linkforge` 自建测试库。
  ⚠️ **但这只在本地做**，生产绝不照搬——本地是单人开发环境，生产是多人协作且暴露在网络下。

- **本地补权限的命令**（⚠️ **仅本地手工执行一次**，禁止写进 Flyway 迁移脚本或生产文档）：

  ```sql
  -- ⚠️ 本地开发环境专用。生产禁止执行（应用账户不应有 CREATE/DROP）。
  GRANT CREATE, DROP ON *.* TO 'linkforge'@'%';
  GRANT ALL PRIVILEGES ON linkforge_test.* TO 'linkforge'@'%';
  FLUSH PRIVILEGES;
  ```

- **⚠️ 为什么这两条 SQL 不能进迁移脚本**：
  1. `GRANT` 是**管理语句**，Flyway 迁移是**schema 版本化**机制，两者职责不同；
  2. 迁移脚本会**在评审者的干净环境里执行**，往里塞提权语句等于把本地便利强加给所有人；
  3. `GRANT` 需要 `GRANT OPTION` 或管理员权限，**迁移账户往往没有**，
     写进去会让迁移在权限不足的环境直接失败；
  4. 权限是**环境配置**，不是**schema 结构**——schema 会变，权限不该跟着版本走。

- **⚠️ 已知偏差（留档）**：D4 实际执行时，先用 `linkforge` 试 `CREATE DATABASE` 失败（1044），
  随后用 `.env` 里的 **root 凭据**建了 `linkforge_test` 并 `GRANT` 给 `linkforge`。
  这与本决策「本地用 `linkforge` 自建」的意图不完全一致。
  **保留偏差的原因**：`.env` 里存在 `MYSQL_ROOT_PASSWORD` 本身就是个应当收紧的点——
  本地开发机上放着 root 口令，风险不为零。DR-035 已将其记入待收紧清单。
  若日后收紧 root 凭据，应改用上面的 `GRANT CREATE, DROP` 让 `linkforge` 自建库。

- **影响**：D5 及之后不涉及权限变更；第 5 周 CI 落地时需按「生产/CI」一栏准备两个账户
  （应用账户 + Flyway 账户），并把该配置写进 README 的部署说明。

## DR-035 `.env` 中的 root 凭据是待收紧项（v1 保留，v2 移除）

- **决策**：**v1 保留现状不动**（`.env` 继续持有 `MYSQL_ROOT_PASSWORD`），
  但明确记为**待收紧项**，在 v2 或第 5 周部署收口时处理。
- **结论**：**现在不改**，但写进决策记录，避免「它一直都在」被当成「它没问题」。
- **理由**：
  1. `.env` 已被 `.gitignore` 覆盖、**不会进仓库**（DR-001 / PROJECT_BRIEF §12.7），
     凭据不外泄。单机本地开发环境下风险有限。
  2. 本地需要它来初始化容器（`docker-compose.yml` 的 `MYSQL_ROOT_PASSWORD` 必填），
     移除的收益不足以抵消「立刻改不动本地环境」的代价。
  3. 但它确实是**权限模型上的一个例外**：DR-034 已确立「应用账户不持 DDL」，
     而 root 凭据一旦在手，实际情况等价于「任何进程都能提权到 DDL」。

- **⚠️ 风险具体是什么**（不是泛泛而谈）：
  - `.env` 里的 root 口令可以被**任何能读该文件进程的代码**拿到——
    包括本项目自己的构建脚本、测试、乃至未来引入的第三方插件；
  - 「应用只需要 DML」这条边界在**代码层被证明，在凭据层被绕过**：
    一段误引入的脚本用 `.env` 的 root 连上去，权限模型就形同虚设。

- **收紧方案（v2 或第 5 周执行，届时择一）**：
  1. **初始化后轮换 root 口令**，把真实值移出 `.env`（本地口令管理器 / 手工记忆）；
  2. **删除 `.env` 中的 `MYSQL_ROOT_PASSWORD`**，容器初始化改用随机值并由 `.env.example` 占位；
  3. 应用账户改为只持有 `linkforge.*` 与 `linkforge_test.*` 的权限，
     DDL 全部交给 Flyway 专用账户（DR-034 的「生产/CI」一栏）。

- **验证方式（收紧后如何确认真的收紧）**：
  ```sql
  -- 应当被拒绝：若成功，说明 root 凭据仍在生效
  REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'linkforge'@'%';
  -- 应用账户的最终权限面（应只有业务库与测试库，无全局 CREATE/DROP）
  SHOW GRANTS FOR 'linkforge'@'%';
  ```

  出现了就说明 DR-034 的边界没落实。

- **影响**：无 v1 代码改动。README 的「安全说明」小节应引用本条，

## DR-036 D5 不引入跳转缓存，且**不预建缓存接口**

> ⚠️ **本条已被后续决策部分推翻**（第 6 周收尾核对）：
> `RedirectCacheService` 接口**最终是建了**（第 2 周的 `RedisRedirectCache` 需要它，
> 见 DR-045 / DR-060）。本条记录的是**第 1 周的判断**——
> 「不预建抽象」这个原则**当时是对的**，只是后来需求确定了，抽象也就该建。
> 保留原文是为了留档**判断是如何随信息增加而变化的**，不做历史涂改。

- **决策**：D5 的跳转每次直查 MySQL；`RedirectService` 直接依赖 `LinkRepository`，
  **不定义** `RedirectCacheService` 之类的抽象接口。
- **5 个决策点**（D5 方案确认，全部采纳推荐值）：
  1. 不带缓存（保留第 1 周性能基线分母）；
  2. `LinkState` 放 `core`（查询接口必须给出一致状态码，规则只有一份才可能一致）；
  3. 长度不符 404 / 非法字符与尾斜杠 400（API.md §4.1），字符检查先于长度检查；
  4. 不做限流（第 3 周）；
  5. `LinkController` 与 `RedirectController` 独立。
- **理由（缓存接口延后）**：**为猜不准的需求提前建抽象往往要返工**。
  缓存的形态在第 2 周才定（本地缓存 `maximumSize` / `expireAfterWrite` 的回填、
  空值 TTL、降级路径都未定），此时抽出来的接口签名会跟着需求反复改，
  改的成本高于「等需求确定后再抽一次」。KISS：现在只需要「查库 → 跳转」。
- **第 2 周的改法**：新增 `RedisRedirectCache` 时改 `RedirectService` 的一处依赖即可，
  属**局部改动而非架构改动**——DTO、用例编排、Controller 与错误码映射均不动。
- **影响**：无回滚风险。性能基线（D7 压测）测到的就是纯 DB 路径的 P99，
  这正是 PRD A-3 要求的分母。

## DR-037 路径短码的「字符 400 / 长度 404」与判定顺序

- **决策**：`GET /{code}` 的格式校验分两步，且**字符检查必须先于长度检查**。
  - 尾斜杠、含非 Base62 字符 → **400 `LINKFORGE-400-01`**；
  - 字符合法但长度不是 7 → **404 `LINKFORGE-404-01`**。
- **理由**：
  1. **字符非法是「请求格式错误」**，调用方能立刻发现自己的拼接 bug；返回 400 才能暴露这一点。
  2. **长度不符不是「参数非法」，而是「一定查不到」** —— 7 位空间里不可能存在 3 位或 12 位的短码，
     让调用方去排查「我的短码为什么不合法」是误导。
  3. **顺序不可换**：`abc_` 是 4 位且含非法字符。若先判长度会返回 404，
     调用方会反复重试同一个拼接 bug 的请求，永远等不到想要的结果。
- **⚠️ 已知边界（契约既定行为，非遗漏）**：自定义短码允许 4~8 位（API.md §5.2），
  但跳转接口按默认长度 7 定位，因此 **4~8 位但非 7 位的自定义短码会被判 404**。
  该行为在 `LinkValidator.validateForRedirect` 的 Javadoc 中显式标注，
  等契约改写前不擅自放宽。
- **实现要点**：Spring 6 默认**不匹配尾斜杠**（`setMatchOptionalTrailingSeparator(false)`），
  `/{code}/` 不会落到 `GET /{code}` 上，而是变成「找不到处理器」的 404（body 不是统一错误体，等于契约违规）。
  因此 `RedirectController` **显式注册 `/{code}/`** 并抛 400，保证契约写明的行为真的发生。
- **影响**：规则收在 `core` 的 `ShortCodeFormat`（纯格式判定，不抛异常），
  错误码映射在 `LinkValidator`，`RedirectController` 对尾斜杠直接拒绝且不查库。

## DR-038 GC 日志统一用 `-Xlog:gc*`，`-XX:+PrintGCDetails` 仅作历史记录

- **决策**：性能基线与调优阶段的 GC 日志**统一用 `-Xlog:gc*` 输出**（JDK 9+ 的正式方案）；
  `-XX:+PrintGCDetails` 虽在 `JAVA_OPTS` 中保留，但**仅作历史记录**，不作为分析依据。
- **理由**：
  1. `-XX:+PrintGCDetails` 在 **JDK 9 起已废弃**，JDK 17 启动时会打印
     `PrintGCDetails is deprecated. Will use -Xlog:gc* instead.`。
     保留一个「被 JDK 明确告知已废弃」的参数，会让读日志的人误以为它在生效。
  2. `-Xlog:gc*` 可指定输出目标与装饰器（`file=/dev/stdout:time,uptime,level,tags`），
     能把 GC 日志直接送进容器日志，`docker compose logs app` 即可取到；
     旧参数只能写文件，容器里还得额外挂卷捞。
  3. **保留旧参数是为了口径不漂移**：D6 决策 Q2 原文写的是 `-XX:+PrintGCDetails`。
     若基线阶段就悄悄换成新参数，第 5 周回看基线报告时无法判断 GC 差异来自参数变更还是来自代码。
     因此**基线阶段的 `JAVA_OPTS` 与决策原文保持一致**，同时**追加** `-Xlog:gc*` 让日志真的落到日志流。
- **⚠️ 何时可以删掉 `-XX:+PrintGCDetails`**：第 5 周做调优对比时，
  应在报告里显式声明「基线含废弃参数、结果不含」，且两边的 GC 日志均取自 `-Xlog:gc*`，
  之后再移除。**提前移除会让基线与结果不可比**。
- **影响**：`Dockerfile` 的 `JAVA_OPTS` 与 `docker-compose.yml` 的 `JAVA_OPTS` 同步携带两者；
  分析 GC 行为时只读 `-Xlog:gc*` 的行，忽略 `PrintGCDetails` 的 deprecation warning。

## DR-039 成功响应统一套 `data` 外壳，失败响应不套

- **决策**：创建接口的成功响应改为 API.md §3.3 定义的
  `{"data": {...}, "timestamp": "..."}`；**失败响应保持** `{code, message, timestamp, details?}` **不套外壳**。
- **理由**：
  1. **契约以 API.md 为准**：§3.3 与 §5.3 都写明成功响应有 `data` 层，
     而实现此前返回扁平结构——是实现偏离契约，不是契约写错。
  2. **失败不套外壳是 API.md 的原文约定**，不是遗漏。失败时没有业务数据，
     硬套一个 `data: null` 只会让调用方多写一层判空。
  3. **外壳与 DTO 分离**：`ApiResponse<T>` 是协议，`CreateLinkResponse` 是业务。
     第 4 周查询接口、第 3 周 admin 接口只需换 DTO，外壳复用同一份。
- **实现要点**：`timestamp` 在**外壳**上而非 `data` 里——它标记「响应生成时间」而非业务字段，
  放进 data 会让各接口的 data 内容不一致。
- **影响**：新增 `redirect/api/dto/ApiResponse`；`LinkController` 构造签名增加 `ZoneId`；
  `LinkControllerTest` 的 jsonPath 断言从 `$.xxx` 改为 `$.data.xxx`，
  并新增「顶层只有 data 与 timestamp」的结构测试。

## DR-040 `short_code` 列使用 `ascii_bin` 排序规则

- **背景**：V1 建表时 `short_code` 继承了表默认的 `utf8mb4_0900_ai_ci`（`_ci` = case-insensitive），
  但短码空间是 Base62（`0-9A-Za-z`），**同时使用大小写字母**。
  于是 `0Q1A`（序号 100016）与 `0Q1a`（序号 100042）在 ci 比较下是同一个值，
  `uk_short_code` 判定冲突，发号器重试 3 次后返回 503（`LINKFORGE-503-01`）。
- **实测**（2026-10-15D6 造数）：序号区间 100000~100065 共 66 个短码，
  ci 去重后仅 42 个，**24 组冲突（约 36%）**。这不是边缘情况而是常态——
  只要序号递增跨过大小写字母边界就必然踩到。
  D4/D5 只造个位数短码，因此从未暴露。
- **根因**：契约要求与 schema 不一致。API.md §5.2 明写「短码大小写敏感，
  `Abc123` 与 `abc123` 是两个不同短码」，DR-025 也以此为前提；
  但建表时用了库默认排序规则，没人核对过它是否满足契约。
- **决策**：Flyway V3 把 `short_code` 改为 `CHARACTER SET ascii COLLATE ascii_bin`。
- **为什么不选 `utf8mb4_0900_as_cs`**：它的大小写敏感语义是对的，但按 utf8mb4 存
  **4 字节/字符**，对纯 ASCII 的短码是 4 倍浪费。
  `ascii_bin` 是 1 字节/字符 + 二进制比较，语义精确且存储最优——
  短码不该有任何 Unicode 语义（不区分重音、不做等价归一）。
- **实测收益**：`idx_status_code(status, short_code)` 覆盖索引中，
  `short_code` 从 32 字节/行降到 8 字节/行（`EXPLAIN` 的 `key_len` 从 34 变 10）。
- **回归测试**（`LinkRepositoryMyBatisTest`）：
  - `shortCodesDifferingOnlyByCaseAreDistinct` —— `0Q1A` / `0Q1a` 双双插入并各查回自己的 `targetUrl`
  - `identicalShortCode_shouldStillBeRejected` —— 完全相同的码仍被唯一索引拒绝（防修复过头）
  - `shortCodeLookup_shouldUseUniqueIndex` —— `EXPLAIN` 断言 `type=const` + `key=uk_short_code` + `rows=1`

## DR-041 `referer_domain` 保持 `utf8mb4_0900_ai_ci`（不改成大小写敏感）

- **背景**：D6 检查所有列的排序规则时，我（提出检查的人）曾按「唯一键组成部分应从严」
  的直觉提出把 `link_stats_daily.referer_domain` 也改成大小写敏感。**该判断经论证后推翻。**
- **理由**：
  1. **DNS 规范本身大小写不敏感**——`EXAMPLE.COM` 与 `example.com` 是同一个域名，
     这是协议规定的事实，不是数据库的选择。
  2. **统计表的语义是聚合**。`uk_link_date_referer(link_id, stat_date, referer_domain)`
     的目的是「同一天、同一短链、同一个来源站点」。
     ci 让等价域名**合并**（正确归一）；改成敏感会让它们**分裂成两个来源**，
     导致同一来源的 PV 被错误拆分——这是数据质量问题，不是安全问题。
  3. **危害方向相反**。「唯一键从严」的直觉适合的是**需要精确区分**的字段
     （如用户名），而域名是需要**归一**的字段。
- **决策**：保持 `utf8mb4_0900_ai_ci` 不变。
- **⚠️ 记录目的**：防止后续读者按「唯一键从严」的直觉把它改回去。
  这类「看起来更严格、实际更错误」的改动，光看代码审不出来——
  必须回到字段的业务语义上判断。
- **同理**：`short_link.target_url` 也保持 `utf8mb4_0900_ai_ci`。
  它存用户提交的原始 URL，**可能含中文路径与查询参数**，
  改成 ascii_bin 会让含中文的 URL 直接插入失败。

## DR-042 号段发号：Mapper 返回受影响行数，不返回 `max_id`

- **决策**：`IdSegmentMapper` 拆成两条语句——
  `advanceMaxId()` 返回**受影响行数**（`int`），
  `advanceAndGetNewMaxId()` 在**同一 `REQUIRES_NEW` 事务**内先 update 再
  `selectMaxId`，返回真正的 `max_id`。
- **根因**：原实现把 `advanceAndGetMaxId` 声明成返回 `long`，但 MyBatis 的
  `<update>` **一律返回受影响行数**（该语句恒为 1），不是 `max_id`。
  于是号段右端点被算成 1，段首变成 `1 - 1000 + 1 = -998`（负序号），
  抛 `IllegalArgumentException: 序号不能为负`，最终变成 **500**。
- **⚠️ 为什么能长期潜伏**（本条最重要的教训）：
  两重遮蔽叠加——① `SegmentShortCodeGeneratorTest` 把 `IdSegmentAllocator` mock 掉了，
  mock 返回的是真 `max_id`，8 个单元测试全绿；
  ② 该路径只在 **Redis 不可用时的降级分支**上执行，
  而 D4/D5 的启动验证都是低并发，Redis 路径从未失败过。
  **「测试全绿」与「路径从未被执行」是同时成立的。**
- **为什么不合成一条 SQL**：MySQL 没有 `UPDATE ... RETURNING`，
  常见技巧是 `SET max_id = LAST_INSERT_ID(max_id + step)` 再 `SELECT LAST_INSERT_ID()`。
  但它依赖 MySQL 特有行为，且读的是**连接级**变量——
  从连接池拿到的连接若不是同一条，结果就是错的。
  降级发号是低频路径，多一条 SELECT 的开销可忽略，通用性与可读性更重要。
- **为什么必须 `REQUIRES_NEW`**：取号段要独立于业务事务。
  号段一旦取走，无论业务成功失败都**不还回去**（只跳号、不重号）；
  若与业务事务共用，创建失败回滚时号段也回滚，
  而进程内 `current` 已向前走，同一段号会被重复发出。
- **防御性断言**：`refillSegment` 新增「段首不得小于 `SEGMENT_FIRST_SEQUENCE`」检查。
  DR-042 正是绕过了这一步才让负序号漏到业务层——
  补上之后同类错误会在发号器内部被拦住。
- **回归测试**（`SegmentShortCodeGeneratorMysqlTest`，9 个）：
  **刻意不 mock 任何一层**，也**刻意不加类级 `@Transactional`**
  （那会让测试事务持有 `id_segment` 行锁，与 `REQUIRES_NEW` 自锁，
  每个用例卡 50s `Lock wait timeout`——生产无此问题）。
  覆盖：100 个号全正无重复、序号落在 `[10亿, +∞)` 不与 Redis 区间重叠、
  100 个号只推进 1 段、跨段 2500 个号无重号、
  区间用尽/段首为负/行不存在三种异常都抛 `ShortCodeGenerationException`、
  以及直接断言 Mapper 的 `advanceMaxId` 返回 1 而非 `max_id`（锁定根因）。

## DR-043 号段发号失败映射 503 而非 500

- **决策**：
  1. `SegmentShortCodeGenerator` 内部所有异常（负数、越界、SQL 异常）统一包装为
     `ShortCodeGenerationException`；
  2. `GlobalExceptionHandler` 为它单独注册 handler → **503 `LINKFORGE-503-01`**。
- **理由**：500 与 503 语义不同，处置方式也不同——
  500 = 「服务有 bug，需要人介入」；503 = 「依赖暂时不可用，调用方可以重试且会自愈」。
  号段发号失败通常是数据库暂时不可达，把它报成 500 会**误导告警与排查方向**
  （让人去查代码，而实际问题在依赖）。
  D6 实测正是这样：负序号异常漏到兜底 handler，409 个请求返回 500，
  而真正的根因（Mapper 返回值错误）在数据库侧。
- **⚠️ 这类异常泄漏的通用教训**：基础设施层的异常若不显式映射，
  就会被兜底 handler 一律报成 500，把「依赖问题」伪装成「代码问题」，
  浪费排查时间。新增基础设施异常类型时，**必须同时确认它有明确的 HTTP 语义映射**。
- **实现要点**：兜底 handler 只应在「确实没有更精确的映射」时兜底，
  它不是「所有异常都该进这里」的许可。

## DR-044 未匹配路由映射 404（NoResourceFoundException）

- **背景**：D6 收尾时发现 `GET /` 返回 **500 + LINKFORGE-500-01**，而按 API.md 应为 404。
- **根因**：Spring 6.1起静态资源处理器在路径无匹配时抛
  `org.springframework.web.servlet.resource.NoResourceFoundException`
  （取代已废弃的 `NoHandlerFoundException`）。本项目没引actuator、也没有静态资源目录，
  该异常直接落到 `GlobalExceptionHandler` 的兜底 handler，被报成 500。
- **决策**：`GlobalExceptionHandler` 新增
  `@ExceptionHandler(NoResourceFoundException.class)` → **404 `LINKFORGE-404-01`**，
  与短码查询路径的「短码不存在」用同一个错误码。
  日志级别 **WARN 且不打堆栈**（404 是正常业务语义，不是故障）。
- **理由**：
  1. 500 的语义是「服务有 bug，需要人介入」。用户敲错一个地址就把服务标成故障，
     会污染告警与可用性指标；
  2. 与短码查询共用404-01，调用方只需判断「404 = 没有可跳转的东西」，
     不必区分是路径写错还是短码不存在；
  3. 不处理的话Spring 会走 `/error` 分发再进兜底，结果一样是 500 + 一次多余转发。
- **实测代价**：该缺陷在 D6 压测间隙的 2 分钟内产生了 **122042 条 ERROR 级日志**
  （每次请求约 50 行堆栈，共 610 万行），把真正的错误日志彻底淹没——
  这是「基础设施/框架异常必须显式映射」的又一个实例（与 DR-043 同源）。
- **回归测试**：`NoResourceFoundHandlerTest`（4 个）
  - `unmappedPathReturns404Not500`
  - `usesSameErrorCodeAsShortCodeLookup`
  - `doesNotLeakInternals`
  - `doesNotWrapFailureInDataEnvelope`
- **⚠️ 测试写法说明**：用 `standaloneSetup` +显式 `setControllerAdvice`，
  而不是 `@WebMvcTest`。原因是本测试要验证的是**handler 对该异常类型的映射**，
  而 `@WebMvcTest` 下未匹配路径抛哪种异常会随上下文装配变化
  （限定 `@ContextConfiguration` 时不加载静态资源处理器，异常类型会变），
  那测的是框架装配细节而非本项目的映射逻辑。

## DR-045 跳转缓存：两级结构与关键参数

- **结构**：Caffeine（本地，第 1 层）→ Redis（第 2 层）→ MySQL 回源（Cache Aside）。
  编排集中在 `TwoLevelRedirectCache`，调用方不感知层级。
- **Redis key**：`shortlink:code:{shortCode}`（ARCHITECTURE.md §206 已定义）。
  空值缓存**复用同一个 key**，用哨兵值 `__EMPTY__` 区分——分前缀会让失效路径需要删两处。
- **序列化**：自定义长度前缀格式 `v1|status|expireAt|len|targetUrl`。
  ⚠️ `targetUrl` 放最后且带长度前缀：它是用户输入，`LinkValidator` 不排除换行与分隔符，
  用 `\n` 或 `|` 直接拼接会让字段串位。解析失败一律按「未命中」处理并删掉坏数据，
  最坏是多查一次库，**绝不返回错误数据**。不用 Jackson：需额外配 JavaTimeModule，
  跨版本格式漂移会在滚动发布期间造成新旧实例写两种格式。
- **TTL**：正常值 1 小时 + 随机 0~5 分钟抖动；空值 30 秒不加抖动。
- **Redis 故障一律降级为未命中**，不向上抛。缓存是加速器不是依赖——
  这与发号器路径不同（那里 Redis 是工作前提，故障必须暴露）。

## DR-046 本地缓存 expireAfterWrite = 5 分钟

- **推导（业务决定，不由 Redis TTL 倒推）**：
  本地缓存**无法精确失效**——多实例部署时每个实例各有一份，
  一个实例删了 Redis key，其它实例的本地缓存毫不知情。
  因此**最大不一致窗口 = Caffeine 的 TTL**，这个数字由业务能接受多久的
  「删除短链后仍可跳转」决定。业务确认可接受 **5 分钟**，故定为 5 分钟。
- ⚠️ **刻意不写「≤ Redis TTL 的 1/12」**：5 分钟恰好也接近 1h/12，但那是巧合。
  若哪天 Redis TTL 改成 30 分钟，**不应该**跟着把本地缓存改成 2.5 分钟——
  业务窗口不变，本地 TTL 就不该变。
- **已知限制（记录但不解决）**：多实例下删除操作最长 5 分钟才在所有实例生效。
  **第 3 周先量出删除操作的实际频率**，再决定是否引入「版本号 + 失效广播」。
  现在上复杂机制是为不存在的问题付复杂度成本。
- **maximumSize = 10000 是数据量依赖，不是通用常数**：由第 1 周实测的 1 万条压测语料决定。
  生产环境应按「活跃短码数 × 0.1~0.3」重新评估——短链访问是长尾分布，
  少数码贡献绝大多数流量，全量缓存是浪费。换数据量时这个值必须一起改。

## DR-047 本地缓存只缓存 Hit，绝不缓存 NegativeHit

- **决策**：Caffeine 的 value 类型定为 `CacheEntry.Hit` 而非 `CacheEntry`，
  **用类型在编译期挡住 NegativeHit**，而不是靠运行时 `if` 判断。
- **理由**：空值 TTL 只有 30 秒，本地 TTL 是 5 分钟。若把「不存在」也缓存到本地，
  一个**刚被创建**的短码会持续 404 长达 5 分钟——缓存了一个比它本身存在时间还长的错误结论。
  这个坑隐蔽（代码看起来完全正常，测试也可能全绿），必须留档防止后人「优化」掉。

## DR-048 缓存异常处理的两条不变量

- **回源异常绝不进缓存**：数据库超时/连接失败必须向上抛（→ 503），
  绝不能当成「不存在」缓存——那会把一次数据库抖动固化成 30 秒的 404 风暴，比不做缓存更糟。
  回归测试 `repositoryFailureIsNeverCached`。
- **缓存命中也必须走状态判定**：`CachedLink` 携带 `status` 与 `expireAt`，
  命中后仍走与第 1 周完全相同的判定顺序（DELETED 先于 EXPIRED）。
  若命中就直接返回 302，「先跳转后删除」的链接在最长 5 分钟内仍会跳到目标，
  违反 DELETE 语义（API.md §7.1）。回归测试 `cachedDeletedStillReturns404` /
  `cachedExpiredStillReturns410`。
- **evict 顺序不可调换**：先删本地、再删 Redis。反过来会出现
  「删 Redis 后、删本地前」的窗口，并发读回查到旧值并重新写入本地，
  让已失效的值在本地又活一个 TTL 周期。

## DR-049 异常日志必须去重或限流

- **背景**：D6 压测间隙的 2 分钟内，`GET /` 未匹配路由产生 **122042 条 ERROR 级日志**
  （每次请求约 50 行堆栈，共 610 万行），把真正的错误信号彻底淹没。
- **决策**：业务异常一律**记 WARN 且不打堆栈**（4xx 是调用方问题）；
  只有 5xx 才带栈。404 属于正常业务语义，连 ERROR 都不该是。
- **通用规则**：任何会被高频触达的异常路径，日志必须**去重或限流**
  （按短码采样、按时间窗聚合），否则单点异常就能淹没整个错误日志。
  这与 DR-043（基础设施异常必须显式映射）、DR-044（404 不是 500）是同一条主线的三个实例。

## DR-050 targetUrl 显式拒绝 C0 控制字符（U+0000~U+001F）

- **背景**：第 2 周做缓存序列化时发现缺陷——`targetUrl` 用 `\n` 分隔存储会串位。
  改用长度前缀格式后回头追查，发现**更根本的问题**：`LinkValidator`
  只校验协议与长度，从未显式排除控制字符。
- **⚠️ 实测结论（重要，不要误读为「堵上了安全漏洞」）**：
  JDK 17 的 `java.net.URI` 对 `\n \r \t \0` 及其它 C0 控制字符**一律抛
  `URISyntaxException`**（已在容器内实测：`\n`、`\r`、`\t`、`\u0000`、`\u0007` 全部 FAIL）。
  **也就是说这个输入当前并没有真的漏过去**，它被 JDK 兜住了。
  本次修复的实质是：**把「碰巧被第三方实现兜住的事」变成「我们自己的契约」**。
- **决策**：`LinkValidator.validateTargetUrl` 在**协议白名单之前**
  显式扫描 C0 控制字符，命中即抛 `LINKFORGE-400-01`，消息含具体码位（如 `U+000A`）。
- **为什么不依赖 URI 解析兜底**：
  1. **JDK 行为可能变化**——不同版本、不同 URI 实现的严格程度不同，
     把正确性押在第三方实现细节上是不可持续的依赖；
  2. **存在绕过 URI 解析的路径**——当前顺序是「协议白名单（纯字符串 `startsWith`）
     → URI 解析」，而缓存序列化、统计落库等路径可能不经 URI 解析；
  3. **错误码不对**——靠 `URISyntaxException` 兜住时消息是「targetUrl 不是合法 URI」，
     调用方无法区分「有个控制字符」与「URI 结构写错了」。
- **⚠️ 刻意不拦截的两类输入**：
  - **百分号编码**（`%0A`、`%09`）：这是**合法 URL**，符合 RFC 3986 的
    percent-encoding 规则，在 HTTP 传输层安全（不会真的产生 header 注入）。
    过度拦截合法 URL 比放过一个编码形式更有害。
    回归测试 `encodedFormsAreAllowed` 锁住这个决定，防止后人写成「任何不可见字符都拒绝」。
  - **U+007F（DEL）**：不在 C0 段内。实测 `new URI()` 也会拒它，
    但那是 URI 解析的既有行为，与本检查无关。若要扩展，改的是 `findControlChar` 的边界。
    回归测试 `delIsNotBlockedByControlCharCheck` **断言的是「不是被控制字符检查拦下的」**
    而不是「整体通过校验」——这个区别必须写清楚，否则会被误读为漏网之鱼。
- **回归测试**：`LinkValidatorTest.ControlChars`（12 个）
  - `c0ControlCharsRejected`（参数化 7 个码位）
  - `messageIdentifiesTheCharacter`
  - `encodedFormsAreAllowed`（参数化 2 个）
  - `delIsNotBlockedByControlCharCheck`
  - `checkedBeforeProtocolCheck`（含控制字符的 `javascript:` 必须返回 400-01 而非 400-02）

## DR-051 两级缓存必须是三段式（L1 优先），「为正确性付代价」的说法要警惕

### 背景

第 3 周给 `getOrLoad` 写单飞时，我把顺序实现成了**「先问 L2（Redis），再查 L1（Caffeine），最后回源」**，并在注释里论证这是「为正确性付的代价」——理由是 `caffeine.get(key, loader)` 只在 L1 miss 时执行 loader，不给「先问 L2 再决定要不要 loader」的机会。

压测实测 QPS 从第2 周的 **81289掉到 3153**，`shortlink.cache.local.hit`恒为 0。

### 结论：那不是取舍，是缺陷

> ⚠️ **顺序已演进**：本条定的「L1 → L2 → 回源」在DR-052 之后更新为
> **「L1 → (布隆 + L2 合并) → 回源」**——布隆插在 L2 那一段，
> 与 ARCHITECTURE §158「判断顺序必须是布隆 → 缓存 → DB」一致。
> 往返数不变（L1 命中 0 次、L1 miss 1 次），但那 1 次里多了布隆检查。

| | 三段式（L1 优先） | 两段式（L2 优先） |
|---|---|---|
| L1 命中时的 Redis 往返 | **0次** | 1 次 |
| 正确性 | 一样 | 一样 |
| 回源次数与实例数无关 | ✅ 一样成立 | ✅ 一样成立 |

**三段式没有牺牲任何正确性。** 我在注释里写的「两次 L1 查找之间存在竞态」是伪问题：
`getIfPresent` 只读不写，第二次 `get(key, loader)` 的加载不依赖第一次的结果，两者不冲突。

真正被绕过的性质是「L1 命中这一分支根本走不到」——每次请求都先问 Redis，
本地缓存形同虚设，8 万 QPS 下 Redis 直接成为瓶颈。

### 教训：「为正确性付代价」这个说法本身要警惕

> **如果代价不换任何正确性，它就是缺陷。**

写注释时给一个取舍编造理由，比不写理由更糟：它让后来人（包括我自己复核时）
以为这是有意为之的性能权衡，从而不再去质疑它。DR-042 讲的是
「测试全绿与路径未执行可同时成立」，本条是它的姊妹篇——
**「我以为的取舍可能只是缺陷」**，而错误的自我认知比缺陷更难发现，
因为它有完整的论证支撑。

### 正确实现与回归测试

```java
// 第 1 段：L1
CacheEntry.Hit localHit = local.getIfPresent(shortCode);
if (localHit != null) { localHitCounter.increment(); return localHit; }
// 第 2 段：L2
Optional<CacheEntry> fromRedis = redis.get(shortCode);
...
// 第 3 段：单飞回源
CacheEntry.Hit hit = local.get(shortCode, loader);
```

⚠️ **回归测试 `localHitSkipsRedisCompletely`**（比指标测试更重要）：
直接断言「L1 命中时 `redis.get` 调用次数 == 0」。
只断言 `local.hit` 计数是不够的——那测的是指标，而缺陷恰恰可以绕过指标发生。
**要断言被优化的那个资源本身没被访问。**

## DR-052 布隆检查与 L2 查询合并为一次 Redis 往返

### 背景

DR-007 明确要求「布隆检查与缓存查询合并为**一次** Redis 往返」，实现时也确实写了这个方法
（`RedisBloomFilter.checkAndGet`，Lua 脚本：EXISTS → k 次 GETBIT → GET 缓存key）。

⚠️ **但它从未被调用**——`RedirectService` 走的是裸的 `mightContain`，那是
「先 `EXISTS` 再 7 次 `GETBIT`」= **8 次独立网络往返**。合并脚本成了**死代码**。

### 后果

8 万 QPS 下等于每秒 **64 万次** Redis 往返，Redis 直接成为绝对瓶颈。
第 3 周压测的 3153 QPS 里有相当一部分由此而来（另一部分是 DR-051 的 L1 失效）。

### 决策

`RedirectService` 改为调 `checkAndGet`，L1 miss 时 **1 次 Lua** 同时完成
布隆检查 + L2 查询。新的调用链与往返数：

```
L1 命中        → 0 次 Redis
L1 未命中      → 1 次 EVAL（k 次 GETBIT + 1 次 GET，服务端执行）
布隆判不存在   → 1 次 Redis，然后 404
L2 有值        → 1 次 Redis，写 L1 后返回
都无          → 1 次 Redis + 单飞回源
```

⚠️ **L1 命中时布隆不执行**：L1 里的值是之前查过库确认存在的，
布隆判它「不存在」的唯一可能是假阴性（重建漏扫），
而此时我们已有一份**确定正确**的数据。反过来若先问布隆，
L1 命中也会多一次往返，DR-051 的修复就白做了。

### 代价

**布隆不是零成本，是从 8 次降到 1 次。** L1 miss 时仍要占一次往返。

### 验证

用 `redis-cli MONITOR` 确认真实往返（比 mock 强）：

```
客户端：[0 127.0.0.1:43206] "EVAL" "...整个脚本..." "2" "shortlink:bloom" "shortlink:code:xxx" ...
服务端：[0 lua] "EXISTS"  shortlink:bloom
       [0 lua] "GETBIT"  shortlink:bloom 100
       ...（共 8 条）
```

客户端只有 1 条命令，内部 8 条标记 `[0 lua]`（服务端执行，无网络往返），
1.2 毫秒内完成。

### 教训：「写好了没接上」比「没写」更危险

> 没写：review 时看得见「这里还没做」。
> 写好了没接上：review 时**以为设计已落地**。

死代码比缺失更危险，因为它让「是否已实现」这个问题无法从代码结构回答。
本条与 DR-051（「我以为的取舍其实是缺陷」）同源：
**错误的完成感比明显的缺失更难发现。**

### 触发场景

第 3 周压测前的设计核对。是用户要求「核实布隆是 1 次还是 7 次往返」时发现的。

### 回归测试

`BloomMergedRoundTripTest`（11 个）锁的是**往返次数**而非功能：
`localHitCausesZeroRedisCalls`（L1 命中 → `verifyNoInteractions`）、
`localMissCausesExactlyOneBloomCall`（恰好 1 次 `checkAndGet`）、
`bloomAbsentShortCircuitsWithoutLoading`（判否后不回源）、
`l2HitBackfillsLocalSoNextCallIsFree`（第二次请求 0 次 Redis）。

⚠️ **功能测试无法发现这类缺陷**：初版 `mightContain` 的单测全绿，
因为它功能完全正确。**只有断言「往返/访问次数」的测试能拦住它。**

#### ⏳ Redis 首连延迟与 50ms 命令超时的冲突

**现象**：编写 `checkAndGet` 的真实 Redis 验证时，用 `@SpringBootTest` 启动上下文后
**第一个 Redis 命令就超时**：

```
Caused by: io.lettuce.core.RedisCommandTimeoutException: Command timed out after 50 millisecond(s)
```

**待验证**：应用冷启动后**首次** Redis 调用的延迟分布。
若首连普遍超过 50ms，考虑把**连接超时**与**命令超时**分开配置：
连接放宽到 500ms，命令保持 50ms。

**为什么**：`spring.data.redis.timeout: 50ms` 目前同时约束了连接建立与命令执行。
但DR-011 的 50ms 是**命令执行预算**（跳转总预算 P99 < 50ms，慢于此已无意义），
**不该被连接建立消耗掉**——一次偶发的慢连接会让本该成功的请求被判为「Redis 不可用」，
进而走降级路径放行全部流量，限流与缓存同时失效。

**现状（2026-10-26 收尾核对）**：
- ❌ **未拆分**：`spring.data.redis.timeout` 仍是单一的 50ms；
- ⏳ **未验证**：第 5 周为单实例部署，长连接复用让首连只发生在启动时，
  多实例冷启动场景没有真实数据；
- 📌 **建议 v2 处理**：无论实测结果如何，**连接超时与命令超时分开配置**本身是对的 ——
  两者的语义完全不同，用一个值同时约束它们是历史包袱。


## DR-053 号段游标的初始化与清理顺序；压测容器必须显式回收

### 背景

第 3 周压测前清数据时，先删了 `shortlink:id:seq`，应用重启后发号器按默认值
重建为 `99999`。但**数据库里还留着 D5 建立的 6 条自动短码**：

```
0000Q0u  100000     0000Q0w  100002     0000Q0y  100004
0000Q0v  100001     0000Q0x  100003     0000Q0z  100005
```

（Base62 字母表是 `0-9 A-Z a-z`，**大写在小写之前**——
用小写字母表反解会得到 `0000q0U`，与库里对不上。核对时必须先读
`Base62.ALPHABET` 再算，不能凭「Base62 一般怎么排」的印象。）

于是下一个 `INCR` → `100000` → `0000Q0u` → **撞 id=13 的基线记录**，
`uk_short_code` 会拒绝，表现为创建接口批量 409/503。

### 决策

**清理 Redis 时，如果库里还有历史数据，必须把 `shortlink:id:seq`
设为 `max_existing_seq`，而不是删掉让它按默认值重建。**

本次：库中最大序号是 `100005`（对应 `0000Q0z`），
`SET shortlink:id:seq 100005` 后新数据从 `100006` → `0000Q10` 起。

⚠️ **删 key「看起来更干净」恰恰是错的**——它让状态依赖发号器的默认值，
而那个默认值（99999）与「历史上发过多少号」没有任何关系。
**序号是持久状态，不是可重建的缓存。**

### 附带决策：压测容器必须显式回收

前两次压测用 `timeout N bash scripts/bench-create.sh` 启动，
SIGTERM 只杀掉了**宿主 bash 脚本**，**容器内的 `xargs`/`curl` 子进程活了下来**，
持续打 MySQL，最终：

```
HikariPool-1 - Connection is not available, request timed out after 30000ms
(total=10, active=10, idle=0, waiting=136)
```

10 个连接全被这些僵尸进程占满，后续造数 136 个请求排队、30 秒集体超时。

规则：
1. `docker run` 一律带 `--rm`
2. 后台执行时**记录容器 ID**，结束时显式 `docker kill <id>`
3. **不依赖 `timeout` 杀宿主进程**——信号不传递到容器内，
   容器是独立的进程树

### 附带发现：造数并发必须小于连接池的 2 倍

造数并发 50 而 `maximum-pool-size=10`，是**一直存在的超配**，
只是前两周 1 万条里没有足够长的连接占用把它暴露出来。
本次并发降到 20（池子 2 倍）。

⚠️ **不要为了造数去调大连接池**——那是生产配置。
为了造数方便而改生产参数，等于让压测语料的生产环境与真实环境不一致，
压出来的数据失去了意义。造数慢一点没关系，它不参与性能数据。

### 教训

**DR-022（号段回退）从「已知风险」变成了「实际发生」。**

之前它被归类为「Redis 被清空时的故障场景」，评估结论是
「号段回退会造成短码冲突，有唯一索引兜底，不会数据损坏」。
本次证明了另一半：**唯一索引确实兜住了数据，但代价是创建接口批量失败**——
不是数据损坏，是**功能不可用**。评估风险时只看最坏的数据后果，
会低估可用性后果。

### 教训二：`bash -x` 不是 dry-run

与「SIGTERM 杀宿主 ≠ 容器内进程停了」并列的**同一种认知偏差**：

> **以为在「观察」，实际在「执行」。**

`bash -x scripts/bench-create.sh 10000 2` 本意是「看看实际执行的 docker 命令」，
但 `bash -x` 会**照常执行**脚本——它只是把命令打印出来。
结果这一条调试命令往库里真造了 **1350 条**数据。

两者是同一个错误的两个方向：

| 我以为 | 实际 | 后果 |
|---|---|---|
| `timeout` 杀宿主 → 容器内也停了 | 信号不传递，容器是独立进程树 | 僵尸进程占满连接池 |
| `bash -x` → 只是打印不执行 | 照常执行 | 调试污染了测试数据 |

规则：**脚本需要「看命令」的能力时，由脚本自身提供 `--dry-run`，
不要借 `bash -x`。** 借来的观察手段往往带着副作用。

### 归因澄清：两个独立问题，不要混为一谈

本次 exit=1 时，我一度把原因判成「造数并发 50 > 连接池 10」，后来发现真因是
`docker -v` 的源路径是相对路径（Git Bash 下被当成无名卷）。**但不能因此
推翻连接池那条**：

| 结论 | 是否成立 |
|---|---|
| 本次 exit=1 的直接原因 = 路径 | ✅ |
| 「并发 50 > 连接池 10」是历史隐患 | ✅ **仍然成立** |
| 「并发 50 从未被真正验证过」 | ✅ **仍然成立** |

路径问题让并发问题**没机会暴露**，不是让并发问题不存在。
两个都修，归因分开记。

### 教训三：并发输出的顺序 ≠ 发号顺序

造数用 `xargs -P 20` 并发，20 个 curl **并行输出**到同一文件，
谁先返回谁先写。所以 `codes.txt` 的第一行是「最早返回的响应」，
不是「最先分配的序号」。

⚠️ 验证发号起点**必须用 SQL 聚合**，不能用文件首行：

```sql
SELECT MIN(short_code) FROM short_link WHERE id > 18 AND is_custom = 0;
```

本次用 `head -1 codes.txt` 读到 `0000Q19` 而误判「起点错了」，
实际 `MIN(short_code) = 0000Q10`，完全正确。

>并发下的「第一」是个陷阱：文件顺序、返回顺序、分配顺序是三件不同的事。

### 教训四：期望值要写算式并复核两侧相等

本次我把期望值写成 `100005 + 10000 = 101005`——**算术错误**，
但它**符合预期形状**（都以 10 开头、都以 5 结尾），
看起来完全像一个合理的结论，于是自查时没有被拦下。

> **期望值写成算式后，必须复核等式两边是否真的相等。**
> 不能凭「感觉应该在 X 左右」——那是在用结论找依据。

这类错误最难自查，因为它**长得像结论**。本条与 DR-042 同源：
「看起来正常的值」恰恰是最需要验证的值。

## DR-054 Lua 合并调用的三个缺陷，以及「验证两层 ≠ 验证链路」

### 背景

`ecac087`（第 3 周）提交了 `RedisBloomFilter.checkAndGet`——把「布隆检查 +
L2 查询」合并为一次 Redis 往返。提交时我写「5 条验证全过」。

**实际上线后跳转全部 500。**

### 三个缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `toArgs` 返回 `List<String>`，而 `redisTemplate.execute(script, keys, Object... args)` 是**变参** | List 被当作单个元素包成 `Object[]{list}`，`StringRedisSerializer` 内部 `(String) value` 强转 → **ClassCastException** |
| 2 | `toArgs` 首元素放的是 `BIT_SIZE` 占位符，Lua 从 `for i = 2` 开始 | 实际只检查 **k-1 = 6** 个位，**Lua 不报错** |
| 3 | `catch (DataAccessException e)` 抓不住 CCE（它是 `RuntimeException`） | 本该「降级为回源」的兜底失效，异常穿透到 Controller → 500 |

### 三层测试的实际覆盖

| 层 | 当时的验证 | 有效性 |
|---|---|---|
| Lua 脚本行为 | `redis-cli --eval` + MONITOR | ✅ 真的验过 |
| 返回值解析 | Mockito 构造 `List.of(...)` | ⚠️ 形状由测试者决定 |
| **Java 调用 → Spring Data Redis → Lua** | **完全没有** | ❌ **缺陷所在** |

`RedisBloomFilterTest` 是 `@ExtendWith(MockitoExtension.class)` + `@Mock
StringRedisTemplate`——**`redis.execute` 本身被打桩**。参数序列化的真实行为
从未执行。

### 教训一：「两端都验过」不等于「链路通了」

> Lua 用 redis-cli 验了，解析用 mock 验了，
> **中间那层「Java 把参数交给 Spring Data Redis」没人验**——
> 而 `checkAndGet` 从提交到本次排查前，**Java 调用路径一次都没跑通过**。

与 DR-042 同源但更严重：
- DR-042：测试全绿，但路径未执行
- 本次：**测试全绿、脚本也对，但它们从未接在一起**

规则：**验证的覆盖范围必须明确说清——验证的是哪一层，不是整条链路。**
写「验证全过」时要说「验证了 Lua 行为与解析逻辑」，
不能省略成「验证全过」。

### 教训二：跨进程/跨语言边界必须有全链路集成测试

涉及 Redis Lua、HTTP 外部调用、MQ 序列化时，mock + 脚本单独验证不够——
必须有**走真实链路、断言外部可见效果**的测试（HTTP 状态码 + Location 头），
而不是断言内部方法返回值。

### 教训三：静默的错误比崩溃更危险，但也别夸大它的后果

缺陷 ②（k 从 7 变 6）不崩溃、不报错。我最初在注释与提交信息里写：

> 「误判率从 1% 升到 1.3%」

**这个数字是错的。** 实测（`scripts/bloom-fprate.py`）：

| n（写入量） | k=7 误判率 | k=6 误判率 |
|---|---|---|
| 1 000 | 0.0000% | 0.0000% |
| 1 000 000 | 0.0000% | 0.0000% |
| **10 000 000**（设计规模） | **1.0039%** | **1.0143%** |

**占位符 bug 的真实危害是 k 与设计规格不符（文档 7、代码 6），
不是误判率恶化。** 差异仅 0.01 个百分点。

> **教训：涉及数学公式的判断，必须算，不能凭直觉。**
> 我用「k 减小 → 误判率上升」这个常识替代了 `(1-e^(-kn/m))^k` 的计算，
> 而在 k 接近最优值时这个直觉**不成立**。

同理，**误判率不能用于判定 k 是 6 还是 7**（两者几乎相同）。
判定 k 的唯一可靠方法是：只置 6 个位、第 7 位留 0，看脚本是否判否
（`scripts/verify-bloom-lua.sh` 场景 E）。

### 附带修正：测试 profile 的 Redis timeout

`application-test.yml` 把 `spring.data.redis.timeout` 放宽到 **1000ms**，
生产 `application.yml` **保持 50ms 不动**（DR-011）。

50ms 是跳转命令的执行预算，不该被连接建立消耗——
一次偶发慢连接会让请求被判「Redis 不可用」，进而放行全部流量。
放宽只发生在测试 profile：否则测试测的是一个「与生产不同的超时」，
而超时行为正是需要验证的东西之一。

## DR-055 布隆重建窗口期：新创建的短码会 404

### 现象

容器重启后，**旧布隆不包含重建完成前新写入的短码**，这些短码在重建窗口期内
全部返回 404。

实测（1 万条数据）：

```
21:08:29  404  短码不存在: 0000Q0u← 布隆重建完成之前
21:08:30  404  短码不存在: 0000Q0v
21:08:31  404  短码不存在: 0000Q10
21:08:38  布隆全量重建完成：10009 条，耗时 19756 ms
（重测 → 全部 302）
```

### 影响

- **可用性黑洞**：重建窗口期内**新建的业务全部不可用**
- 窗口长度 = 全量重建耗时，随数据量线性增长：1 万条 20 秒，10 万条会更久
- 触发时机：应用重启、定时重建（每小时一次）
- ⚠️ 双缓冲（RENAME 原子切换）解决的是「重建期**旧数据**仍可用」，
  **没有解决「新数据在重建期不可用」**——后者是数据写入与布隆更新的时序问题

### v1 处置（本次采用）

**压测脚本造数后，必须等日志出现「布隆全量重建完成：N 条」才能开始打流量。**
不要用固定等待时间——数据量越大重建越久，固定时间必然踩坑。

### v2 优化方向（第 4 周考虑）

1. **创建时同步写穿布隆**（已实现，`BloomFilterMaintenance.writeThrough`），
   但它挂在事务 `afterCommit`，且**重建期间新建的 key 会被下一轮重建覆盖**——
   需要确认写穿与重建的并发顺序
2. **自愈机制**：重建期间若数据库查到短码但布隆说没有，
   允许把新发现的短码**补写进现行布隆**（而不是等下一轮）
3. **临时降级开关**：提供「布隆未命中只查库、不返回 404」的开关，
   重建期间自动开启、重建完成后自动关闭
4. **生产重建应在低峰期**，并限制单批扫描时间，避免与高流量重叠

### 与 DR-007 的关系

DR-007 的双缓冲设计目标是「重建不产生窗口」，这个目标**只对已有数据成立**。
本条补上的是「重建对新增数据的影响」——原文没有考虑这一面。

## DR-056 高并发下 Redis 限流阻塞应用线程（含 A/B 验证）

### 现象

第 3 周 QPS 从第 2 周的 **81289** 降到 **27641**（降 66%）。
在「新增功能只有布隆 + 单飞 + L1 优先」的前提下，这个降幅**完全不合预期**——
按 §9.1 的预注册，应该接近第 2 周。

### 根因

限流在 `RedirectController.redirect` 的**最前端**——在 L1 缓存之前：

```java
RedisTokenBucketLimiter.Decision decision =
        limiter.tryAcquire(resolveClientId(request), RateLimitScope.REDIRECT);
String targetUrl = redirectService.resolveTargetUrl(code);   // L1/L2 在这里面
```

每个请求（含 100% 命中 L1 的请求）都要先过一次同步 Redis EVAL，
约 0.5ms。在 Tomcat 线程池里，这个等待时间累积成吞吐断崖。

### 证据：A/B 对照 + CPU 采样

加 `linkforge.ratelimit.enabled` 开关做对照（**必须完全跳过 EVAL**——
把阈值调到 100 万做不到，那样 Lua 每次仍会执行，只是不再拒绝）：

| 组 | 限流 | QPS | P50 | P99 |
|---|---|---|---|---|
| A | 开启 | 21085 | 4.39ms | 15.74ms |
| B | 关闭 | **56638** | 1.29ms | 8.40ms |

CPU 采样（`docker stats`，压测中）：

| 组件 | CPU 占用 |
|---|---|
| linkforge-app | **900%**（约 9 核满载） |
| linkforge-redis | **0.4%** |

⚠️ **这是最关键的一条证据**：Redis 占用不到 0.5%，远未饱和。
瓶颈**不在 Redis 的计算能力**，而在**应用线程同步等待往返**。
若只看「QPS 掉了」就去查 Redis，会完全找错方向。

### 附带发现：压测流量共享同一个 IP 令牌桶

wrk 容器所有请求走同一个出口 IP → `resolveClientId` 返回同一个值
→ 全部请求争抢**同一个 Redis key**。这加剧了单 key 写热点
（`HSET` + `PEXPIRE` 打在同一个 key 上）。

⚠️ **但不能用「生产环境多 IP 会分散」来开脱**：
单 IP 高频攻击正是限流要防的场景。分散只让压测数据好看，
不代表设计没问题。

### 已做的微优化

Lua 里的 `PEXPIRE` 从「每次请求都执行」改为「**仅首次创建 key 时**执行」：

```lua
if state[1] == false or state[2] == false then
  redis.call('PEXPIRE', KEYS[1], math.ceil(ARGV[3]))
end
```

依据：桶的 `ts` 字段本来就靠 elapsed 判断补令牌，
即使 key 活得比 TTL 久，超期的桶也会被「补满」而非「拒绝」；
空闲 IP 的 key 由 `maxmemory` 淘汰策略兜底。

| 版本 | QPS | P99 | 每请求 Lua 写命令 |
|---|---|---|---|
| 每次 PEXPIRE | 21085 | 15.74ms | 2 条 |
| 首次才 PEXPIRE | **27641** | **11.74ms** | **1 条** |
| 提升 | +31% | −25% | −1 条 |

⚠️ 但这只把折损从 **63% 收窄到 51%**，**根因未解**。

### 决策

**v1（本周）**：保留 Redis 限流作为集群防刷底线，
把性能折损量化记录（63% → 51%），**不为了指标好看而摘掉限流**。

**v2（第 5 周或架构演进）**：引入**本地内存限流**（Guava RateLimiter /
Sentinel）拦截绝大多数流量，Redis 限流降为**低频兜底**
（如每 100 个请求抽样 1 个走 Redis 校验，或只对可疑 IP 启用）。

### 教训

> **任何保护机制的代价都要量化。**
> 「加一个防护」在低 QPS 下看不出问题，在高 QPS 下可能是断崖。
> 限流本身没问题，问题是**它被放在了同步路径的最前端**——
> 而没有人测过「关掉它能快多少」。

配套的方法论（PROJECT_BRIEF 第 12、13 条）：
- 加了保护机制后，必须有**关闭它的开关**，才能量化它的成本
- 只测「打开时性能够不够」是不够的——那测不出机制的代价

### 触发场景

第 3 周压测，QPS 未达预注册区间后的排查。

## DR-057 压测环境隔离与 JIT 爬坡

### 现象 1：宿主被无关应用抢占 CPU，QPS 缩水 50%

第 3 周第一次正式压测（容器已跑 19 小时）：

| 轮次 | QPS | 说明 |
|---|---|---|
| 30s 第 1 轮 | 24057 | 正常 |
| 30s 第 2 轮 | 24529 | 正常 |
| **60s** | **14365 → 11389** | **断崖式下跌** |

诊断发现两件事：

**① 宿主负载**：`loadavg 8.81 ~ 12.29`，系统 CPU 占用 27%~59.9%，
进程列表里 `douyin` 三个进程合计占约 1.5 个核。
清理后（`douyin` 进程数 0、CPU 降至 13~19%）重跑，
QPS 恢复到 **27641**（+12.7%）。

**② 容器长时运行后 GC 退化**：应用容器连续运行 19 小时后——

```
GC(152) Pause Young (Normal) (G1 Evacuation Pause) 662M->51M(1024M) 10.985ms
GC(152) Metaspace: 74443K(75456K)
容器内存：1.274 GiB（重启后降到 651 MiB）
```

Metaspace 已 74MB，G1 频繁 evacuation，吞吐掉 50%+。
重启容器后 Metaspace 清零，QPS 恢复。

⚠️ **两个因素都会污染数据，且都与代码无关**。

### 决策

**压测前置检查（写进 scripts/README.md 的流程）**：

1. 宿主 CPU 占用 **< 20%**，`loadavg < 2.0`
2. **重启应用容器**（清空 Metaspace 与 GC 状态）
3. 等日志出现「布隆全量重建完成：N 条」（DR-055）
4. 预热至少 15 秒（见现象 3）

### 现象 3：JIT 在 90 秒内未收敛

第 3 周三轮 QPS **单调上升**：

```
第1轮 25862 → 第2轮 27641 → 第3轮 28817 → 60s 29362
```

60 秒窗口比 30 秒高 **6.2%**。第 2 周三轮基本持平，本周却在爬坡。

原因：限流路径的代码路径更长（Lua EVAL + 结果类型转换 + 计数器自增），
HotSpot 需要编译更多方法。

> ⚠️ **口径影响**：任何带 Redis 同步调用的路径，
> **30 秒窗口不足以采到稳态数据**。后续周次若涉及此类路径，
> 主口径应改为 60 秒。

### 待验证（第 5 周：长稳测试）

19 小时 Metaspace 增长至 74MB，**疑似 Micrometer 动态 Tag 导致的泄漏**
——若代码里存在「按 IP / 按 key 动态创建 Counter/Timer」，
每个新维度都会常驻一个 meter。

⚠️ **这只是怀疑，未验证**。第 5 周长稳测试需要覆盖：
- 连续运行 8~24 小时后的 Metaspace 与堆增长曲线
- Micrometer registry 的 meter 总数是否随请求量线性增长
- 若确认，改为「预注册固定维度 + 高基数维度走聚合上报」

### 教训

> **性能数据的可信度，首先取决于环境，而不是代码。**
>
> 同样的代码，环境干扰下 QPS 差 50%。若不先控制变量，
> 后面所有的归因分析都建立在流沙上——
> 我曾差点把「宿主被抖音占满 CPU」误判成「限流优化失败」。

配套方法论：
- 压测前先记录**宿主负载 + 容器运行时长**作为元数据
- 数据作废就作废，**不要在污染的数据上做归因**

## DR-058 统计与跳转的单向解耦（异步队列 + 不可反压）

### 背景

第 4 周要把「跳转时统计 PV/UV」接进主链路。第一直觉是同步写：

```java
// ❌ 直觉写法
redis.opsForValue().increment(pvKey);
redis.opsForHyperLogLog().add(uvKey, visitor);
```

第 3 周的教训（DR-056）在这里直接适用：**每请求一次同步 Redis 往返，
在 5 万并发下足以耗尽 Tomcat 线程池**。第 3 周实测：限流的同步 EVAL 让 QPS
从 5.66 万掉到 2.45 万（折损 51%）。若统计也走同步路径，
主链路要承受两次这样的往返。

### 决策

**单向解耦**：跳转链路只做「投递」，统计的写入完全在独立的消费线程上。

```
RedirectController ──offer()──> ArrayBlockingQueue(10000) ──> 消费线程 ──> Redis
      │  （纯内存，< 1µs）              │
      │                                └── 写 Redis 慢在这里，不影响跳转
      └── 队列满 → 丢弃 + 计数
```

三条硬性红线：

1. **offer 绝不能阻塞**：它在跳转主链路上，任何阻塞都是延迟。
   用 `ArrayBlockingQueue.offer`（满时立即返回 false），不用 `put`。
2. **队列满绝不能降级为同步写**：**禁用 `CallerRunsPolicy`**。
   它会让调用方线程亲自执行「写 Redis」这个慢操作 ——
   等价于「队列满了就退化成同步写」，恰好是要避免的行为，
   而且**连指标都看不到**（只有延迟，没有丢弃计数）。
3. **丢弃必须可观测**：静默丢弃会让「统计不完整」无从发现。
   `shortlink.stats.dropped{reason=full|error}` 两个维度分开计 ——
   `full` 说明消费端跟不上（要扩容量），`error` 说明有 bug（要查），混在一起会互相掩盖。

### 为什么不用 `@Async`

三个已知坑：自调用失效（同类内部调用不生效）、异常被吞、
线程池满时的行为不明确。而我们需要的是「**明确的丢弃语义 + 可观测的丢弃计数**」。

### 为什么用 SmartLifecycle 而不是构造器里 start 线程

早期版本在构造函数里 `new Thread(...).start()`，有三个问题：
- 构造函数后续抛异常时线程已经起来，对象处于半初始化状态；
- 没有优雅停机：Spring 关闭时消费线程还在跑；
- 单元测试无法控制生命周期（每次 new 都会起一个线程）。

`SmartLifecycle` 把启停交给容器，且 `stop(Runnable)` 能保证容器等到消费线程真正退出。

### 附带决策：队列容量可配置

`linkforge.stats.queue-capacity`（默认 10000）。默认值按「1 万条短码的压测语料 ×
少量突发缓冲」定的，不是拍脑袋的整数。调大前先看 `shortlink.stats.queue.size`：
若它长期贴近容量而 `dropped{reason=full}` 仍为 0，说明消费端跟得上，
加容量只是浪费内存。

## DR-059 统计落库的「取走即删」与 PV/UV 双通道分离

### 背景

阶段 3 要把 Redis 里的统计增量定时落库到 `link_stats_daily`。
设计稿（docs/DESIGN-W4.md §5）给的是「HGETALL + DEL 的 Lua 脚本」，
实现时发现这套方案有三个硬伤。

### 决策 1：dirty set（写侧登记）取代 SCAN / HGETALL

**问题**：`HGETALL` 适用于「一个 key 装了一天的全部数据」的场景，
但本项目的 PV 是「每天每短码一个 key」（`shortlink:pv:{code}:{yyyymmdd}`），
一天可能有上万个 key。HGETALL 一次取不全。

改用 `SCAN` 也不行：
- SCAN 是**游标遍历不是快照**，扫描期间新产生的 key 可能被漏掉；
- 无法区分「今天有量」与「35 天内有量」，每分钟扫全量是纯粹的浪费。

**决策**：引入 dirty set `shortlink:stats:dirty:{yyyymmdd}`，
**谁产生数据谁登记**。PV 的 Lua 脚本在 `INCRBY` 的同一次执行里追加
`SADD dirty {code}` —— **不增加任何往返次数**。

### 决策 2：SPOP / GETDEL 取代「读 + 删」两步

⚠️ **绝不用 `SMEMBERS` + `SREM`**：两者之间若有新流量登记进来，
`SREM` 会把它一起删掉 —— 那批数据**既不会被本轮处理、也不会被下一轮处理**，
静静烂在 Redis 里直到 35 天 TTL 过期。

⚠️ **PV 用 `GETDEL`（Redis 6.2+）**：先 GET 再 DEL 的窗口里若进程崩溃，
下次 flush 会把**同一份增量再落一次库** → PV 翻倍。

⚠️ **UV 的 HLL key 不能删**：`PFCOUNT` 返回的是「当日至今的累计基数」，
删掉会把历史访客基数清零。残留靠 TTL 回收；下次同一短码再有流量时
读到的仍是更大的累计值，由 MySQL 侧的 `GREATEST` 天然去重。

### 决策 3：PV 与 UV 分成两条独立 SQL

```sql
-- PV：增量累加
... ON DUPLICATE KEY UPDATE pv = pv + VALUES(pv)
-- UV：覆盖
... ON DUPLICATE KEY UPDATE uv_estimated = GREATEST(uv_estimated, VALUES(uv_estimated))
```

两条理由都不可妥协：

1. **累加语义相反**。PV 是「自上次落库以来新增的量」；UV 的 `PFCOUNT` 是
   「当日至今的基数」，**不是增量**。若也用累加，一天 flush 1440 次
   会把同一个访客计 1440 遍。`GREATEST` 既符合语义，又让重试天然幂等。
2. **靶向重试的前提**。PV 成功、UV 失败时**只重试 UV**。
   若合并成一条语句，重试会把已成功的 PV 再累加一遍 ——
   而 PV 一旦多加**无法回滚**（UV 用 GREATEST，重复执行反而无害）。
   **「数据丢了」是少，「数据多了」是错**，后者严重得多。

### 决策 4：DLQ 靶向重试，payload 带 stage 维度

DLQ payload 格式：`v1|{stage}|{channel}|{linkId}|{statDate}|{value}`。

- `stage=mysql` → 重放动作是**写数据库**；`stage=redis` → 重放动作是**写 Redis**。
  用错会导致 PV 凭空翻倍或 UV 被清零。
- `channel=pv|uv` → 靶向重试的依据。**绝不在一次重试里同时更新两者**。

⚠️ DLQ 用 `LRANGE` 窥探 + `LREM key 1 value` 精确删除，**不用 `LPOP`**：
`LPOP` 一取出就出队，若取出后崩溃/失败那条数据就没了 ——
死信队列会退化成「一次性丢弃队列」。

⚠️ DLQ 的 key 用**处理当天**而非 `stat_date`：DLQ 是「处理队列」，
真正的归属日写在 payload 里。若按 `stat_date` 分桶，
一条 3 天前失败的数据会被塞进 3 天前的队列，而 replay 只回看 2 天 ——
它就永远不会被处理了。

### 决策 5：@Scheduled 方法体 catch-all Throwable

Spring 的 `@Scheduled` 在任务抛出异常后，**会取消该 Trigger 且不重建**。
表现是「跑了一次之后统计再也没落过库」，而日志里只有第一次的堆栈。

所以用 `catch (Throwable)` 而非 `catch (Exception)` ——
`NoClassDefFoundError` 这类 `Error` 同样会让调度永久失效。

配套：`spring.task.scheduling.pool.size: 2`。
默认单线程调度下，一个 42 秒的落库（重试 21s × 2 路）会**冻住整个调度器**，
阶段 4 的过期清理、阶段 5 的报表聚合全被一起拖死。

### 决策 6：执行前二次校验锁的 value

拿到锁之后、真正干活之前，再校验一次 value（`holdsLock`）。
防的是「超时实例继续破坏」：本实例加锁后业务跑了 90 秒（锁已 60 秒过期），
锁已被别人接管并持有 —— 此时若继续落库就是两个实例并发写，
PV 会被重复累加且不可回滚。校验失败就放弃本轮：
**宁可这一批数据多等一分钟，也不能重复累加 PV**。

### 教训

> **「取走即删」不是一个优化，是一个正确性约束。**
>
> 每一步多线程/多实例的边界上，「读」和「删」之间都有一道缝。
> 缝里发生崩溃，代价是同一份数据被处理两次 ——
> 而对于累加型统计，这个错误**不可逆**（不知道多加了哪一次）。
>
> 所以：能一条命令做完的，绝不拆成两条；
> 能用 Lua 原子做的，绝不靠客户端保证。
> 校验值（value / instanceId）不是多余的严谨，是**唯一**能证明
> 「这个锁确实是我的」的依据。

## DR-060 过期短链的定时清理：只清缓存、不改状态

> ⚠️ **本条决策在阶段 4 实现过程中被修订过一次**（2026-10-24）。
> 初版是「软删除过期短链」，修订为「**只清缓存，不修改 status**」。
> 修订理由见决策 2。**保留修订痕迹**是为了让后来人知道
> 「为什么不软删除」是一个被认真考虑过的选择，而不是没想到。

### 背景

第 4 周阶段 4：实现「定时扫描过期短链 → 清理缓存」的完整链路。

### 决策 1：定时扫描（每 5 分钟），但它**不是正确性必需**

跳转路径上本来就有惰性判定（`RedirectService` 每次请求都检查 `expire_at`），
所以从「用户能不能跳过去」的角度，清理**不是必需的**——过期短链在库里放着也跳不过去。

它解决的是**另外两件事**：
1. **缓存不释放**：`shortlink:code:{code}` 的 TTL 是 1 小时 + 抖动。
   过期短链的缓存条目会一直占着 Redis 内存。
2. **缓存一致**：过期短链的缓存条目在 TTL 到期前仍会命中，
   每次命中都要多走一遍状态判定。清理掉它们能省下这部分开销。

**频率取 5 分钟**：因为清理不是正确性必需，过期短链晚 5 分钟被清理用户侧完全无感；
而每分钟扫一次 1000 万行的表是纯粹的浪费。

### 决策 2：⭐ 只清缓存，**绝不修改 status** —— 保住 410 语义

**初版实现是「软删除过期短链」**（`status = DELETED`）。**它是错的**，错在：

```
清理前：status=ACTIVE + expire_at 已过 → LinkState.resolve → EXPIRED → 410 Gone
软删除后：status=DELETED                    → LinkState.resolve → DELETED → 404 Not Found
```

一个纯粹的过期链接，因为被后台任务扫过一次，对外就从
「**曾经存在但已失效**」变成了「**从未存在**」。

而 410 的**全部价值**就在于告诉调用方「这个码曾经有效」
（docs/API.md §4.4、PRD US-4）。软删除把这个信息抹掉了。

⚠️ 这不是「实现细节」，而是**对外契约的回退**。
后台任务不该有能力改变对外可观测的语义。

**修订后的决策**：

| 项 | 内容 |
|---|---|
| 数据库 | **完全不改**。`status` 保持 `ACTIVE`，`expire_at` 保持原值 |
| 缓存 | 清 L2（`shortlink:code:{code}`）+ L1（本地 Caffeine，靠 TTL 兜底） |
| 布隆 | **不动**（标准 Bloom 不支持删除） |
| 用户可见行为 | **完全不变**：请求过期短码 → L2 miss → 回源查库 → `LinkState.resolve` 发现 `expire_at < now` → **410** |

**为什么不需要新增 `EXPIRED` 枚举值**：
初版方案 B/C 的讨论里，「给 `LinkStatus` 加第三值」是保住 410 的另一种做法，
但它要动表结构、枚举、`LinkStatusTypeHandler`、所有 `status` 过滤、还有布隆语义。
而「不改状态」这一条路**零改动**就能达到同样的对外效果。

### 决策 3：新增 `idx_expire_status (status, expire_at)` 索引

V1 的两个索引都**不适用**于过期扫描：
- `uk_short_code (short_code)`：按短码查，跳转路径用；
- `idx_status_code (status, short_code)`：`status` 是**等值前缀**但 `expire_at` 不在索引里
  → MySQL 必须先取出所有 `status=0` 的行（1000 万行里约 1% = 10 万行）**回表**读 `expire_at` 再过滤。

这是最容易被忽略的一种「看起来用了索引、实际是全表扫」。

**实测对比**（20 万行、2000 条已过期、真实 MySQL 8.4）：

| 索引 | type | rows 估算 |
|---|---|---|
| `idx_status_code (status, short_code)` | `ref` | **97,181** |
| `idx_expire_status (status, expire_at)` | `range` | **2,000** |

约 50 倍差距。放到 1000 万行的生产表上：前者每轮扫约 500 万行，后者只扫 2 万行。

⚠️ **列顺序是 `(status, expire_at)`**：让 `status` 做等值前缀、`expire_at` 承担范围扫描。
它还能跳过「已软删除」的过期行（实测估算行数从 2000 降到 1）。

⚠️ **「不改状态」不影响这个索引**：扫描条件仍是 `status = 0 AND expire_at < ?`
（只清理「有效但已过期」的短码；已被 admin 手动删除的短链（status=1）
在删除时就已经清过缓存了，不需要重复清理）。

### 决策 4：扫描 + 逐条清缓存

清缓存需要**短码**。所以流程是「扫描 → 拿到 (id, shortCode) → 逐条清缓存」。

⚠️ **扫描本身不写库**，所以不需要事务，也不需要 `UPDATE ... LIMIT` 的影响行数语义。

### 决策 4b：⭐⭐⭐ 扫描**必须有游标**（否则后面的短码永远清不到）

**这是「只清缓存」这个决策的直接后果，也是阶段 4 收尾时发现并修复的缺陷。**

初版实现（软删除版）不需要游标：软删除把 `status` 改成 1，
扫描条件 `status = 0` 自然把已处理的行排除掉了。

但改成「**不修改 status**」之后，扫描条件 `status = 0 AND expire_at < ?`
对同一批行<b>永远成立</b>。于是：

```
第 1 轮：LIMIT 1000 → 拿到 id 最小的 1000 条 → 清掉它们的缓存
第 2 轮：LIMIT 1000 → **还是** id 最小的 1000 条 → 缓存早就不在了，白跑
第 3 轮：同上……
```

**结果：库里 10 万条过期短码，只有最前面 1000 条的缓存被清过，
后面 99900 条的缓存永远占着 Redis 内存。**

⚠️ 讽刺的是，这个 bug 在「软删除版」里不存在 —— 是「保住 410」这个正确的决策
暴露了它。**决策正确 ≠ 实现正确。**

**修复**：加游标，扫描条件加 `AND id > #{afterId}`。

| 项 | 决策 |
|---|---|
| 游标存哪 | **Redis**（`shortlink:stats:cleanup:cursor:{yyyymmdd}`），不是内存 |
| 为什么存 Redis | 任务在多实例下运行且进程可能重启。存内存会让「重启后从头开始」—— id 最小的那批被反复清理，中间那段永远扫不到 |
| 何时推进 | **清缓存之后**。若先推进再清，中途崩溃会跳过这一批，那批的缓存永远清不到 |
| 推进到哪 | 本批的**最大 id**（`ORDER BY id` 保证升序） |
| 游标 TTL | 35 天（与其它统计 key 一致） |
| 读游标失败 | **从头扫**，不中断清理（重复清一批幂等无害） |
| 写游标失败 | 只记日志，不中断清理（下一轮重复清一批，幂等无害） |

⚠️ 游标按天独立：跨天后从头扫新的一天（昨天的过期短码昨天就该扫完了）。

### 决策 4c：⭐⭐ 清缓存用**批量 DEL**，不是逐条 evict

初版逐条调 `cache.evict(shortCode)`，那是 **N 次 Redis 往返**。
实测（真实 Redis，5000 个 key，本机）：

| 方式 | 5000 条耗时 | 单条延迟 |
|---|---|---|
| 逐条 `delete` | **3174 ms** | 635 µs |
| 批量 `delete(Collection)` | **60 ms** | — |
| **加速比** | **52.9x** | |

逐条删会让一轮清理逼近分布式锁的 TTL —— 锁到期后另一个实例会进来重复清理
（幂等，但浪费，而且会出现两个实例同时清同一批）。

**修复**：`RedirectCacheService` 增加 `evictAll(Collection<String>)`，
实现是「先删本地（`invalidateAll`，无网络往返）→ 再一次多键 DEL」。

⚠️ Spring Data Redis 的 `delete(Collection)` 会把多键拼成**一条** `DEL k1 k2 k3 ...`，
不是 pipeline —— 效果一样（1 次往返），但要注意单条命令的参数长度上限。
5000 个 key 的命令约 100KB，远小于 Redis 的 512MB 限制，安全。

### 决策 5：布隆过滤器**不删除**，且**不会**被过期清理淘汰

标准布隆过滤器**不支持删除**（要删就得重算所有元素的位并重建整条链），
而重建成本是 O(全部短码数)。

本项目**已经有**每小时一次的全量重建（`BloomFilterMaintenance`），
但它走 `scanActiveWithId`——**只取 `status = 0` 的短码**。

⚠️ **代价（决策 2 的直接后果）**：由于本任务不改 status，
过期短码**永远留在布隆里**（重建也扫得到它）。
后果是：请求过期短码时，布隆判「可能存在」→ 缓存已清（miss）→ 回源查库 → 410。
比「布隆直接判不存在 → 404」多一次查库，但**结果完全正确**。

彻底解决需要让布隆能区分「有效」与「已过期」，即给 `LinkStatus` 增加第三值
—— 那是更大的改动，本阶段不做。

> **文档记录**：布隆的误判率随删除累积缓慢上升，但每小时全量重建会把它重置。
> admin 手动删除的短链（status=DELETED）仍会被重建自然淘汰。

### 决策 6：与统计 flush 用**不同的锁**，且**必须能并行**

`shortlink:stats:flush:lock`（统计落库） vs `shortlink:stats:cleanup:lock`（过期清理）。

两个任务操作的是**不同的数据**（`link_stats_daily` vs `short_link` 的读 + Redis 缓存删），
用同一把锁会让其中一个白等一轮。而且它们**必须能并行**：
清理要扫大表、flush 要写统计表，串行化会让两者总时长相加。

⚠️ 由于本任务**不改数据库**，它与 flush 之间**没有任何数据竞争**。

### 决策 7：统计**继续**落到已过期（甚至已删除）短链的 link_id 上

`resolveIdsByShortCodes` **不过滤 status**（口径与 `findByShortCode` 一致）；
统计落的是**已发生的访问**——那些访问真实发生过，不该被丢弃。

⚠️ 反过来「跳过已过期短链」是**错的**：那会让「过期前最后一分钟的访问量」凭空消失，
且**没有任何指标能发现**。

### 决策 8：清缓存失败只记指标，不抛异常

失败的后果是「缓存条目多留一会儿」（TTL 到期自然消失），**不影响任何正确性**——
缓存里存的是带 status 与 expireAt 的 `CachedLink`，
跳转路径命中缓存后**仍然要走一遍状态判定**。

### 决策 9：⚠️ `@Transactional` 的同类自调用陷阱（差点又踩一次）

初版把软删除 + 清缓存写成了 `ExpiryCleanupService` 的**私有方法**，
用 `this.softDeleteBatch(...)` 调用，并标注 `@Transactional`。

**这是错的**：`@Transactional` 依赖 **Spring AOP 代理**生效，
同类自调用走的是**原始对象**而不是代理 → 注解**完全不生效** → 方法里根本没有事务。

后果：`TransactionSynchronizationManager.isSynchronizationActive()` 返回 false
→ 走「无事务时立即清缓存」的退化路径 → **缓存清理发生在数据库事务提交之前**。
而那正是 admin 的 `DeleteLinkService` 早就踩过的坑：
并发请求会在「缓存已删但事务未提交」的窗口回源，
读到未删除的旧值并重新写入缓存 —— **删除静默失效**，而监控上一切正常。

**修复**：把软删除抽成**独立 bean**（`LinkExpiryService`），
跨 bean 调用才走代理。

⚠️ 本条教训**在最终方案下不再适用**（不写库 ⇒ 无事务需求），
但它值得单独记下来——**因为「加了 @Transactional 就以为有事务」是一个极隐蔽的坑**。

### 教训

> **后台任务不该有能力改变对外可观测的语义。**
>
> 初版实现里，「把过期短链软删除」看起来是理所当然的清理动作，
> 而且在数据库层面完全正确（状态与事实一致了）。
> 但它在**协议层**制造了一次静默的语义变更：
> 410 Gone（曾经存在）变成了 404 Not Found（从未存在）。
>
> 这个问题的隐蔽性在于：所有单元测试都绿，数据库状态也"更一致"了，
> 唯一能发现它的是**对照 API 契约去检查对外响应码**。
>
> 判据：**清理类任务应该只释放资源，不该重定义语义。**
> 「过期」与「删除」是两种不同的业务事实，清理任务没有资格把它们合并。
>
> 另一条同样重要的：
> **决策正确 ≠ 实现正确。**
> 「不修改 status」这个决策是对的，但它让「扫描条件永远成立」——
> 而扫描条件是实现细节，**它不会因为决策变了就自动跟上**。
> 改决策时必须重新审视受影响的每个机制：扫描条件、索引、游标、事务边界。
> 这次是靠「10 万条里只有 1000 条能被清」这个具体的推演发现的，
> 不是靠跑测试（测试里只有几条数据，每轮都扫到同一批也「看起来正常」）。

## DR-061 「Micrometer 动态 Tag 导致 Metaspace 泄漏」是伪 bug —— 附 Hidden Class 机制

> ⚠️ **本决策推翻的是 DR-057 里记录的一个「怀疑」，不是推翻 DR-057 的全部内容。**
> DR-057 的另外两个结论（宿主被无关应用抢占 CPU 需隔离压测环境、
> 容器长时运行后 GC 退化需重启）**依然成立**。
> 被推翻的只有「Metaspace 涨是 Micrometer 动态 Tag 导致的」这条因果链。

### 背景

DR-057 记录：

```
GC(152) Pause Young (Normal) (G1 Evacuation Pause) 662M->51M(1024M) 10.985ms
GC(152) Metaspace: 74443K(75456K)
容器内存：1.274 GiB（重启后降到 651 MiB）
```

现象是「容器跑 19 小时后 Metaspace 涨到 74MB，G1 频繁 evacuation，吞吐掉 50%+」，
当时的怀疑对象写的是 **Micrometer 动态 Tag**。

第 5 周安排 8 小时长稳测试来验证这个怀疑。

### 决策 1：先做**静态核查**，把「怀疑」拆成可证伪的子命题

在跑任何测试之前，先用静态扫描确认「哪些假设根本不可能成立」：

| 假设 | 核查方法 | 结果 |
|---|---|---|
| Micrometer 动态 Tag | 扫描全部 `.tag(...)` 调用点 | ❌ **所有 tag 值都是编译期常量**，无 per-request meter 创建 |
| 弱引用 Gauge 泄漏 | 检查 `AsyncStatsQueue` 的 Gauge 绑定对象 | ❌ 绑定 `final` 字段，被 Spring 容器**强引用** |
| 动态代理 / 反射类加载 | 扫描 `Proxy.newProxyInstance` / `Class.forName` / CGLIB | ❌ **零命中** |
| `http.server.requests` 的 `path` tag | 检查实际暴露的 tag 集合 | ❌ **未开启**（只有 `uri` 模板，基数固定） |

⚠️ **四种子假设全部被静态排除**。这一步的价值：
它把「跑 8 小时看看」从「碰运气」变成了「验证唯一剩下的机制性可能」。

### 决策 2：⭐ 概念纠正 —— **Metaspace 是类加载，动态 Tag 是堆**

这是整个排查的**认知转折点**：

| | 存储什么 | 什么会让它涨 | 例子 |
|---|---|---|---|
| **Metaspace** | **类元数据**（class metadata） | **加载新类**（类一旦加载就永不卸载，除非类加载器被回收） | Spring Bean、CGLIB 代理、lambda 隐藏类 |
| **堆（Heap）** | 普通对象 | 对象数量增加 | Micrometer 的 **Meter**、缓存条目 |

**Micrometer 的 Meter 是普通堆对象。动态 Tag 增长的是堆，与 Metaspace 无关。**

> ⚠️ 所以「Micrometer 动态 Tag 导致 Metaspace 增长」这条**因果链在机制上就不成立** ——
> 就算 tag 真的是动态的，涨的也是堆。

**但这不能只靠推理否定一个观察到的现象。** 推理只能排除假设，
不能证明「那 74MB 到底是什么」。所以仍然要跑 8 小时长稳。

### 决策 3：观测方案必须能区分「三种情况」，而不是只测一条曲线

| 曲线 | 判读 |
|---|---|
| `jvm_memory_used_bytes{area="nonheap",id="Metaspace"}` | 怀疑对象 |
| `jvm_classes_loaded_classes` | ⭐ **最直接的证据**：已加载类数 |
| `jvm_classes_unloaded_classes_total` | 累计卸载数（本项目**恒为 0**） |
| `shortlink.meter.count`（自建 Gauge） | 对照组：动态 tag 涨的是**堆**不是 Metaspace |

⚠️ **一个差点让结论反转的坑**：查 `jvm_memory_used_bytes{area="metaspace"}`
返回**空**——而 Micrometer 里 Metaspace 的 `area` 是 **`nonheap`**（与
Compressed Class Space 同属一类）。
**空曲线看起来像「没有泄漏」，结论会完全反过来**（TROUBLESHOOTING T-020）。

### 决策 4：Hidden Class（lambda 隐藏类）—— 中途的一次认知修正

运行 1 小时后，实测数据**推翻了我自己写下的推论**：

```
[16:10:29] Metaspace=77168928 (+0.089MB)  Classes=+0  Unloaded=0
```

**Metaspace 涨了 93KB，而 `LoadedClassCount` 一点没涨。**

根因是 **JDK 15+ 的 hidden class（隐藏类）**：

- Lambda 表达式在运行时由 JVM 生成一个**隐藏类**（LambdaForm）；
- 它**计入 Metaspace**（它确实占元空间）；
- 但它**不计入 `LoadedClassCount`**（那个计数器只统计「普通」的、被
  ClassLoader 加载的类）；
- 隐藏类的数量 = 代码里**不同的 lambda 调用点**数量（**固定**），
  **与请求量无关**。

> **这正是设计阶段列出的「嫌疑 3：Lambda 隐藏类累积」。**

**修正后的两层表述**：

| 层 | 结论 |
|---|---|
| ① | `unloaded_total` 恒为 0 → 类加载器从未被回收 → **已加载类数单调递增、不会回落** |
| ② | Metaspace 增长 = 已加载类 + **hidden class（lambda）** + 其它元数据 |

⚠️ **但最终 8 小时数据又修正了一次**：总增量 1.55MB / 50 类 = **31.7 KB/类**，
**高于**普通类 ~19KB/类 的基准 → 说明**增量主体确实是类加载**，
hidden class 的贡献很小（后期那几 KB 才是）。

> **教训**：**「我修正过一次」不等于「修正到位了」。**
> 第二次修正（最终数据）推翻了第一次修正（hidden class 是主要嫌疑）的一部分。
> 每一层修正都要有数据支撑，不能停在「听起来合理」。

### 决策 5：✅ 最终判定 —— **不是泄漏**，DR-057 的 74MB 是**稳态基线**

**8 小时实测数据**（详见 `docs/DESIGN-W5.md §2`）：

| 节点 | Metaspace | Classes | Meters | GC（young） | Full GC |
|---|---|---|---|---|---|
| 基线（重启后） | 72.47 MB | 14,946 | 197 | — | — |
| 2 小时 | 73.78 MB | 14,995 | 199 | — | — |
| 4 小时 | 74.01 MB | 14,996 | 199 | — | — |
| **8 小时** | **74.02 MB** | **14,996** | **199** | **14,388** | **0** |

**增量逐段收敛**：

```
0~1h   +1,090.0 KB  (1.06 MB/h)   Classes +46
1~2h     +238.1 KB  (0.23 MB/h)   Classes  +3
2~4h     +158.2 KB  (0.08 MB/h)   Classes  +1
4~6h      +93.6 KB  (0.05 MB/h)   Classes  +0
6~8h       +5.8 KB  (0.00 MB/h)   Classes  +0   ← 完全走平
```

**六条判定依据**：

1. **8 小时只涨 1.55 MB**，且增量**单调收敛到 0**（最后 2 小时 5.8 KB）。
   ⚠️ **泄漏是恒定速率增长，不是单调递减** —— 形态就不匹配。
2. **已加载类数从 t=120m 起完全平稳**（14,995 / 14,996）—— 没有持续加载新类。
3. **Meter 数从 t=30m 起恒为 199**（7.5 小时零增长）——
   **动态 Tag 根本没有增长**，原怀疑被直接证伪。
4. **零 Full GC**（`sum(jvm_gc_pause_seconds_count{action=~".*major.*"})` 返回空），
   14,388 次全是 young GC。
5. ⭐ **JVM 自己触发了 1 次 `cause="Metadata GC Threshold"`** ——
   说明**元空间管理机制正常工作**，不是应用层失控。
6. 终点 **74.02 MB** 与 DR-057 记录的「19 小时后 74MB」**几乎一致** ——
   那个数字是**稳态基线**，不是泄漏水位。

**流量真实性**：8 小时 **369,536,164** 次跳转（≈ 12,566 QPS），
`/actuator/prometheus` 被抓取 1,861 次（每 15s 一次，8 小时不间断）。

### 决策 6：⚠️ 排查过程中我自己犯的三个错（必须记录）

每一个都差点导致错误结论 —— 这部分的价值可能高于结论本身。

#### ① 「GC 恒为 1」—— **差了 4 个数量级**

采样脚本取 Prometheus 返回的**第一条** series。而
`jvm_gc_pause_seconds_count` 有**多条**（每个 GC cause 一条）：

| cause | count |
|---|---|
| `G1 Evacuation Pause` | **14,387** |
| `Metadata GC Threshold` | 1 |

`r[0]`（按 label 排序第一条）恰好是 count=1 那条 ——
于是日志里出现「8 小时只 GC 了 1 次」。

> **教训**：**取多 series 查询的第一条，等于取一个与语义无关的值。**
> Prometheus 的 series 顺序由 label 排序决定，**与「哪个更重要」无关**。
> 判据：**要总数就用 `sum()`，要分类就逐条列出，不要用「第一条」。**

#### ② 「PV 累计 1,805」—— **根本不是 PV**

采样用 `http_server_requests_seconds_count{uri=~"/.*"}` 的第一条 series，
而 `r[0]` 是 **`/actuator/prometheus`**（每 15s 抓一次）。
30 分钟 120 次 —— **正好是抓取频率**，数字看起来「很合理」，
但它与业务 PV 毫无关系。真正的 PV 在 `uri=~"/{code}"`：**369,536,164**。

> **教训**：**「数字看起来合理」是最危险的验证方式。**
> 120 次/30 分钟与抓取频率完全吻合，说明它**自洽**，但自洽 ≠ 正确。
> 判据：**指标必须显式限定维度**，不能靠「取第一条」。

#### ③ shell 引号嵌套会**静默破坏查询**

`--data-urlencode "query=$q"` 中若 `$q` 含双引号
（如 `uri="/actuator/prometheus"`），**shell 会把它当作结束引号** →
参数被拆散 → Prometheus 返回空 → 脚本**不报错**（只取到空串）。

修复：`q="${q//"/'}"`（PromQL 的 string literal 单双引号等价）。

> **教训**：**「取到空值」与「查询写错了」在脚本里长得一模一样。**
> 一个静默返回空的采集脚本，比一个会报错的脚本危险得多 ——
> 后者会让人去查，前者只会让人**相信数据是「没有变化」**。

### 教训

> **一、机制性推理可以排除假设，但不能替代数据。**
>
> 决策 2 的概念纠正（Metaspace vs 堆）**逻辑上完全正确**，
> 但它只能证明「原怀疑不成立」，**不能证明「那 74MB 是什么」**。
> 必须用 8 小时的曲线数据回答后者。
>
> **二、「看起来像 bug」的现象值得认真对待，但值得用「值得证伪的方式」对待。**
>

> 它有 8 小时的可信曲线、有六条互相独立的依据、
> 以及一个**能解释为什么它看起来像 bug** 的机制（hidden class）。
>
> **三、采样脚本的 bug 会变成「数据结论」。**
>
> 决策 6 的三个错误，每一个都产生了**看起来合理**的错误数字。
> 最危险的不是「采不到数」，而是「采到一个**自洽的错数**」——
> 它会让整个 8 小时的曲线都变成另一个故事。
>
> **四、每次改决策，都要重新审视受影响的每个机制。**
>
> 第 4 周的 DR-060 就踩过这个坑（改成「不改 status」之后，
> 扫描条件变成了永远成立 → 游标必须补上）。
> 本次也一样：把「动态 Tag」从「元空间问题」重新归类到「堆问题」之后，
> **分析方法**（从「看 Metaspace」变成「看两个增量的比值」）必须跟着变。

## DR-062 第 6 周收尾发现的 4 处缺口：**一律不改代码**，全部归档为 v2 事项

### 背景

第 6 周「交付物收口」阶段做了一次**逐条比对「文档写了什么」与「代码做了什么」**的审计，
发现 4 处**文档与实现不一致**或**设计未落地**的地方：

| # | 缺口 | 性质 | 首次发现于 |
|---|---|---|---|
| 1 | 布隆重建窗口内**写穿没有双写**（`put()` 只写现行 key，`rebuild()` 的 `RENAME` 覆盖现行 key）→ 新建短码偶发 404 | 设计要求有，实现漏了 | DR-055（第 3 周实测到，v1 绕过） |
| 2 | 统计 **HLL key 驻留 35 天**（设计要求「当天」），落库只 `PFCOUNT` 不删 UV key | 实现与硬约束不符 | `docs/DATABASE.md` §9.2 原设计 |
| 3 | 统计 **90 天保留的批量清理任务未实现** | 设计未落地 | `docs/DATABASE.md` §7.3 |
| 4 | **readiness 不含 MySQL / Redis / 布隆**（无自定义 `HealthIndicator`） | 实现与文档不符 | `docs/ARCHITECTURE.md` §15.2 原文档 |

### 决策

> **这 4 条一律不改代码，全部保留为 v2 Roadmap 项，并在 README / 文档中如实标注。**

### 理由

1. **第 5 周的性能数据已冻结**。
   「29,387.67 QPS / P99 11.00ms」是本项目最有价值的产出，
   而它的可复现性依赖于**冻结的代码**。
   任何代码改动都会让这组数字失去意义，除非重跑整套压测 ——
   而「为了修一个非阻塞问题而重跑整套压测」是明显的成本倒挂。
2. **这 4 条都不是当前部署形态下的阻塞问题**：
   活跃链路数远低于 PRD 的 10 万假设（HLL 内存没到）、
   布隆重建窗口是分钟级窄窗口、清理任务在统计行数上来之前不影响、
   readiness 缺口已由 Compose 侧各容器的 healthcheck 兜住。
3. **把它们明确写下来，比默默留着或草率改掉更有价值。**
   「知道自己没做什么、为什么不做、什么时候做」本身就是工程判断力 ——
   尤其在求职场景下，**能说清取舍边界**比「看起来什么都会」更可信。

### 代价与影响

- ⚠️ **必须承担的风险**：这 4 条是真的缺陷，不是「可以忽略的细节」。
  项目方与读者需要明确知道：
  ① 新建短码在布隆重建窗口内可能 404；
  ② Redis 内存上界比设计高约 35 倍（1.2GB → 42GB）；
  ③ 统计表不会自动清理；
  ④ 「readiness 通过」不代表依赖可用。

## DR-063 自定义短码长度与跳转路径不一致：非 7 位是「创建成功但永远 404」的死链

### 背景

第 6 周**封板自检**（功能冒烟）时实测发现：

| `customCode` | 长度 | 创建 | 跳转 |
|---|---|---|---|
| `abcd` | 4 | **201** | **404** |
| `Abcde` | 5 | **201** | **404** |
| `Abcdef` | 6 | **201** | **404** |
| `Abcdefg` | 7 | **201** | **302** ✅ |
| `Abcdefgh` | 8 | **201** | **404** |

数据库里查得到这些记录（`status=0`、`expire_at=NULL`），布隆与缓存都正常，
**只有跳转接口返回 404**。

### 根因

| 侧 | 规则 | 出处 |
|---|---|---|
| **创建** | `customCode` 匹配 `^[a-zA-Z0-9]{4,8}$` —— 4~8 位**全部放行** | `ShortCodeFormat` + API.md §5.2 |
| **跳转** | 长度必须 `== IdSpace.SHORT_CODE_LENGTH`（= **7**），否则按「不存在」处理 → **404** | `LinkValidator.validateForRedirect()` |

⚠️ **代码里其实早就写明了这件事** —— `validateForRedirect()` 的 javadoc：

> 「⚠️ **自定义短码（4~8 位）在这里会被判为 404**，这是契约的既定行为而非遗漏：
> 跳转接口按默认短码长度定位，自定义短码是否可跳转属于**待确认项**，
> **在契约改写之前不擅自放宽**。」

所以这不是「实现跑偏了」，而是**一个被有意推迟的契约问题**，
但它**从未进入 `docs/API.md` 的待确认清单（§13）** ——
**对外文档在积极鼓励用户使用一个会产出死链的长度**。

### 决策

> **v1 不改代码**（与 DR-062 同理：第 5 周性能基线已冻结）；
> **但必须补齐对外文档的披露** —— 这是纯文档改动，不影响任何性能数据。

具体动作：
1. `docs/API.md` §5.2 新增「已知契约缺口」小节 + §13 待确认清单补 **P-6**；
2. `docs/TROUBLESHOOTING.md` 新增 **T-029**；
3. `docs/ROADMAP.md` §15 新增 **V2-5**；
4. `README.md`「已知缺口与 v2 Roadmap」补第 5 条。

### 理由

1. **改代码会破坏已冻结的性能基线** —— 改的是跳转路径的校验分支（压测热路径）；
2. **跳转路径的「长度不符 → 404」是有意为之的契约**（DR-037）：
   7 位空间里不可能存在 4 位短码，按「不存在」比按「参数非法」更符合语义。
   若为支持自定义短码而放宽，**「长度不符 = 一定不存在」这条推理就不再成立**，
   DR-037 规定的判定顺序（字符检查必须先于长度检查，理由是 `abc_` 这类
   4 位非法串应当 400 而非 404）也需要一并重新审视；
3. 因此正确顺序是**先改契约、再改实现**（方案 A：把正则收窄为 `^[a-zA-Z0-9]{7}$`），
   而不是单方面在实现里放宽。

### 代价与影响

- ⚠️ **v1 的对外契约是自相矛盾的**：API.md 声称支持 4~8 位自定义短码
  （还专门写了「比自动生成的 7 位更宽松，便于用户取有意义的名字」），
  却不说明其中 4 种长度会产出死链。
- ✅ **本次已修正文档**（见上方 4 项动作），调用方据此知道「只应用 7 位」。
- ✅ **主路径不受影响**：自动生成的短码恒为 7 位，永远可跳转；
  受影响的只是自定义短码中长度 ≠ 7 的那 4 种长度（占允许长度的 4/8）。
- ⚠️ **这是本次 5 个已知缺口中严重性最高的一个** ——
  前 4 个是「边缘场景 / 量没到」，这个是「**按文档正常使用就会踩到**」。
  它之所以没被前 4 周发现，是因为**前几周的压测语料全是 7 位自动码**，
  而功能冒烟此前只验过「自动码能不能跳」。

### 教训

> **契约的两端必须同时验证：能创建出来的，必须能被访问到。**
>
> 单元测试与集成测试都覆盖了「创建成功」（201）与「7 位码能跳转」（302），
> 但**没有一条测试断言「创建出来的短码一定能被访问」**——
> 因为测试用例的短码碰巧全是 7 位。
> **测试用例的取值分布决定了它能发现哪一类缺陷**：
> 全用「典型值」的测试集，对「边界值类缺陷」是盲的。

### 与其它决策的关系

- **DR-037**：跳转路径的「字符 400 / 长度 404」与判定顺序 —— 本条放宽它就会推翻它的前提；
- **DR-062**：v1 一律不改代码的整体决策 —— 本条沿用同一原则；
- **DR-015**：短码路径字符校验与尾斜杠处理；
- **API.md §5.2 / §13 P-6**：本条对应的文档落点。

### 触发场景

第 6 周封板自检：功能冒烟逐个长度验证自定义短码时发现。

## DR-064 后台鉴权前移为 Servlet 过滤器；「方法不被支持」映射 405 而非 500

### 背景

2026-10-27 本地验收实测到一个**真实缺陷**：

```
GET /admin/api/v1/links/0000VF0   Authorization: Bearer <错误的 Token>
→ 500 {"code":"LINKFORGE-500-01","message":"internal server error"}
```

契约（API.md §7.3）要求「缺失、格式错误、值不匹配**一律返回 401**，无例外」。

### 根因分析（⚠️ 与最初的猜测不同）

最初的猜测是「Token 比对时抛了 NPE / `MessageDigest.isEqual` 遇到 null 炸了」。
**实测排除了这个猜测**：

| 验证 | 结果 |
|---|---|
| `AdminToken.matches(null)` / `matches("")` | 早已被挡住，返回 false，**不抛异常** |
| `DELETE` + 错误 Token | **401** ✅ 一直是对的 |
| `GET` + 错误 Token / 无 Token | **500** ❌ |
| 应用日志 | `HttpRequestMethodNotSupportedException: Request method 'GET' is not supported` |

**真实根因有两层，都与「Token 比对」无关**：

1. **鉴权的位置错了**：`/admin/api/v1/links/{code}` 只定义了 `DELETE`。
   Spring 在**路由解析阶段**就抛出 `HttpRequestMethodNotSupportedException`，
   而鉴权检查写在 **Controller 方法体内**，**根本没被执行到**。
2. **异常没有映射**：该异常没有被任何 `@ExceptionHandler` 映射，
   于是掉进兜底分支 → **500**。

> 换句话说：**只要鉴权在 Controller 里，「路由不匹配」这个分支就永远绕过鉴权**，
> 而绕过鉴权的表现不是「放行」，是「500」——
> 一个**客户端问题**被伪装成**服务故障**，会污染错误率指标与告警。

### 决策

1. **鉴权前移为 Servlet 过滤器**（`AdminAuthFilter`，注册在 `/admin/*`）。
   Servlet 过滤器在 `DispatcherServlet` 之前执行，因此**先于路由解析**。
2. **判定逻辑集中到唯一入口**：`AdminToken.matchesAuthorizationHeader(String)`。
   它对 null / 空串 / 缺 `Bearer ` 前缀 / 乱码 / 长度不符 一律返回 `false`，
   **永不抛异常**。Controller 内保留同样的调用作为**纵深防御**。
3. **`HttpRequestMethodNotSupportedException` → 405**（新增 `LINKFORGE-405-01`），
   响应带 `Allow` 头。不再让它落进兜底分支。
4. **错误体构造下沉到 core**（`ErrorBody`）：过滤器在 Servlet 链上，
   **不在** `@RestControllerAdvice` 的处理范围内，必须自己写响应体；
   若两处各写一份，格式迟早漂移成「有些接口的错误体少一个 timestamp」。

### 理由

- **500 的语义是「服务有 bug，需要人介入」**。把「客户端用错了 HTTP 方法」
  报成 500 会让运维去查代码，而问题在调用方。405 是 HTTP 的标准语义。
- **过滤器比拦截器更早**：HandlerInterceptor 的 `preHandle` 在**路由解析之后**才执行，
  解析失败时它根本不会被调用 —— 解决不了本问题。Filter 在 `DispatcherServlet` 之前，是唯一能保证
  「先鉴权、后路由」的位置。
- **URL 模式交给容器**（`FilterRegistrationBean.addUrlPatterns("/admin/*")`）
  而不是 `@Component` + 运行期判断路径前缀：
  后者要求过滤器自己判断「哪些路径要鉴权」，漏一个前缀就是漏一个接口的防护。
- **core 保持零 web 依赖**（DR-021）：`ErrorBody` 只用 `Map` 与 `OffsetDateTime`。

### 代价与影响

- ⚠️ **新增一个错误码** `LINKFORGE-405-01`（契约的加法，不改变任何既有行为）。
- ⚠️ **过滤器与 Controller 各有一次检查**（纵深防御的代价：一次极廉情的
  `MessageDigest.isEqual`，可忽略）。
- ✅ **性能无影响**：过滤器只在 `/admin/*` 上运行，跳转热路径完全不受影响。
  ⚠️ 这也意味着**第 5 周冻结的性能基线依然有效**（本次改动不触碰跳转链路）。

### 验证

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `GET /admin/...` + 错误 Token | **500** | **401** `LINKFORGE-401-01` |
| `GET /admin/...` + 无 Token | **500** | **401** `LINKFORGE-401-01` |
| `DELETE /admin/...` + 错误 Token | 401 | 401（不变） |
| `GET /admin/...` + 正确 Token | **500** | **405** `LINKFORGE-405-01` + `Allow: DELETE` |
| `DELETE /admin/...` + 正确 Token | 200 | 200（不变） |
| 鉴权失败后短链是否还在 | — | **仍在**（`status=0`） |

新增测试：`AdminAuthFilterTest`（9 个，单元）、`GlobalExceptionHandlerTest`（8 个，单元）、
`AdminAuthEndToEndTest`（8 个，真实 HTTP + 真实 MySQL 容器）。

### 教训

> **「守卫要站在被保护的资源之前」，而不是「站在它的某个分支里」。**
>
> 写在 Controller 里的鉴权，看起来「在任何业务逻辑之前」—— 事实上只在
> 「路由能匹配上」的前提下才在业务逻辑之前。
> **路由解析失败是一条独立的路径**，它绕过了你写在方法体里的所有前置检查。
>
> 泛化地说：**任何「先检查再执行」的守卫，都要问一句「检查失败时会不会走到另一个分支」。**
> 这里的另一个分支就是「没有匹配的 handler」。
>
> ⚠️ 附带的客户端教训：本类第一次用 `RestTemplate` 写，**DELETE 的 401 响应体读不出来**
> （`getBody()` 返回 null，而响应头里明明有 `Content-Length: 117`）——
> 是 `SimpleClientHttpRequestFactory` 底层的 `HttpURLConnection`
> 在 401 上的鉴权处理路径把错误流吃掉了。
> **用错 HTTP 客户端，断言会失败在「读不到 body」上，而那与服务端行为无关** ——
> 极易被误判成「服务端的 bug」，从而去改本来正确的服务端代码。
> 改用 JDK 的 `HttpClient` 后稳定读到全部响应体。
