# LinkForge 数据库设计（DATABASE）

> 上游依据：`docs/PRD.md`（v1 范围与容量假设）、`docs/ARCHITECTURE.md`（缓存、事务边界、降级）。
> 决策来源：`docs/DECISIONS.md`（DR-001 ~ DR-012）。
> 本文档**只做设计描述**：含字段语义、索引意图与保留策略；**不含实体类，不含可直接执行的建表 SQL**。

---

## 1. 上游约束与设计目标

| 来源 | 约束 | 对数据库设计的直接要求 |
|---|---|---|
| PRD §6.2 | 1000 万短链总量、**活跃比例 1%**、日 500 万跳转、统计保留 90 天 | 单库单表；统计行数上界约 900 万行（§9） |
| PRD §6.3 | 创建后立即可跳、删除后立即可失效 | 短链的写入与状态变更必须强一致 |
| PRD §7.2 | 跳转路径**不写数据库** | 跳转只读；PV/UV 计数不落库，靠异步批量写 |
| PRD US-4 | 已过期 → 410；不存在 → 404 | `status` 与 `expire_at` 必须能区分两种失效 |
| PRD D-5 | 只存按天聚合，不留原始明细 | 统计表按「短码/链路 + 日期」聚合，无明细表 |
| ARCHITECTURE §7.1 | 布隆过滤器**每小时从 DB 全量重建** | 需要一个高效的「只扫有效短码」的访问路径（§5.2） |
| ARCHITECTURE §10 | 缓存与布隆在事务提交后操作 | 表操作与缓存操作的事务边界必须清晰 |
| DR-011 | 短码由**发号器**分配，固定 7 位 | 需要号段/序号存储；`short_code` 唯一索引降为兜底 |
| DR-012 | 活跃比例 1% 是「不做分表」的前提 | 该假设必须可被实测校验（§9.3） |

**设计目标**：让「短链的真相」在一个单库单表里完整、可校验、可维护 90 天以上，并且**不给跳转路径引入任何写操作**。

**非目标**：不做分库分表、不做读写分离、不做数据仓库式明细留存、不做跨库事务。

## 2. 存储选型与职责边界

| 存储 | 角色 | 存什么 | 丢了会怎样 |
|---|---|---|---|
| **MySQL 8** | **唯一真相来源** | 短链记录、发号序号、统计聚合结果 | **数据丢失，不可接受**（需备份） |
| **Redis 7** | 加速与计数 | 跳转缓存、布隆过滤器、PV/UV 计数、限流状态 | **可接受**：缓存回源重建；布隆靠定时重建；未落库的统计会丢（分钟级） |

**核心原则：真相只在 MySQL。** Redis 全丢不影响短链的正确性，只影响性能与最近几分钟的统计（ARCHITECTURE §15.3）。

**明确不做的存储选型**：不引入 Elasticsearch（无全文检索需求）、不引入时序库（统计粒度是「天」不是「秒」）、不引入 MQ（v1 无异步消息需求，ARCHITECTURE §8.1）。

## 3. 逻辑数据模型总览

三组数据，按「真相 → 派生 → 基础设施」排列：

```
┌─────────────────────┐
│  短链主表            │  真相：短码 ↔ 原始 URL、状态、过期时间
│  (short_link)       │  写少读多；被唯一索引与布隆重建依赖
└──────────┬──────────┘
           │ 1 : N（按天）
           ▼
┌─────────────────────┐
│  统计聚合表          │  派生：按天 × 链路 × 来源域的 PV/UV
│  (link_stat_daily)  │  只写聚合结果，不存明细；保留 90 天
└─────────────────────┘

┌─────────────────────┐
│  发号序列表          │  基础设施：号段分配（DR-011）
│  (id_segment)       │  仅在 Redis 不可用的降级路径与初始化时使用
└─────────────────────┘
```

刻意**不建**的表：无来源维度表（§4.3 内联理由）、无访问明细表（PRD D-5）、无用户表（PRD D-9）、无短码映射历史表（短码不可变）。

## 4. 字段设计要点

> 本节描述**字段语义与约束意图**，不给出建表语句。字段类型是设计约定，最终以 `docs/DATABASE.md` 定稿后的迁移脚本为准。

### 4.1 短链主表

| 字段 | 语义 | 关键约定 |
|---|---|---|
| `id` | 内部主键（自增或号段分配） | 统计表用 `link_id` 关联，**不直接存短码**（见 §4.3） |
| `short_code` | 短码 | **固定 7 位** Base62；**唯一**；**只读不可改**；自动生成与自定义**共用同一唯一空间** |
| `target_url` | 原始长链 | **`VARCHAR(2048)`**；创建接口**拒绝超长**（返回参数错误，不截断） |
| `status` | 状态 | **`TINYINT`**：`0 = ACTIVE`，`1 = DELETED`。**不使用 ENUM** |
| `is_custom` | 是否自定义短码 | 用于区分自动生成与自定义，便于排查与运营 |
| `expire_at` | 过期时间 | **可 NULL** ⇒ 永久有效；精确到秒 |
| `created_at` | 创建时间 | **由数据库生成**（`DEFAULT CURRENT_TIMESTAMP`），避免多实例时钟差异 |
| `updated_at` | 最后变更时间 | 状态变更时更新，便于排查「何时被删」 |

**逐条说明关键取舍**：

- **`short_code` 唯一性与「共用同一空间」**：自定义短码与自动生成短码若分属两个空间，一定会出现「自定义的码正好等于将来某个自动生成的码」而撞码。共用一张表、一个唯一索引是唯一安全的做法。
- **`target_url` 为什么是 2048**：覆盖绝大多数真实 URL（浏览器与主流服务对 URL 长度的实际容忍上限量级）。**明确不做的事**：不截断超长 URL（截断会产生指向错误地址的短链，比拒绝更危险）、不做 URL 归一化（去 `utm_*` 参数、统一大小写、去末尾斜杠）——归一化会让「用户提交的链接」与「实际跳转的链接」不一致，v1 只做字符串精确存储。
- **`status` 为什么用 `TINYINT` 而不是 `ENUM`**：`ENUM` 的取值变更需要 DDL（改表），且不同驱动/ORM 对 ENUM 的映射行为不一致；`TINYINT` 取值变更只需应用层约定，迁移成本低。
- **`expire_at` 与 `status` 的职责分离**：两者表达**不同的事**——`status=DELETED` 是「人主动删的」，`expire_at < now` 是「时间到了」。PRD US-4 要求两者返回**不同状态码**（404 vs 410），合并成一个字段会让这个区分变得晦涩。

### 4.2 失效判定优先级（写死，不允许各处以不同顺序实现）

```
1. 先看 status：
     status = DELETED  → 404 Not Found（直接返回，不看 expire_at）
2. 再看 expire_at：
     expire_at IS NOT NULL 且 expire_at <= now  → 410 Gone
3. 否则：
     status = ACTIVE 且未过期 → 正常 302
```

**为什么优先级必须写死**：如果各条代码路径对「已删除且已过期」的链接给出不同状态码（一处 404、一处 410），对外行为就不确定，`docs/API.md` 的契约与测试都无从写起。**删除是更强的语义，优先级高于过期。**

### 4.3 统计聚合表

| 字段 | 语义 | 关键约定 |
|---|---|---|
| `link_id` | 关联短链主表 `id` | **`BIGINT`**；**不设外键约束**；**不直接存 `short_code`** |
| `stat_date` | 统计日期 | 按**自然日**；与 `link_id` 组成唯一键 |
| `referer_domain` | 来源域名 | **只存域名**；**空 Referer 存字符串 `'direct'`，不存 NULL** |
| `pv` | 当日浏览量 | 累加语义（UPSERT）：`pv = pv + VALUES(pv)` |
| `uv_estimated` | 当日独立访客 | **HyperLogLog 估算值**，约 0.81% 误差（PRD §7.4）；覆盖语义：`GREATEST(uv_estimated, VALUES(uv_estimated))` |
| `created_at` / `updated_at` | 落库与更新时间 | 便于排查落库延迟 |

> ⚠️ **字段名是 `uv_estimated` 不是 `uv`**（V4 迁移完成的重命名）。
> 名字带 `-ed` 后缀是刻意的：它是估算值，误差约 0.81%，
> 读 SQL 的人一眼就该看出**不能拿它精确对账**。
> 若叫 `uv`，下游很容易误以为它与 `pv` 一样是精确值。

**逐条说明关键取舍**：

- **为什么不存 `short_code` 而存 `link_id`**：短码长度可变（将来若改长度或加混淆），而 `link_id` 是稳定标识；统计表若直接存短码，一旦短码编码规则变化，历史统计就需要回填。用 `link_id` 让统计表与「短码如何编码」解耦。
- **落地时的映射成本**：Redis 里的统计 key 以**短码**命名（`shortlink:pv:{code}:{yyyymmdd}`），
  而表里存 `link_id`。落库前必须做一次批量映射：
  `SELECT id, short_code FROM short_link WHERE short_code IN (...)`。
  这条 SQL 走 `uk_short_code` 唯一索引且**只 select 两列**，不回表读 2048 字节的 `target_url`。
  ⚠️ 映射**不过滤 `status`**：软删除的短链仍有历史访问量，那部分统计不该丢。
- **为什么不设外键约束**：外键会在每次统计落库时对主表加锁校验，而统计是**每分钟一次的批量写入**，高频批量写 + 外键校验会显著抬高写入成本，并让「短链被清理」与「统计行存在」互相牵制。**完整性由应用层保证**（统计行的产生必然源于一次真实跳转）。这是有意识的取舍，不是疏忽。
- **Referer 解析为什么在应用层**：解析「完整 URL → 域名」需要处理端口、路径、子域、国际化域名、畸形输入等大量边界情况，放在应用层才能写单测、才能统一处理异常；数据库里只存已解析好的域名，保持窄而规整。
- **空 Referer 为什么存 `'direct'` 而不是 NULL**：NULL 在聚合查询里需要 `IFNULL`/`COALESCE` 特殊处理，且 NULL 与「未知」在语义上难以区分。用 `'direct'` 让「直接访问/无来源」成为**普通取值**，查询与统计逻辑保持一致；同时也让唯一键可用（唯一键含 NULL 的行为不直观）。
- **来源为什么不单独建维度表**：来源域是**低基数**字符串（几十到几百个），拆分只会引入一次 join 和一张几乎不变的表，收益为零（§3 已声明不建）。

### 4.4 发号序列表（DR-011）

| 字段 | 语义 | 关键约定 |
|---|---|---|
| `biz_tag` | 业务标识 | 便于将来多业务共用一张号段表 |
| `max_id` | 当前已分配到的最大序号 | 号段分配的权威值 |
| `step` | 号段步长 | 每次取一整段，减少数据库往返 |
| `updated_at` | 更新时间 | 用于排查发号停滞 |

- **用途**：Redis 不可用时的**降级发号路径**（DR-011），以及初始化时确定起始序号。
- **为什么不直接用数据库自增主键当短码序号**：短链主表的主键在将来可能需要变更（如归档、重建），而「已发出去的号」**永远不能回收或重复**。把发号状态独立成表，让发号与业务表解耦，是这个设计的关键。
- **号段取走的号若未用完就重启**：会**跳号**（浪费一小段号）。这是可接受的——短码不需要连续，只需要唯一。

## 5. 索引设计

> 每加一个索引都必须回答：**服务于哪条查询**、**写入代价是多少**。没有明确查询场景的索引不加。

### 5.1 唯一索引：`short_code`

| 项 | 说明 |
|---|---|
| 服务的场景 | ① 跳转回源按短码查；② 创建时插入；③ 自定义短码占用判定；④ 布隆重建全量扫描 |
| 写入代价 | 每次创建多一次唯一索引维护（低频写路径，可接受） |
| 定位 | **兜底防线**：发号器保证短码天然无碰撞，唯一索引用于在出现意外时**保证不出错**而不是**保证不出重**（DR-011） |

### 5.2 覆盖索引：`(status, short_code)` —— 布隆重建专用

| 项 | 说明 |
|---|---|
| 服务的场景 | **布隆过滤器每小时全量重建**：`WHERE status = 0` 只取有效短码，只读这两列 |
| 为什么需要 | 若走主键或全表扫描，1000 万行的重建会读大量无用列（URL 最长 2048 字节，全表扫是巨大的 IO 浪费） |
| 代价 | 多一个二级索引的写入与存储成本；换取**每小时一次可预期的、只读小列的扫描** |
| 执行时机 | **低峰期执行**（避免与峰值跳转流量抢 IO） |

**这是本设计中最关键的一个索引**：它把布隆重建从「可能的全表扫」变成「可控的索引区间扫」，直接决定重建成不成问题。

### 5.3 统计表唯一索引：`(link_id, stat_date, referer_domain)`

| 项 | 说明 |
|---|---|
| 服务的场景 | ① 落库 UPSERT 的冲突判定；② 按链路 + 日期范围查统计；③ 按日期批量清理 |
| 顺序理由 | 查询总是「先定链路（`link_id`）→ 再定日期范围（`stat_date`）→ 来源是低基数尾巴」，因此 `link_id` 打头 |
| 为什么唯一 | 保证「同一链路 + 同一天 + 同一来源域」只有一行，UPSERT 的幂等性来源 |

### 5.4 统计表清理索引：`stat_date`

| 项 | 说明 |
|---|---|
| 服务的场景 | 90 天保留的**按日期批量删除**（§8.2） |
| 为什么单独需要 | 清理条件是纯 `stat_date` 范围，与 5.3 的索引前缀（`link_id`）不匹配，无法复用 |

### 5.5 过期扫描索引：`idx_expire_status (status, expire_at)`

> ⚠️ **本节是阶段 4 新增的**（V5 迁移）。它**推翻了 V1 的一个决定**——
> V1 曾明确写「不建 `expire_at` 索引，因为过期判定走读时惰性判定」。
> 那个判断在「只有读时判定」时是对的，但阶段 4 增加了「定时批量扫描过期短链」的主路径，
> 于是这个索引从「不需要」变成了「必需」。

| 项 | 说明 |
|---|---|
| 服务的场景 | 阶段 4 过期清理的扫描（§6.2）。⚠️ 清理**不修改 status**，但扫描条件仍是 `status = 0 AND expire_at < ?`（只清理「有效但已过期」的短码） |
| 列顺序为什么是 `(status, expire_at)` | `status` 做**等值前缀**、`expire_at` 承担**范围扫描**——范围查询索引的标准形态 |
| 为什么 `idx_status_code (status, short_code)` 不够 | 那个索引的 `status` 是等值前缀但 `expire_at` **不在索引里** → MySQL 只能先取出所有 `status=0` 的行**回表**读 `expire_at` 再过滤。这是「看起来用了索引、实际是全表扫」的典型 |
| 实测差距 | 20 万行、2000 条已过期：`type=ref, rows=97,181` → `type=range, rows=2,000`，约 **50 倍** |

⚠️ **为什么这个索引能跳过「已软删除」的过期行**：
软删除后 `status` 变成 1，这些行不该被反复扫描。
`(status, expire_at)` 让优化器能同时用上两个条件
（实测「50% 过期行已软删除」时估算行数从 2000 降到 1）。

完整实测数据与验证方法见 docs/TROUBLESHOOTING.md T-011。

### 5.6 明确不建的索引

| 不建 | 理由 |
|---|---|
| `target_url` 上的索引 | v1 无「按长链反查短链」的需求（幂等创建已明确不做，PRD D-8）；2048 字节的 URL 建索引代价高 |
| `expire_at` **单列**索引 | 阶段 4 已有 `(status, expire_at)` 复合索引。单列版本会被复合索引完全覆盖（复合索引的前缀就是 expire_at 的单列能力），纯属浪费 |
| `status` 单列索引 | 选择性极差（绝大多数行都是同一个值），单独使用无意义；它在 5.2 与 5.5 的复合索引里作为前缀才有价值 |

## 6. 并发与唯一性

- **`short_code` 唯一索引是唯一真相**。应用层的任何判重都只做「优化路径」，**不做正确性保证**。
- **正常路径不依赖冲突重试**：发号器（DR-011）保证序号唯一 ⇒ 短码唯一。唯一索引冲突一旦发生，说明发号器或编码逻辑有 bug，应当**记指标 + 告警**，而不是静默重试掩盖问题。
- **自定义短码是唯一会真正发生冲突的路径**：其唯一性完全由数据库唯一索引判定，冲突返回**冲突错误（409 语义）**，**不做静默覆盖**（PRD US-2）。
- **明确不使用「先查再插」**：并发下必然存在竞态窗口（两个请求同时查到「未占用」→ 同时插入）。正确做法是**直接插入并依赖唯一索引裁决**。
- **事务边界**（与 ARCHITECTURE §10 一致）：
  - 创建：事务覆盖「插入短链记录」（含发号序号的推进），提交后再写布隆过滤器；
  - 删除：事务内改 `status`，提交后再删缓存；
  - 统计落库：事务覆盖批量 UPSERT，提交后再清理 Redis 计数 Key。

## 7. 失效与清理策略

### 7.1 过期判定：读时惰性判定为基线

- **基线机制**：读路径（跳转回源）拿到记录后**当场判定** `status` 与 `expire_at`（§4.2）。
- **为什么以惰性判定为基线**：它保证**正确性不依赖任何后台任务能否按时运行**。即使清理任务挂了、延迟了，过期链接依然不会生效。
- **物理清理是「维护」而不是「正确性来源」**：清理任务只负责释放空间与保持布隆重建的扫描量，它的失败不影响业务正确性。

> ✅ **阶段 4 已落地这个清理任务**（`ExpiryCleanupService`，每 5 分钟一次）。
> 上面的原则**没有被推翻**——清理任务挂了，过期链接依然跳不过去（惰性判定照常生效）。
>
> ⚠️ **阶段 4 的清理任务完全不修改 `status`**：短链的 `status` 保持 `ACTIVE`，
> 过期判定仍由读路径的 `LinkState.resolve` 完成 → **410 Gone**。
>
> ⚠️ 这一点是**刻意**的：若清理把短链软删除成 `DELETED`，
> 因为 `status = DELETED` 优先于 `expire_at`（§4.2），
> 对外状态码会从 410 变成 404 —— 那是对外契约的回退
> （410 的价值正是告诉调用方「这个码曾经有效」）。
>
> 详见 docs/DECISIONS.md DR-060 决策 2 与 docs/DESIGN-W4.md §6.3。

### 7.2 删除语义

- 删除采用**标记状态**（`status = 1`），**不做物理删除**。
- 理由：
  1. 布隆过滤器**不支持删除**（DR-007），被删短码在过滤器里仍为「可能存在」，物理删除不会改变这一点；
  2. 保留记录可以回答「这条短链曾经存在、由谁在何时删除」，对排查与运营有价值；
  3. 物理删除会与统计表的 `link_id` 产生悬空引用（统计表无外键约束，不会报错但会让统计无法解释）。
- **删除后短码是否可被重新使用**：**不可**。发号器不会重发已用序号，且被删短码的记录仍在表中（唯一索引仍然占用）。这是刻意的——已分享出去的链接不应被后来者接管。

### 7.3 90 天保留与清理

- 统计聚合数据保留 **90 天**（PRD §6.2）。
- **清理方式：按日期批量 `DELETE`，低峰期执行**。
  - 单次删除按 `stat_date < 今天 - 90 天` 的区间进行，分批提交（避免一次删除大事务长时间持锁）。
  - 走 §5.4 的 `stat_date` 索引。
- **分区表列入 v2 备选**：按 `stat_date` 做 range 分区后，清理可以退化为「直接 drop 分区」，比批量 DELETE 更快、对业务影响更小。v1 不做的理由：900 万行的量级下批量 DELETE 完全可控，而分区会引入分区键约束、跨分区查询与迁移复杂度——在当前量级属于过度设计。

## 8. 统计聚合与落库

> ⚠️ **本节已按阶段 3 的实际实现更新**（2026-10-21）。
> 落库流程的细节见 docs/DESIGN-W4.md §5 与 docs/DECISIONS.md DR-059。

### 8.1 落库流程（与 ARCHITECTURE §5.4、§8 一致）

```
定时任务（每分钟，@Scheduled cron + Redis 全局锁）
  1. 守卫：queue.isRunning() 为 false 则整轮跳过
  2. 取全局锁 shortlink:stats:flush:lock（SET NX EX 60）
     └─ 拿不到：跳过本轮（多实例下正常）
  3. SPOP shortlink:stats:dirty:{date}  → 当日待落库的短码清单（取走即删）
  4. 批量映射短码 → link_id（SELECT id, short_code ... IN，走 uk_short_code）
  5. GETDEL shortlink:pv:{code}:{date} → PV 增量（取走即删）
     PFCOUNT shortlink:uv:{code}:{date} → UV 估算（只读，不删）
  6. 落库：PV 与 UV 是**两条独立**的批量 UPSERT
     └─ PV 失败：重试 3 次（1s/4s/16s）→ 仍失败 → 写死信（stage=mysql, channel=pv）
     └─ UV 失败：重试 3 次（1s/4s/16s）→ 仍失败 → 写死信（stage=mysql, channel=uv）
  7. 死信重放：LRANGE 窥探 → 靶向重试 → LREM 精确删除成功的条目
  8. 释放锁（Lua 校验 value，不误删他人的锁）
```

⚠️ **为什么 PV 与 UV 分成两条 SQL**：PV 是**增量**（`pv = pv + VALUES(pv)`），
UV 是**当日累计估算**（`GREATEST(uv_estimated, VALUES(uv_estimated))`）。
合并成一条后，「PV 已成功、UV 失败」的重试会把 PV 再累加一遍 ——
而 PV 一旦多加**无法回滚**。详见 DR-059 决策 3。

⚠️ **为什么 UV 用 `GREATEST` 而不是累加**：`PFCOUNT` 返回的是「当日至今的基数」，
不是增量。累加会让同一个访客被计 1440 遍（一分钟 flush 一次）。
`GREATEST` 既符合语义（当日值只增不减），又让重试天然幂等。

### 8.2 幂等性的来源

- **「取走即删」**（SPOP / GETDEL）⇒ 同一份增量**不会被处理两次**。
  这是本项目最重要的一条约束：对于累加型统计，
  **重复处理比丢失严重得多**（多了无法回滚，少了可以补）。
- **UPSERT 累加** ⇒ 落库「重放同一份数据」会让 PV 翻倍，
  所以 DLQ 重放必须**靶向**（`channel=pv` 只补 PV，`channel=uv` 只补 UV）。
- ⚠️ **已知的重复计数窗口**：若「MySQL 写成功但客户端收到异常」，
  重试会再加一次。这个窗口无法完全消除（分布式系统的固有代价），
  但通过「取走即删」已把窗口从「每轮都可能」缩小到「单次网络抖动」。
  接受这个不精确，并在文档中写明，避免被当成 bug 排查。

### 8.3 批大小与写入量估算

- 每分钟一轮 ⇒ 每天 **1440 轮**。
- 每轮的聚合行数取决于**当轮被访问的不同链路数**，而非请求数。
  按日 500 万跳转估算，活跃比例 1%（PRD §6.2）⇒ 约 5 万活跃短码，
  单轮聚合行数通常在**几十到几百行**量级（活跃分布高度集中于热门短链）。
- 单轮写入用**批量 UPSERT** 完成（`batch-size: 500`），避免逐行往返。
- ⚠️ **单轮最多处理 20 批**（`max-batches-per-run`）：
  `SPOP` 到空为止在理论上没有次数上限，而一批落库最坏要 45 秒（重试 42s + IO）。
  无上限会让这一轮长期占着全局锁，后续轮次全部因抢不到锁而空转。
  没处理完的数据下一分钟继续——**这不是丢失**（SPOP 只移除已取走的部分）。

## 9. 容量估算与增长

### 9.1 前提（来自 PRD §6.2 + DR-012）

| 假设 | 值 |
|---|---|
| 短链总量 | 1000 万 |
| **活跃短链比例** | **1%（约 10 万条）** |
| 日跳转量 | 500 万 |
| 统计保留 | 90 天 |

### 9.2 量级估算

**短链主表**：

- 行数：**1000 万**。
- 单行主要开销：`target_url` 平均长度决定。按平均 100 字节估算，加短码（7 字节）、状态与时间字段、索引开销，单行量级约 **200~300 字节**。
- 总量级：**约 2~3 GB**（含索引）。对 MySQL 8 单表完全可控。

**统计聚合表**：

- 行数上界 = **活跃短链 × 保留天数 = 10 万 × 90 = 约 900 万行**。
- 聚合行只含 `link_id`、日期、域名（短字符串）、两个整数 ⇒ 单行约 **100 字节**量级。
- 总量级：**约 1 GB**（含索引）。单表可控。

**Redis 内存**：

| 项 | 估算 |
|---|---|
| 布隆过滤器 | **约 12MB**（规格写死，DR-007） |
| 跳转缓存 | 按热点短码数 × 单条 URL 长度；被缓存的是「被访问过的短码」，量级远小于 1000 万 |
| UV HyperLogLog | **约 12KB / key**，key 数 = 活跃链路 × 天数；900 万个 key 是不可接受的，见下方 ⚠️ |
| 限流状态 | 按活跃 IP 数 × 单 key 开销，随窗口自动过期 |

> ⚠️ **必须正视的 HLL 内存上界问题**：若为「每个活跃链路 × 每一天」都保留一个 HLL，90 天 × 10 万 = 900 万个 key × 12KB ≈ **108GB**，这**远远超出单机内存**。
> 因此实现上**必须**满足：HLL key 只在**当天**存活（TTL 到当天结束后不久即过期，因为聚合结果当天就会被落库），落库后立即释放。这样并发存活的 HLL key 数上界 ≈ **当日活跃链路数**（约 10 万 × 12KB ≈ **1.2GB**），属于可接受量级。
> 这条约束是**硬性**的：HLL key 不允许跨天长期驻留。该点已记入 §12 待确认项，需在实现时用 TTL 与落库清理双重保证。

### 9.3 ⚠️ 活跃比例假设必须被实测校验（DR-012）

- 「活跃短链比例 1%」是**估算**，不是观测结果。它同时是「不做分表」结论的前提。
- **校验动作（第 1 周基线阶段）**：统计「当日被访问过的短码数 / 短码总量」，得出实际比例并回填本文档与 PRD §6.2。
- **若实测显著高于 1%**：统计表行数与 HLL 内存都会按比例放大，必须重新评估：
  1. 缩短统计保留期（如 90 天 → 30 天）；
  2. 统计表改分区表（v2 备选提前）；
  3. 降低 `referer_domain` 维度的粒度（如只保留 Top-N 渠道）。
- **不允许**在实测数据与假设冲突时默默沿用失真假设。

## 10. 数据生命周期与备份

| 数据 | 生命周期 | 说明 |
|---|---|---|
| 短链记录 | **永久**（软删除标记保留） | 已分享出去的短码不可重发；删除只改状态 |
| 统计聚合行 | **90 天** | 按日期批量清理（§7.3） |
| Redis 缓存 | TTL 决定（最长约 1 小时 5 分钟） | 丢了回源重建 |
| Redis 布隆 | 每小时重建 | 丢了靠重建恢复，不依赖持久化 |
| Redis HLL | **当天内**（落库后释放） | 见 §9.2 的 ⚠️ 硬约束 |

- **备份**：MySQL 需有备份策略（真相来源）；Redis **不需要**为持久化做额外投入（RDB 即可，ARCHITECTURE §15.3）。
- **恢复目标**：MySQL 恢复后，Redis 缓存与布隆可自动重建，**不依赖 Redis 备份**。这是「Redis 可丢」设计的直接收益。

## 11. 数据迁移与初始化

- **工具：Flyway**（决策见本章末决策点），版本化迁移脚本进仓库。
- **脚本命名：`V1__init_schema.sql` 格式**（`V<版本>__<描述>.sql`，双下划线分隔）。后续变更依次为 `V2__...`、`V3__...`，**版本号只增不改**。
- **DDL 硬性禁令**：
  - **禁止 `DROP TABLE`**。表一旦进入仓库历史就不得在迁移脚本里删除；如需废弃，改为停用 + 记录在文档中。
  - 理由：迁移脚本会在评审者的干净环境里**从零执行**，也可能在已有数据的环境里**增量执行**。`DROP TABLE` 在前者无害、在后者是数据灾难，且无法用「只在本地跑」辩解。
  - 同理禁止 `TRUNCATE`、禁止无 `WHERE` 的破坏性 DML。
- **初始化数据**：号段表的初始行（`biz_tag` / `max_id` / `step`）需要在首次启动时存在，由迁移脚本插入或应用启动时兜底初始化。
- **迁移与启动的关系**：迁移在应用启动时自动执行，满足 PRD A-1「干净目录按 README 一键起、无手工建表步骤」。

**本章决策点：迁移工具选型**

| 选项 | 说明 | 评价 |
|---|---|---|
| **Flyway（选中）** | 版本化 SQL 迁移，启动时自动执行 | ✅ 让建表成为启动过程的一部分，消除 README 里的人工步骤；schema 变更可追溯 |
| 手工 SQL 脚本 | 人工执行 | ❌ 把人工步骤转移给评审者，直接违背 PRD A-1 |
| Liquibase | 支持 XML/YAML/SQL 多种描述方式 | ❌ 能力超出本场景需求，概念更多 |
