## 故事 1：性能「劣化」66% 的真凶不是缓存，是一次同步阻塞

### Situation（背景）

第 2 周项目优化到 **81,290 QPS**（P50 0.97ms），是第 1 周 13,427 QPS 的 **6.05 倍**。
第 3 周加了布隆过滤器、单飞回源、L1 优先读取三项功能后，
QPS 却掉到 **27,641**——按当时的预注册目标（6~9 万），这是**未达标**。

### Task（任务）

在「只新增功能、不改核心逻辑」的前提下，定位这 66% 的降幅来自哪里。

### Action（行动）

**① 先证伪最可能的假设。** 降幅出现的同周新增了布隆过滤器，
第一反应是「布隆误判率太高导致大量回源」。但监控显示**布隆误判率稳定在 0.1%**
（`docs/PERFORMANCE.md`），缓存命中率也没掉——假设被数据否掉。

**② A/B 对照，而不是猜。** 加 `linkforge.ratelimit.enabled` 开关做对照，
且**必须完全跳过 EVAL**（把阈值调到 100 万做不到——Lua 仍会执行，只是不再拒绝）：

| 组 | 限流 | QPS | P50 | P99 |
|---|---|---|---|---|
| A | 开启 | 21,085 | 4.39ms | 15.74ms |
| B | 关闭 | **56,638** | 1.29ms | 8.40ms |

**③ CPU 采样定位瓶颈位置。** 这是最关键的一步：

| 组件 | CPU 占用 |
|---|---|
| linkforge-app | **900%**（约 9 核满载） |
| linkforge-redis | **0.4%** |

Redis 占用不到 0.5%，**远未饱和**——瓶颈不在 Redis 的计算能力，
而在**应用线程同步等待网络往返**。
⚠️ 若只看「QPS 掉了就去查 Redis」，会完全找错方向。

**④ 找到根因。** 限流在 `RedirectController` 的**最前端**，
在 L1 缓存**之前**——于是**每个请求（包括 100% 命中 L1 的请求）**
都要先过一次同步 Redis EVAL（约 0.5ms），在 Tomcat 线程池里累积成吞吐断崖。

**⑤ 优化。** 用 Lua 合并往返、去掉每次操作的 `PEXPIRE`，
把限流路径的折损从 **63% 收窄到约 51%**（DR-056）。

### Result（结果）

- 归因链完整：**限流路径的同步阻塞**，而非缓存退化或布隆误判（DR-056）。
- 产出 3 条可迁移的方法论：
  1. **性能劣化先证伪最可能的假设**，用数据排除而不是用直觉坚持；
  2. **A/B 对照的开关必须能「完全跳过」被测逻辑**（放宽阈值不等于跳过）；
  3. **CPU 采样比 QPS 曲线更能定位瓶颈位置**——
     「谁在满载」直接区分了「计算慢」与「等待慢」。
- 顺带发现压测流量共享同一个 IP 令牌桶（单 key 写热点），
  并明确写下「**不能用『生产环境多 IP 会分散』来开脱**」——
  单 IP 高频攻击正是限流要防的场景。
- ⚠️ **诚实记录**：第 3 周的 27,641 QPS **未达预注册的 6~9 万**，
  该记录**原样保留在 `PERFORMANCE.md §10.5`**，不回头修改判据（DR-052）。

### 可能的追问

| 追问 | 回答要点 |
|---|---|
| 为什么不直接把限流放到 L1 之后？ | 那样会让「未命中缓存的请求」绕过限流吗？不——真正的问题是限流语义必须覆盖**所有**跳转请求，不能因为缓存命中就免检。所以只能优化限流路径本身（合并往返、去 PEXPIRE），不能挪位置。 |
| Lua 里去掉 PEXPIRE 会不会导致 key 永不过期？ | 用的是「带 TTL 的首次 SET + 不续期」策略，靠单独的清理兜底；具体权衡见 DR-056。 |
| 27,641 vs 81,290 差这么多，为什么还能算「优化成功」？ | 两者**口径不同**：81,290 是不带限流的极限值。第 3 周的目标是「在完整限流语义下跑多快」，不是复刻第 2 周的数字。这正是 `PERFORMANCE.md §11.2` 要把「同配置基线」与「调优版」分开的原因。 |

## 故事 2：Mock 全绿 ≠ 链路通了——从一次「上线即全 500」到三层测试体系

### Situation（背景）

第 3 周实现了「布隆检查 + L2 查询合并为一次 Redis 往返」的优化
（`RedisBloomFilter.checkAndGet`），提交时写「5 条验证全过」。
**上线后跳转全部 500。**

### Task（任务）

找出「测试全绿、脚本也对」的代码为什么一上线就崩，
并建立能拦住这类问题的验证体系。

### Action（行动）

**① 逐层盘问「到底验了什么」。** 那个测试是
`@ExtendWith(MockitoExtension.class)` + `@Mock StringRedisTemplate`
—— **`redis.execute` 本身被打桩**，参数序列化的真实行为从未执行。

| 层 | 当时的验证 | 有效性 |
|---|---|---|
| Lua 脚本行为 | `redis-cli --eval` + MONITOR | ✅ 真的验过 |
| 返回值解析 | Mockito 构造 `List.of(...)` | ⚠️ **形状由测试者决定** |
| **Java 调用 → Spring Data Redis → Lua** | **完全没有** | ❌ **缺陷所在** |

**② 定位到 3 个缺陷**，其中一个是真正的「500 触发器」：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `toArgs` 返回 `List<String>`，而 `redisTemplate.execute(script, keys, Object... args)` 是**变参** | List 被当成**单个元素**包成 `Object[]{list}` → `StringRedisSerializer` 内部 `(String) value` 强转 → **ClassCastException** |
| 2 | `toArgs` 首元素是 `BIT_SIZE` 占位符，Lua 从 `for i = 2` 开始 | 只检查 **k-1 = 6** 个位，**Lua 不报错**（静默的错误结果） |
| 3 | `catch (DataAccessException)` 抓不住 CCE（它是 `RuntimeException`） | 本该「降级为回源」的兜底失效，异常穿透到 Controller → 500 |

**③ 补上缺失的那一层**，并把教训固化成**三层测试体系**：

| 层 | 覆盖什么 | 手段 |
|---|---|---|
| L1 单元 | 纯逻辑 | Mockito + 手写替身（**明确不 mock 被测边界**） |
| L2 集成 | 真实中间件 | **真实 MySQL 容器**（Testcontainers）+ **真实 Redis** + 真实 Lua |
| L3 E2E | 整条链路 | 真实 HTTP + 断言**外部可见效果**（状态码 + Location 头） |

**④ 消除「静默跳过」。** 原集成测试靠环境变量开关
（`RUN_MYBATIS_IT`），缺失时**整个类被跳过**——
而「跳过」在 CI 上和「通过」长得一模一样。改为 Testcontainers 一次性容器，
**环境变量依赖全部消除**（`TEST_MYSQL_PASSWORD` / `RUN_MYBATIS_IT` / `ADMIN_API_TOKEN`）。

**⑤ 顺带修掉一个隐蔽陷阱**：E2E 里用 `System.getenv("ADMIN_API_TOKEN")`
读取凭据，**绕过了 Spring 的属性源**——`application-test.yml` 里配的固定值
完全不生效，干净环境（CI / 新克隆）下必失败。改为 `@Value` 注入。

### Result（结果）

- 从「mock 全绿 → 上线全 500」到 **611 个测试全绿**
  （含 **58 个真实 MySQL 8.4 容器测试** + **20 个真实 Redis 集成测试** + **8 个 E2E**）。
- 产出 2 条方法论：
  1. **「两端都验过」不等于「链路通了」**——
     必须明确说清验证的是**哪一层**，写「验证全过」时不能省略成「全过」（DR-054）；
  2. **凡涉及跨进程/跨语言边界（Redis Lua、HTTP、MQ 序列化），
     mock + 脚本单独验证不够**，必须有走真实链路的测试（DR-054）。
- 附带产出：`docs/TROUBLESHOOTING.md`（20 条排障记录）与
  `docs/PITFALLS.md`（防呆清单），把踩过的坑变成可复用的知识资产。

### 可能的追问

| 追问 | 回答要点 |
|---|---|
| 为什么不直接把 mock 换成真实 Redis？ | 换不了——**被测边界**（`redisTemplate.execute`）正是要验证的对象，mock 掉它等于没测。正确做法是加更高一层的测试（真实 Redis 的集成测试 / 真实 HTTP 的 E2E），而不是替换 mock。 |
| Testcontainers 让 CI 变慢怎么办？ | 实测**全量 1 分 37 秒**、容器**只启动 1 次**（静态初始化块 + JVM shutdown hook，所有测试类共享同一个已启动容器）。慢的原因从来不是容器本身，而是**每个测试类各起一个**。 |
| 三层都要写，成本怎么控？ | 分层依据是**「这个 bug 会在哪一层暴露」**：纯逻辑错误 L1 能抓；序列化/协议错误 L1 抓不到（mock 的形状是测试者自己定的）；跨进程错误只有 L2/L3 能抓。**不是每层都写全套**，是每层只写它能抓的那类。 |

## 故事 3：推翻一个「伪 bug」——Metaspace 涨的是元空间，不是堆

### Situation（背景）

第 3 周压测时记录到：应用容器连续运行 19 小时后，
**Metaspace 涨到 74MB**，G1 频繁 evacuation，吞吐掉了 50%+，
重启容器后 Metaspace 清零、QPS 恢复（DR-057）。
怀疑对象写进了决策记录：**疑似 Micrometer 动态 Tag 导致**。

### Task（任务）

第 5 周做 8 小时长稳测试，验证这到底是不是内存泄漏。

### Action（行动）

**① 先做静态核查，把「怀疑」拆成可证伪的子命题。**

| 假设 | 核查结果 | 判断 |
|---|---|---|
| Micrometer 动态 Tag | 代码里**所有** tag 值都是**编译期常量**，无 per-request meter 创建 | ❌ **不成立** |
| 弱引用 Gauge 泄漏 | `AsyncStatsQueue` 的 Gauge 绑定 `final` 字段，被 Spring 强引用 | ❌ **不成立** |
| 动态代理 / 反射类加载 | 全模块扫描 `Proxy.newProxyInstance` / `Class.forName` / CGLIB：**零命中** | ❌ **不成立** |

**② 发现原判断犯了一个概念错误**（这是整个故事的转折点）：

> **Metaspace 涨 = 类加载多。堆涨 = 对象多。两者机制完全不同。**
>
> - Metaspace 存的是**类元数据**，只有**加载新类**才会涨（类一旦加载就永不卸载，
>   除非类加载器被回收）。
> - Micrometer 的 Meter 是**普通堆对象**，动态 tag 增长的是**堆**，与 Metaspace 无关。
>
> 所以「动态 Tag 导致 Metaspace 增长」这条**因果链根本不成立**——
> 就算 tag 是动态的，涨的也是堆。

**③ 用实测数据检验「74MB 是不是基线」。** 重启后取干净基线：
**Metaspace 70.7MB / 已加载类 14,638**——与 DR-057 记录的「19 小时后 74MB」
**只差 3MB**。这强烈提示 74MB 是**正常基线**，不是泄漏。

**④ 设计能区分三种情况的观测方案**，而不是只测一条曲线：

| 曲线 | 判读 |
|---|---|
| `jvm_memory_used_bytes{area="nonheap",id="Metaspace"}` | 怀疑对象 |
| `jvm_classes_loaded_classes` | ⭐ **最直接的证据**：平稳但 Metaspace 涨 = 类卸载不掉；线性增长 = 能用 jcmd 抓类名 |
| `shortlink.meter.count`（自建 Gauge） | 对照组：动态 tag 涨的是**堆**不是元空间 |

⚠️ **一个差点让结论反转的坑**：查 `jvm_memory_used_bytes{area="metaspace"}`
返回**空**——而 Metaspace 的 area 其实是 **`nonheap`**。
**空曲线看起来像「没有泄漏」，结论会完全反过来**（TROUBLESHOOTING T-020）。

**⑤ 跑 8 小时长稳。** ⏳ 数据待补（见下）。

### Result（结果）

⏳ **待补**：8 小时长稳的最终曲线 + 结论（证伪 / 证实）。

**已确定的部分**（无论结论如何都成立）：

- **认知修正**：Metaspace 是类加载，动态 Tag 是堆。原 DR-057 的因果链被推翻。
- **方法论价值**：一个「看起来像 bug 的现象」被证伪，
  **比发现 100 个 bug 更能体现工程能力**——它要求区分「现象」与「机制」，
  并用「干净基线 vs 长跑后」的可比数据说话。
- **可观测性建设**：为了能回答这个问题，补了 `shortlink.meter.count` Gauge、
  开了 `percentiles-histogram`、把 `path` tag 显式关掉并写明理由
  （`path` 是实际路径 → 每个短码一个 tag → meter 数线性增长 → **堆涨 + Prometheus series 爆炸**）。
- ⚠️ **诚实记录**：DR-057 的原始怀疑**原样保留**，
  修正以新增决策的形式记录，而不是改写历史。

### 可能的追问

| 追问 | 回答要点 |
|---|---|
| 怎么确认 74MB 是基线而不是「刚好正常」？ | 对比三个数据点：干净基线 70.7MB、第 3 周长跑后 74MB、本次 8 小时长跑后的值。**关键是长跑曲线是否线性**——如果 8 小时后仍是 73~75MB 且已加载类数平稳，就是基线；如果线性增长到 100MB+，就是泄漏。 |
| 如果 Metaspace 真在涨，第一步查什么？ | `jvm_classes_loaded_classes`。它平稳 → 是类卸载不掉（查 ClassLoader 引用）；线性增长 → `jcmd VM.classloader_stats` + `jcmd GC.class_histogram` 直接抓出新增的类名。 |
| 为什么不直接用 arthas / async-profiler？ | 那类工具需要 attach 到生产进程，在容器里改配置的成本高于收益。**先用已有的 Micrometer 指标 + jcmd（JDK 自带）**——够用且零侵入。 |
