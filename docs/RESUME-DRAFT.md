## 压测数据汇总（四个标签）

> ⚠️ **口径警告（放简历里也可以，但必须带一句）**：
> 第 2 周与第 3 周的数字**不是同一口径**——
> 第 2 周**没有限流**，第 3 周**有完整限流语义**。
> 直接说「第 3 周比第 2 周慢了 66%」是**误导**。
> 正确的说法是：「第 3 周在**加上了限流**之后仍跑到 2.7 万」。

| 周次 | Tag | 关键变更 | QPS | P50 | P99 | 非 302 / Socket 错误 |
|---|---|---|---|---|---|---|
| 第 1 周 | `w1-baseline` | 无缓存，直查 DB | **13,426** | 6.59ms | 未采 | 0 / 0 |
| 第 2 周 | `w2-cache` | + 两级缓存（L1 本地 + L2 Redis） | **81,290** | **0.97ms** | 未采 | 0 / 0 |
| 第 3 周 | `w3-shield` | + 布隆合并往返 + 回源单飞 + **限流** | **27,641** | 3.30ms | 11.74ms | 0 / 8 |
| 第 5 周 | `w5-final` | + Prometheus/Grafana + 异步统计 + 过期清理 | **29,387.67** | **3.08ms** | **11.00ms** | 0 / 4 |

> ⚠️ **第 5 周的对比结论**：QPS 从第 3 周的 27,641 涨到 **29,387.67（+6.3%）**，
> P50 从 3.30ms 降到 **3.08ms（-6.7%）**，P99 从 11.74ms 降到 **11.00ms（-6.3%）**。
>
> **在加入完整监控栈（Prometheus 每 15s 抓一次 `/actuator/prometheus`，
> 该端点每次都要遍历并序列化全部 meter）之后，性能没有任何衰减迹象。**
> 这正是第 5 周的真正验收点。

**后端容量拐点**（阶梯加压，固定 `-t4` 递增 `-c`）：

| 并发深度（`-c`） | QPS | P50 | P99 | wrk CPU 峰值 |
|---|---|---|---|---|
| 50 | 18,247 | 2.31ms | 11.31ms | 138% |
| 100 | 20,980 | 4.20ms | 19.22ms | 153% |
| 200 | 25,223 | 7.15ms | 24.14ms | 156% |
| **400** | **28,758**（峰值） | 12.86ms | 34.77ms | 177% |
| 800 | **26,435**（↓8.1%） | 27.80ms | **76.06ms** | 178% |

> **拐点在 c=400~800 之间**。判读的关键是 **wrk CPU 峰值只有 1.4~1.8 核 / 18 核** ——
> 压测端远未饱和，所以曲线反映的是**后端**的真实容量。

### 一句话概括（性能演进）

> **从第 1 周的无缓存 1.3 万，到第 2 周的 8.1 万（提升 6 倍）；第 3 周为了防刷加了限流，主动牺牲部分性能降至 2.7 万。最终在物理机极限（3.2 万）下，保证了系统的安全性、稳定性和可观测性。**

> ⚠️ **注（放简历时可以删，但面试时值得主动说）**：
> 「主动牺牲」指的是**在完整限流语义下的运行能力**，不是「关掉功能换性能」。
> 第 3 周的归因链是完整的（DR-056）：限流在 Controller 最前端、
> 每个请求（含 100% L1 命中）都要过一次同步 Redis EVAL；
> A/B 对照显示关掉限流能到 5.66 万，CPU 采样显示 **app 900% / redis 0.4%**
> —— 瓶颈是**应用线程同步等待**，不是 Redis 算不动。
> 用 Lua 合并往返 + 去掉每次的 `PEXPIRE` 把限流折损从 63% 收窄到 51%。
>
> **第 5 周的验收点不是「刷到多少 QPS」，而是「加监控后性能无明显衰减」** ——
> 而 `/actuator/prometheus` 每次被访问都要遍历并序列化全部 meter，
> 这是前三周**不存在**的新负载。本机物理上限约 3.2 万 QPS
> （18 核 − 宿主固有 3 核 − 压测端 1.5 核，每请求 417 µs CPU），
> 所以判据是「25,000~32,000 + P99 ≤ 15ms + 零错误」。

### 压测方法论（同样是可讲的部分）

| 做法 | 为什么 |
|---|---|
| 3 次取**中位数**（不是平均、不是最好那次） | 单次有偶然性；中位数对偶发毛刺不敏感 |
| 每轮**重启 app** | 清 Metaspace 与 GC 状态，否则与基线周不同起点（DR-057 的教训） |
| **等布隆全量重建完成**再预热 | 布隆没建好时前几千个请求全 miss，会拉高 P99、拉大 QPS 离散度 |
| 预热 15s 且**丢弃**结果 | JIT 需要收敛（DR-057 的现象 3） |
| 压测前**停掉 Prometheus/Grafana** | `/actuator/prometheus` 每次访问都序列化全部 meter —— 前三周不存在的新污染源 |
| 语料**轮换**而非固定一个码 | 固定一个码会 100% L1 命中、数据库完全不参与，测的不是真实负载 |
| 记录**宿主 CPU 占用**并标注偏差源 | 第 5 周有 WorkBuddy agent 占约 2 核（第 1/2/3 周没有）→ QPS 天然偏低 ~11% |

## 故事 1：性能「劣化」66% 的真凶不是缓存，是一次同步阻塞

### Situation（背景）

第 2 周项目优化到 **81,290 QPS**（P50 0.97ms），是第 1 周 13,427 QPS 的 **6.05 倍**。
第 3 周加了布隆过滤器、单飞回源、L1 优先读取三项功能后，
QPS 却掉到 **27,641**——按当时的预注册目标（6~9 万），这是**未达标**。

### Task（任务）

在「只新增功能、不改核心逻辑」的前提下，定位这 66% 的降幅来自哪里。

### Action（行动）

**① 先证伪最可能的假设。** 降幅出现的同周新增了布隆过滤器，
第一反应是「布隆误判率太高导致大量回源」。但监控显示**布隆误判率稳定在 0.1%**
（`docs/PERFORMANCE.md`），缓存命中率也没掉——假设被数据否掉。

**② A/B 对照，而不是猜。** 加 `linkforge.ratelimit.enabled` 开关做对照，
且**必须完全跳过 EVAL**（把阈值调到 100 万做不到——Lua 仍会执行，只是不再拒绝）：

| 组 | 限流 | QPS | P50 | P99 |
|---|---|---|---|---|
| A | 开启 | 21,085 | 4.39ms | 15.74ms |
| B | 关闭 | **56,638** | 1.29ms | 8.40ms |

**③ CPU 采样定位瓶颈位置。** 这是最关键的一步：

| 组件 | CPU 占用 |
|---|---|
| linkforge-app | **900%**（约 9 核满载） |
| linkforge-redis | **0.4%** |

Redis 占用不到 0.5%，**远未饱和**——瓶颈不在 Redis 的计算能力，
而在**应用线程同步等待网络往返**。
⚠️ 若只看「QPS 掉了就去查 Redis」，会完全找错方向。

**④ 找到根因。** 限流在 `RedirectController` 的**最前端**，
在 L1 缓存**之前**——于是**每个请求（包括 100% 命中 L1 的请求）**
都要先过一次同步 Redis EVAL（约 0.5ms），在 Tomcat 线程池里累积成吞吐断崖。

**⑤ 优化。** 用 Lua 合并往返、去掉每次操作的 `PEXPIRE`，
把限流路径的折损从 **63% 收窄到约 51%**（DR-056）。

### Result（结果）

- 归因链完整：**限流路径的同步阻塞**，而非缓存退化或布隆误判（DR-056）。
- 产出 3 条可迁移的方法论：
  1. **性能劣化先证伪最可能的假设**，用数据排除而不是用直觉坚持；
  2. **A/B 对照的开关必须能「完全跳过」被测逻辑**（放宽阈值不等于跳过）；
  3. **CPU 采样比 QPS 曲线更能定位瓶颈位置**——
     「谁在满载」直接区分了「计算慢」与「等待慢」。
- 顺带发现压测流量共享同一个 IP 令牌桶（单 key 写热点），
  并明确写下「**不能用『生产环境多 IP 会分散』来开脱**」——
  单 IP 高频攻击正是限流要防的场景。
- ⚠️ **诚实记录**：第 3 周的 27,641 QPS **未达预注册的 6~9 万**，
  该记录**原样保留在 `PERFORMANCE.md §10.5`**，不回头修改判据（DR-052）。

### 可能的追问

| 追问 | 回答要点 |
|---|---|
| 为什么不直接把限流放到 L1 之后？ | 那样会让「未命中缓存的请求」绕过限流吗？不——真正的问题是限流语义必须覆盖**所有**跳转请求，不能因为缓存命中就免检。所以只能优化限流路径本身（合并往返、去 PEXPIRE），不能挪位置。 |
| Lua 里去掉 PEXPIRE 会不会导致 key 永不过期？ | 用的是「带 TTL 的首次 SET + 不续期」策略，靠单独的清理兜底；具体权衡见 DR-056。 |
| 27,641 vs 81,290 差这么多，为什么还能算「优化成功」？ | 两者**口径不同**：81,290 是不带限流的极限值。第 3 周的目标是「在完整限流语义下跑多快」，不是复刻第 2 周的数字。这正是 `PERFORMANCE.md §11.2` 要把「同配置基线」与「调优版」分开的原因。 |

## 故事 2：Mock 全绿 ≠ 链路通了——从一次「上线即全 500」到三层测试体系

### Situation（背景）

第 3 周实现了「布隆检查 + L2 查询合并为一次 Redis 往返」的优化
（`RedisBloomFilter.checkAndGet`），提交时写「5 条验证全过」。
**上线后跳转全部 500。**

### Task（任务）

找出「测试全绿、脚本也对」的代码为什么一上线就崩，
并建立能拦住这类问题的验证体系。

### Action（行动）

**① 逐层盘问「到底验了什么」。** 那个测试是
`@ExtendWith(MockitoExtension.class)` + `@Mock StringRedisTemplate`
—— **`redis.execute` 本身被打桩**，参数序列化的真实行为从未执行。

| 层 | 当时的验证 | 有效性 |
|---|---|---|
| Lua 脚本行为 | `redis-cli --eval` + MONITOR | ✅ 真的验过 |
| 返回值解析 | Mockito 构造 `List.of(...)` | ⚠️ **形状由测试者决定** |
| **Java 调用 → Spring Data Redis → Lua** | **完全没有** | ❌ **缺陷所在** |

**② 定位到 3 个缺陷**，其中一个是真正的「500 触发器」：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `toArgs` 返回 `List<String>`，而 `redisTemplate.execute(script, keys, Object... args)` 是**变参** | List 被当成**单个元素**包成 `Object[]{list}` → `StringRedisSerializer` 内部 `(String) value` 强转 → **ClassCastException** |
| 2 | `toArgs` 首元素是 `BIT_SIZE` 占位符，Lua 从 `for i = 2` 开始 | 只检查 **k-1 = 6** 个位，**Lua 不报错**（静默的错误结果） |
| 3 | `catch (DataAccessException)` 抓不住 CCE（它是 `RuntimeException`） | 本该「降级为回源」的兜底失效，异常穿透到 Controller → 500 |

**③ 补上缺失的那一层**，并把教训固化成**三层测试体系**：

| 层 | 覆盖什么 | 手段 |
|---|---|---|
| L1 单元 | 纯逻辑 | Mockito + 手写替身（**明确不 mock 被测边界**） |
| L2 集成 | 真实中间件 | **真实 MySQL 容器**（Testcontainers）+ **真实 Redis** + 真实 Lua |
| L3 E2E | 整条链路 | 真实 HTTP + 断言**外部可见效果**（状态码 + Location 头） |

**④ 消除「静默跳过」。** 原集成测试靠环境变量开关
（`RUN_MYBATIS_IT`），缺失时**整个类被跳过**——
而「跳过」在 CI 上和「通过」长得一模一样。改为 Testcontainers 一次性容器，
**环境变量依赖全部消除**（`TEST_MYSQL_PASSWORD` / `RUN_MYBATIS_IT` / `ADMIN_API_TOKEN`）。

**⑤ 顺带修掉一个隐蔽陷阱**：E2E 里用 `System.getenv("ADMIN_API_TOKEN")`
读取凭据，**绕过了 Spring 的属性源**——`application-test.yml` 里配的固定值
完全不生效，干净环境（CI / 新克隆）下必失败。改为 `@Value` 注入。

### Result（结果）

- 从「mock 全绿 → 上线全 500」到 **611 个测试全绿**
  （含 **58 个真实 MySQL 8.4 容器测试** + **20 个真实 Redis 集成测试** + **8 个 E2E**）。
- 产出 2 条方法论：
  1. **「两端都验过」不等于「链路通了」**——
     必须明确说清验证的是**哪一层**，写「验证全过」时不能省略成「全过」（DR-054）；
  2. **凡涉及跨进程/跨语言边界（Redis Lua、HTTP、MQ 序列化），
     mock + 脚本单独验证不够**，必须有走真实链路的测试（DR-054）。
- 附带产出：`docs/TROUBLESHOOTING.md`（20 条排障记录）与
  `docs/PITFALLS.md`（防呆清单），把踩过的坑变成可复用的知识资产。

### 可能的追问

| 追问 | 回答要点 |
|---|---|
| 为什么不直接把 mock 换成真实 Redis？ | 换不了——**被测边界**（`redisTemplate.execute`）正是要验证的对象，mock 掉它等于没测。正确做法是加更高一层的测试（真实 Redis 的集成测试 / 真实 HTTP 的 E2E），而不是替换 mock。 |
| Testcontainers 让 CI 变慢怎么办？ | 实测**全量 1 分 37 秒**、容器**只启动 1 次**（静态初始化块 + JVM shutdown hook，所有测试类共享同一个已启动容器）。慢的原因从来不是容器本身，而是**每个测试类各起一个**。 |
| 三层都要写，成本怎么控？ | 分层依据是**「这个 bug 会在哪一层暴露」**：纯逻辑错误 L1 能抓；序列化/协议错误 L1 抓不到（mock 的形状是测试者自己定的）；跨进程错误只有 L2/L3 能抓。**不是每层都写全套**，是每层只写它能抓的那类。 |

## 故事 3：推翻一个「伪 bug」——Metaspace 涨的是元空间，不是堆

### Situation（背景）

第 3 周压测时记录到：应用容器连续运行 19 小时后，
**Metaspace 涨到 74MB**，G1 频繁 evacuation，吞吐掉了 50%+，
重启容器后 Metaspace 清零、QPS 恢复（DR-057）。
怀疑对象写进了决策记录：**疑似 Micrometer 动态 Tag 导致**。

### Task（任务）

第 5 周做 8 小时长稳测试，验证这到底是不是内存泄漏。

### Action（行动）

**① 先做静态核查，把「怀疑」拆成可证伪的子命题。**

| 假设 | 核查结果 | 判断 |
|---|---|---|
| Micrometer 动态 Tag | 代码里**所有** tag 值都是**编译期常量**，无 per-request meter 创建 | ❌ **不成立** |
| 弱引用 Gauge 泄漏 | `AsyncStatsQueue` 的 Gauge 绑定 `final` 字段，被 Spring 强引用 | ❌ **不成立** |
| 动态代理 / 反射类加载 | 全模块扫描 `Proxy.newProxyInstance` / `Class.forName` / CGLIB：**零命中** | ❌ **不成立** |

**② 发现原判断犯了一个概念错误**（这是整个故事的转折点）：

> **Metaspace 涨 = 类加载多。堆涨 = 对象多。两者机制完全不同。**
>
> - Metaspace 存的是**类元数据**，只有**加载新类**才会涨（类一旦加载就永不卸载，
>   除非类加载器被回收）。
> - Micrometer 的 Meter 是**普通堆对象**，动态 tag 增长的是**堆**，与 Metaspace 无关。
>
> 所以「动态 Tag 导致 Metaspace 增长」这条**因果链根本不成立**——
> 就算 tag 是动态的，涨的也是堆。

**③ 用实测数据检验「74MB 是不是基线」。** 重启后取干净基线：
**Metaspace 70.7MB / 已加载类 14,638**——与 DR-057 记录的「19 小时后 74MB」
**只差 3MB**。这强烈提示 74MB 是**正常基线**，不是泄漏。

**④ 设计能区分三种情况的观测方案**，而不是只测一条曲线：

| 曲线 | 判读 |
|---|---|
| `jvm_memory_used_bytes{area="nonheap",id="Metaspace"}` | 怀疑对象 |
| `jvm_classes_loaded_classes` | ⭐ **最直接的证据**：平稳但 Metaspace 涨 = 类卸载不掉；线性增长 = 能用 jcmd 抓类名 |
| `shortlink.meter.count`（自建 Gauge） | 对照组：动态 tag 涨的是**堆**不是元空间 |

⚠️ **一个差点让结论反转的坑**：查 `jvm_memory_used_bytes{area="metaspace"}`
返回**空**——而 Metaspace 的 area 其实是 **`nonheap`**。
**空曲线看起来像「没有泄漏」，结论会完全反过来**（TROUBLESHOOTING T-020）。

**⑤ ⭐ 长稳跑起来后，数据推翻了我自己的一个推论。**

我最初写下的是「`unloaded_total = 0` ⇒ Metaspace 增长 ≡ 累计加载了新类」，
理由是类一旦加载就永不卸载。但运行 1 小时后的实测**不支持**它：

```
[16:10:29] Metaspace=77168928 (+0.089MB)  Classes=+0  Unloaded=0
```

**Metaspace 涨了 93KB，而 LoadedClassCount 一点没涨。**

原因是 JDK 15+ 的 **hidden class（lambda 隐藏类）**——
它们**计入 Metaspace，但不计入 LoadedClassCount**。
修正后的表述是两层：
- 已加载类数**只增不减**（`unloaded` 恒为 0，类加载器从未被回收）
  → 它是「类加载累积」的**上界**证据；
- Metaspace 增长 = 已加载类 + **hidden class（lambda）** + 其它元数据。

于是分析方法也跟着变：必须看**两个增量的比值**——
普通类约 **19KB/类**（实测 45 类 → 0.84MB），比值远大于此即有 hidden class 贡献。

⭐ **而这恰好指向了我在设计阶段列的「嫌疑 3：Lambda 隐藏类累积」**。
关键性质：lambda 隐藏类的数量 = 代码里**不同的 lambda 调用点**数量（固定），
**与请求量无关** → 若长跑后收敛（不线性增长），就**不是泄漏**。

**⑥ 跑 8 小时长稳。** ✅ 数据见下（Metaspace +1.55MB 收敛、0 次 Full GC）。

### Result（结果）

> ### ✅ 判定：**不是泄漏**。「Micrometer 动态 Tag 导致 Metaspace 泄漏」是**伪 bug**。

**8 小时实测数据**（3.7 亿次真实跳转，≈ 12,566 QPS）：

| 节点 | Metaspace | Classes | Meters | GC | Full GC |
|---|---|---|---|---|---|
| 基线（重启后） | 72.47 MB | 14,946 | 197 | — | — |
| 2 小时 | 73.78 MB | 14,995 | 199 | — | — |
| 4 小时 | 74.01 MB | 14,996 | 199 | — | — |
| **8 小时** | **74.02 MB** | **14,996** | **199** | **14,388** | **0** |

**增量逐段收敛**：`1.06 → 0.23 → 0.08 → 0.05 → **0.00 MB/h**`（最后 2 小时仅 +5.8 KB）。

**六条互相独立的依据**：

1. 8 小时只涨 **1.55 MB**，增量**单调收敛到 0** —— ⚠️ **泄漏是恒定速率增长，不是单调递减**
2. **已加载类数从 t=120m 起完全平稳** —— 没有持续加载新类
3. **Meter 数从 t=30m 起恒为 199**（7.5h 零增长）—— **动态 Tag 根本没涨**，原怀疑被直接证伪
4. **零 Full GC**，14,388 次全是 young GC
5. ⭐ **JVM 自己触发了 1 次 `Metadata GC Threshold`** —— 元空间管理机制正常工作，不是应用层失控
6. 终点 **74.02 MB** 与 DR-057 的「19 小时后 74MB」**几乎一致** —— 那是**稳态基线**

**认知修正（这个故事的核心）**：

> **Metaspace 是类加载，动态 Tag 是堆。**
> - Metaspace 存**类元数据**，只有**加载新类**才会涨；
> - Micrometer 的 Meter 是**普通堆对象**，动态 tag 增长的是**堆**，与 Metaspace 无关。
>
> 所以「动态 Tag 导致 Metaspace 增长」这条**因果链在机制上就不成立** ——
> 就算 tag 真的动态，涨的也是堆。

**Hidden Class 机制**（中途的一次修正）：运行 1 小时后实测
`Metaspace +93KB 而 LoadedClassCount +0` —— 根因是 **JDK 15+ 的 hidden class**
（lambda 隐藏类**计入 Metaspace 但不计入 `LoadedClassCount`**，
且其数量 = 代码里不同 lambda 调用点数，**与请求量无关**）。

**可观测性建设**（为了能回答这个问题而补的）：
`shortlink.meter.count` Gauge、`percentiles-histogram`、
把 `path` tag 显式关掉并写明理由（`path` 是实际路径 → 每短码一个 tag →
meter 数线性增长 → **堆涨 + Prometheus series 爆炸**）。

⚠️ **诚实记录**：DR-057 的原始怀疑**原样保留**，修正以新增决策（DR-061）的形式记录，
而不是改写历史（DR-052 的原则）。

⚠️ **排查中我自己犯的三个错**（这部分可能比结论更值得讲）：
- **「GC 恒为 1」** —— 取了多 series 查询的第一条，拿到的是
  `Metadata GC Threshold`（count=1）而非 `G1 Evacuation Pause`（14,387），**差了 4 个数量级**
- **「PV 累计 1,805」** —— 同样是「第一条」，拿到的是 `/actuator/prometheus`
  的抓取数（30 分钟 120 次 = 抓取频率，**看起来完全合理**），真正的 PV 是 3.7 亿
- **shell 引号嵌套静默破坏查询** —— `--data-urlencode "query=$q"` 里 $q 含双引号时
  参数被拆散，Prometheus 返回空而**脚本不报错**

> **教训**：**「数字看起来合理」是最危险的验证方式。**
> 自洽不等于正确 —— 一个**自洽的错数**会让整个 8 小时的曲线都变成另一个故事。

### 可能的追问

| 追问 | 回答要点 |
|---|---|
| 怎么确认 74MB 是基线而不是「刚好正常」？ | 对比三个数据点：干净基线 70.7MB、第 3 周长跑后 74MB、本次 8 小时长跑后的值。**关键是长跑曲线是否线性**——如果 8 小时后仍是 73~75MB 且已加载类数平稳，就是基线；如果线性增长到 100MB+，就是泄漏。 |
| 如果 Metaspace 真在涨，第一步查什么？ | `jvm_classes_loaded_classes`。它平稳 → 是类卸载不掉（查 ClassLoader 引用）；线性增长 → `jcmd VM.classloader_stats` + `jcmd GC.class_histogram` 直接抓出新增的类名。 |
| 为什么不直接用 arthas / async-profiler？ | 那类工具需要 attach 到生产进程，在容器里改配置的成本高于收益。**先用已有的 Micrometer 指标 + jcmd（JDK 自带）**——够用且零侵入。 |
| 为什么不用 jcmd 一直盯着？ | ① `GC.class_histogram` 会触发 **full GC**，会污染 GC 曲线；② 容器是 **JRE 镜像不含 jcmd**，跨容器 attach 还要处理 PID/mount namespace（实测直接 jcmd 会报 `Unable to open socket file /tmp/.java_pid1`）。所以我选了 Micrometer 的 `jvm_classes_*` 指标做**无侵入连续量**分析——**趋势本来就比快照更适合回答「是否线性增长」**。 |

## 故事 4：一个「201 创建成功却立刻 404」的缺陷 —— 真相是并发覆盖，不是写穿没生效

### Situation（背景）

第 6 周封板后的本地验收，一组自相矛盾的现象：

```
POST /api/v1/links   → 201（短码 0000VF0 已落库，id=94151）
GET  /0000VF0        → 404 {"code":"LINKFORGE-404-01","message":"短码不存在: 0000VF0"}
docker compose restart app + 等 1 分钟 → 仍然 404
docker compose logs app | findstr "布隆" → **无任何输出**
```

「接口说创建成功、数据库查得到、跳转却说不存在」——
这是短链系统的**头号信任危机**（用户刚拿到的链接打不开）。

### Task（任务）

找出根因并修掉。要求：创建后**立刻**可跳转、重启后旧短码可跳转，
且要补上**能防回归**的测试。

### Action（行动）

**① 我的第一判断是错的，而且是被实测证伪的。**

直觉是「写穿没调用」——新建的短码不在布隆里 → 被判「一定不存在」→ 404。
但实测否定了它：**在重建窗口期外新建的短码，立刻就能 302**。
写穿一直在生效。⇒ 方向必须从「写穿有没有执行」转到「**写穿执行了之后为什么没了**」。

**② ⭐ 只相信时间戳：把三条时间线对齐。**

布隆全量重建不是瞬时的，它是**分钟级**作业。
所以「哪个时刻落库」与「哪个时刻重建」的关系才是关键：

```
11:20:16  重建 #1 开始：扫 id 游标 → 写 :building
11:20:42  用户创建 0000VF0 → 事务提交 → put() 写进【现行 key】
11:20:44  重建 #1：RENAME :building → shortlink:bloom   ← 覆盖语义
11:21:41  GET /0000VF0 → 布隆判「一定不存在」→ 404
```

**根因**：重建是「双缓冲 + 原子切换」，但**写穿没有双写**。
`RENAME` 是**覆盖**语义（不是按位合并），`:building` 里没有的位，切换后就彻底没了。
于是「重建期间创建、且扫描游标已越过其 id」的短码，位信息被丢弃 →
布隆产生**假阴性** → 真实用户拿到 404。

⚠️ 讽刺的是：**设计文档里写的就是「双写」**
（DR-007 原文：构建期间创建操作的写穿**同时写新旧两份**），
**代码里从来没有实现**。DR-055（第 3 周实测到）、T-027、ARCHITECTURE §7.1
都记着同一个洞，处置一直是「v1 绕过、v2 再优化」。
⇒ **两轮「已知问题」记录都没能替代一次实现。**

**③ ⚠️ 两个把排查带偏的陷阱（都不是 bug，是用法问题）**

| 陷阱 | 现象 | 为什么极具误导性 | 正确做法 |
|---|---|---|---|
| `findstr "布隆"` | 日志里"搜不到"重建记录 | Windows 默认代码页下 `findstr` 匹配不了 UTF-8 中文 —— **「没有日志」这句话本身可能是假的** | `docker logs linkforge-app 2>&1 \| grep 布隆`（Git Bash） |
| 「重启 + 等 1 分钟」 | 重启后仍然 404 | 重建 = `initialDelay` 30 秒 **加**实测 28 秒的重建耗时 ⇒ **启动后约 58~65 秒**才切到新布隆。等 1 分钟时，重建**恰好还没完成** | 等日志出现「布隆全量重建完成」再验证，不要用固定等待 |

⇒ **「重建根本没执行」与「重建执行得太晚」在日志里长得几乎一样**
（都是"等 1 分钟还是 404"）。
区分它们的唯一办法是**对齐时间戳**：落库时间 vs 重建起止 vs 请求时间。

**④ 修复（DR-065）**

| # | 改动 | 关键点 |
|---|---|---|
| 1 | **写穿双写** | `beginRebuild()` 开写穿窗口 → 窗口内 `put()` 同时写现行 key 与 `:building` → RENAME 切换后不丢 |
| 2 | **空快照绝不切换** | 库里没有有效短码时跳过重建 —— ⚠️ **空布隆的 key 是存在的**，检查脚本的逻辑是「key 不存在 → 放行；key 存在 → 逐位查」⇒ 空布隆会把**每个请求**判成「一定不存在」→ **全站 404** |
| 3 | **重建提速 8 倍** | 逐条 7 次 SETBIT → **批量 pipeline**：2 万条 **28 秒 → 3.5~6 秒**（重建越慢 ⇒ 暴露窗口越长，提速直接缩小故障窗口） |
| 4 | **批量写独立超时预算** | 跳转路径的 50ms 是**跳转命令**的延迟预算（宁可超时降级查库），批量写用它必然 `Redis command timed out` ⇒ 维护路径另给 5s（连接参数仍同源，不复制配置） |
| 5 | **启动即重建** | 由 `ApplicationReadyEvent` 触发，不再只靠定时任务的 `initialDelay` —— 否则「重启后访问旧短码」依赖上一个实例留下的旧布隆，它若是空的，旧短码集体 404 |
| 6 | **写穿失败不污染响应** | `afterCommit` 时事务**已提交**，异常抛出去 = 「接口 500 但数据已落库」⇒ 诱发调用方重试创建 ⇒ 重复短链 |

⚠️ 第 1 条有两个**顺序约束**（写反即复发）：
**写穿窗口**与 **`:building` 的删除**都必须在**数据库扫描之前**。
这两行换个位置，**编译照样通过、单测照样全绿**（没有任何测试断言过顺序）——
所以我用 Mockito 的 `InOrder` **把顺序钉死**。

**⑤ ⭐ 测试纪律：删掉自己的「假绿」，再做变异验证**

E2E 的 `createLink()` 里原本有一段「手工把短码的 7 个位写进布隆」的代码。
**那等于替应用把写穿做了** —— 于是写穿坏掉时，所有 E2E 用例**照样全绿**。
这正是本次缺陷能溜过两层测试的原因。删掉它，位由应用的写穿负责。

然后做**变异验证**（mutation testing 的最小形态）：把修复临时改成
`if (false && rebuilding.get())` → 断言「重建窗口期写穿不丢」的回归测试**变红** ⇒
证明这条测试真的能抓到这个缺陷，而不是恰好是绿的。

### Result（结果）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 2 万条短码全量重建 | 28 秒 | **3.5~6 秒**（pipeline） |
| 启动后布隆可用 | ~58~65 秒 | **~4~7 秒**（启动即重建） |
| 新建短码**立刻**跳转 | 窗口期内 **404** | **302**（E2E + 容器实测） |
| 重启后访问旧短码 | **404** | **302** |
| 应用日志 ERROR 行数 | 每次验收一屏栈 | **0** |

**新增测试 11 条**（4 条 E2E + 7 条单测），全量 **651 个测试 0 失败**。
E2E 断言里特意加了「布隆里 **7 个位都为 1**」——
因为布隆 key 不存在时检查脚本会**放行**，只断言 302 会是**假通过**。

**顺带清掉两个噪声源**：`/favicon.ico` 落到 `/{code}` 会被判 400，
而**每个浏览器标签页都请求一次** ⇒ 错误日志被噪声淹没 ⇒ 显式映射 204；
「方法不被支持」由 500 改 405（不再有 `AbstractHandlerMethodMapping` 的 ERROR 栈）。

### 可能的追问

| 追问 | 回答要点 |
|---|---|
| 为什么 RENAME 会把位吃掉？ | Redis 的 `RENAME` 是**覆盖**语义（目标 key 被整体替换），不是按位合并。双缓冲只保证「重建期间现行 key 不被删」，**不保证「切换前的增量进了新缓冲」**——后者必须靠写穿双写。 |
| 为什么不干脆用 `BITOP` 把现行 key 的位并进 `:building`？ | ① 9500 万位逐位并集成本高；② 并集只能覆盖「切换前已写入」的部分，**扫描游标之后的并发写入仍会丢**。双写从源头解决，代价只有「窗口期每次写穿多 7 个 SETBIT」。 |
| 多实例部署下这招还成立吗？ | **不成立**。窗口标志目前是**进程内**的 `AtomicBoolean`（本项目单实例部署，已在代码注释里写明）。多实例需要把标志放进 Redis，让「双写」收敛到共享状态上。 |
| 怎么证明 E2E 里没有假绿？ | ① 断言布隆里 **7 个位都为 1**（key 不存在时脚本放行，只断言 302 会是假通过）；② **变异验证**：关掉修复 → 回归测试变红。 |
| 为什么 E2E 的 Redis 要单独一个逻辑库（DB 15）？ | 测试会**真实地全量重建布隆**，而产物是全局 key `shortlink:bloom`（RENAME 原子切换）。与应用共用 DB 0 ⇒ 测试里一次重建就把**本机应用已积累的真实短码的布隆整个覆盖掉** ⇒ 「跑完 mvn test 后自己创建的短码突然全 404」。 |
| 这次为什么拖了这么久？ | 前面被**两个假信号**带偏（findstr 匹配不到中文、重建比预期慢 30 秒）。教训：**排查先对齐时间戳再看结论**；检索工具的编码问题会直接制造「不存在的事件」。 |
